- [x] **M4.1 Models and the account**
  - What (PLAN M4 step 1):
    - the models of `levels.json`, `settings.json` and `users\<account>.json` in Kiler.Core, as the decisions say. Each is read from a `Document` and written to its content with a case-sensitive, source-generated JSON context, and checked: a document that does not fit (a missing name, a level out of order or twice, a name of `keys` that is not the digits of a level, values out of their limits) is invalid, with a reason, not an exception;
    - the current account behind an interface of Kiler.Core: the Windows user name without the domain, in lowercase, checked with `StorageName.Check`. Its implementation is in Kiler.App, with `--account <name>` in `StartOptions` and `--help`, and the tests use a fake.
  - Tests: each model reads what it writes; each invalid case above, and a name in another case; the account without the domain and in lowercase, a name that fails the check refused; `--account` parsed, and refused without a name or with a bad one.
  - Done: the tests of Kiler.Core and Kiler.App pass.
  - Note: decided by the user in this task. A name in `keys` of a user file or of `recovery` that is not the one digit of a level, `"1"` to the top level, makes the document invalid; the M3.3 note under this task said it is left out, and the task said invalid. `displayName` of 1 to 100 characters, not blank; `autoLockMinutes` from 1 to 1440; a level name also not blank. The decisions table of M4.md has them.
  - Note: the code. Kiler.Core: `CoreJsonContext` with the JSON types, every member nullable (`ModelJson.cs`), `KeySets` (the salt and keys of a locked set), `LevelsFile` with `LevelEntry`, `SettingsFile`, `UserFile`, and `ICurrentAccount` with `AccountName.From` (`CurrentAccount.cs`); `InternalsVisibleTo Kiler.Core.Tests` for the `TryRead(DocumentKey, JsonObject, …)` of the tests. Kiler.App: `WindowsAccount` (the name of the token through `WindowsIdentity`, not the `USERNAME` variable), not in DI until M4.4; `--account` in `StartOptions` through the same `AccountName.From` (domain dropped, lowercase), refused with `--diag`, passed on to the local copy; "--account is ignored." when a Kiler already runs. The rules are in `core.md`, "Models", and `SKILL.md`, "Windows parts".
  - Note: choices of the task, kept by the code review. A missing `check` from level 1 is valid and null, so only its level fails to verify (the M4.4 test); a check that is not a string, or a check at level 0, makes `levels.json` invalid. `salt` and `keys` are required in a user file (`{}` is valid) and `recovery` in `levels.json`, whose keys may cover only some of the levels. A member that a model does not know is skipped and left out of a write. The models keep no version. Only ASCII letters are made lowercase (`Ascii.ToLower`), as the lowercase of .NET makes the Kelvin sign `k`.

Each guard was broken alone (27 breaks, a script in the background), and each time a test of its class failed.
  - Note: the code review, one pass (light cycle): no critical or major finding. Seven minor ones are under "Left for after the exam" in M4.md. The two notes that the review found stale were fixed: the M3.2 note under M4.4 and the rule of `kiler-crypto` on a check that is not a string.
- [x] **M4.2 The state of the data and the team in memory**
  - What:
    - `KilerData` always in DI, with a state and its reason (the decisions) instead of only lines on the console, and an endpoint that gives the state to the page;
    - a service of Kiler.Core that keeps the levels, the settings and the users of the local copy. It is made when the copy opens, follows each load that changes them (`DataWatch.Loaded`), and reads the documents again after `Failed` and `OfflineChanged` (core.md, "Calling the layer").
  - Tests: each state of `KilerData`; the team follows a load (a user file new, changed, damaged, gone); the state through the API.
  - Done: the tests of Kiler.Core and Kiler.App pass.
  - Note: the code. Kiler.Core: `Team` (`Team.cs`) with `TeamFiles` (never changed, replaced whole) and `TeamFile<T>` (the model and its version, or a reason; a damaged file has no version and a reason for its damage). `Follow` takes the Changed and Gone of a load, `Reload` reads `DataCopy.Documents()` again. Kiler.App: `KilerData` takes a null `DataPlace` (no data folder chosen) and gives `State` (`DataState`, at the end of `KilerData.cs`, camelCase names through `JsonStringEnumMemberName`), `Folder` and `Team`; the handlers of the watch take the load into the team (`Follow` on `Loaded`, `Reload` on `Failed` and `OfflineChanged`), say the line, then set the state. `KilerHost.Build` always registers it, `KilerData.WithoutFolder()` when given none; `GET /api/data` (`DataApi`) gives `state`, `folder`, `levels` and `settings`. The rules are in `host.md`, "Data", and `core.md`, "The team".
  - Note: two states beyond the list of the decisions, as the open had two more cases: `unusable` (the data folder is a link, or a file is at its name) and `failed` (the local copy cannot be made or locked, or a fault of the code). `opening` lasts until the first load has ended, not only until the copy opens, so a new local copy never shows the page a team without files; at a start whose file server does not answer, that is the same 37 s, then `offline`. `levels` and `settings` of `/api/data` are a reason only while the copy is open or offline, as the team of a copy that is opening may not be the share's.

The published exe on a data folder that is not there answered `/api/data` with `"state":"missing"` (the enum names under Native AOT), stopped after its first wait and left no instance file. Seven guards were broken one by one (the Gone of a user, the same `TeamFiles` for a load without the team, the version of a damaged file, `Reload`, `open` after the first load, `open` set before the line, `offline`), and each time a test of its class failed.
  - Note: the code review, one pass (light cycle): no critical or major finding, seven minor ones. The other five are under "Left for after the exam" in M4.md.

  - Tests:

    - a self-added user (no keys, or keys of another key) does not get in;
    - a user who raised their own `level` or `isAdmin` reads only the levels of their keys, and the admin endpoints refuse them without the key of the top level;
    - a missing or damaged check counts as not verified;
    - without guest mode only the state and the sign-in answer; with it, level 0 only;
    - after a lock, a key in use answers as locked;
    - each kind of endpoint refuses whom it must.
  - Done: the tests of Kiler.Core and Kiler.App pass.

- [x] **M4.5a Change of password**
  - What (step 3, split from M4.5 by the user, as M4.5 held two new mechanisms): the change of password of the decisions, the forced one after a temporary password and the voluntary one with the current password. It locks the keys of the session again with `LevelKeys.Lock`, writes the user file through the copy (a conflict and offline are shown, not repeated), clears `mustChangePassword` in the file and in the session, and brings the write into the team. A new need lets a session with a temporary password through.
  - Tests:
    - the forced change after a temporary password;
    - a voluntary change with a wrong current password is refused;
    - the keys after a change are the same: a group made before reads after it;
    - a level of the file that did not unlock or verify refuses the change;
    - a user file at another version than at the sign-in refuses the change;
    - 7 and 1025 characters are refused;
    - the team keeps the write over a load that ended before it.
  - Done: the tests of Kiler.Core and Kiler.App pass.
  - Note: decided by the user at the start of the task. M4.5 was split into M4.5a and M4.5b (the automatic locking). A user file at another version than the session knows refuses the change with "Sign in again", as the admin may have changed its level or given a new temporary password meanwhile. For M4.5b: `/api/data` is no activity, and without a `settings.json` that fits the lock waits 30 minutes. All are in the decisions of M4.md.
  - Note: the code. Kiler.Core: `Need.SignedIn` and its check in `Access.Check`; `Session.UserVersion`, `MustChangePassword` cleared by `PasswordChanged(version)`, both under a lock of the session, and `LockKeys(password)`, which catches `ObjectDisposedException` as `Use` does; `SignIn` gives the session the version of the user file; `Team.Replace(user, version)` with `_written`, the guard against a load that ended before the write, which lives until the next `Follow`; `PasswordChange.Run` and `PasswordChangeOutcome`. Kiler.App: `PasswordApi` (`POST /api/session/password`, `PasswordRequest`), `SessionApi.Describe` public. The rules are in core.md, "The team" and "Keys and the session", and host.md, "Rights".
  - Note: choices of the task. The forced change takes no current password: the session holds the keys of the temporary one. The version of the user file is checked before the levels, so a file whose level the admin raised meanwhile answers "Sign in again", not "a level did not unlock". The write replaces the version that the session knows, so a newer version on the share that the team has not followed is a `Conflict` and the same answer; a `Conflict` at that version is a slot in the way and answers "try again in a moment" (core.md, "Calling the layer"). `Team.Replace` keeps a newer version that a load brought in between the write and the lock of the team; no test stages that race. 400 is a password that does not fit or a missing current one, 403 a wrong current password or a level that did not unlock, 409 the rest.
