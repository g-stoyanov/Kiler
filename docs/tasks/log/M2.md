- [x] **M2.1 Data folder and names**
  - What:
    - Kiler.Storage gets the layout of a data folder: the folders of design 5.1, with `history\` and `trash\` that repeat them (decided at the start of M2). A private folder `private\<account>\` (`key.json`, `records\`, `history\`, `trash\`) is a root of its own and uses the same code;
    - creating an empty data folder, for the wizard of M4, the demo data and the tests; opening an existing one, which creates nothing. A data folder that does not exist is an error, so nothing makes a `data\` by mistake;
    - a check of every name that becomes part of a path: document ids, account names, folder names. ASCII letters and digits, `.`, `-` and `_`; no leading or trailing dot, no `..`, no reserved device name of Windows (`CON`, `NUL`, `COM1` and so on, also with an extension), a length limit. Names come from the share, which anyone can write, and become paths in the local copy in the profile (M2.7), so a name is checked before any path is built from it. How an account maps to a folder name is decided in M4;
    - a folder or a file that is a link (a reparse point) is not followed. The listing gives the attributes, so this costs no extra request;
    - the file operations go through an internal interface of the layer, with the real implementation on `System.IO`. Tests can then make one step fail (M2.3), count the reads at a time (M2.7) or take the share away (M2.8);
    - the tests that touch the file system take their temporary folder from one place, so M2.11 can point them to a subfolder of the real shared folder.

- [x] **M2.2 Documents**
  - What (PLAN M2 step 2, decided at the start of M2):
    - a document is a UTF-8 JSON object with `id` and `version` at the top. The layer reads only these two and keeps the rest of the object as it is; the models come in M4 and M5, in Kiler.Core;
    - the layer sets `version`: 1 on create, one more on every write. A `version` from the caller does not count;
    - `id` equals the file name without `.json`. A root document (`settings.json`, `levels.json`, `key.json`) has its name as `id`;
    - a file that is not valid JSON, is not an object, has no matching `id`, has no whole `version` of 1 or more, or is larger than a limit is damaged. Reading it gives "damaged" with the reason, not an exception (M2.8 reports it);
    - the format of a written file (for example UTF-8 without a BOM, indented, `id` and `version` first) and the size limit are decided in the task;
    - the layer's own types use a `JsonSerializerContext` with source generation in Kiler.Storage. The content goes through `JsonNode` or `Utf8JsonReader`, which need no reflection.
  - Tests (first): a round trip with Cyrillic and with fields the layer does not know, unchanged; `version` 1 on create and one more on a write, whatever the caller sent; every kind of damaged file; an `id` that does not match its file name; a file over the limit is not read whole.
  - Done: the tests pass. Kiler.Storage.Tests runs with reflection-based JSON turned off (`JsonSerializerIsReflectionEnabledByDefault`), as Kiler.App.Tests does.
  - Note (decided in the task, by the user): the limit is 1 MiB. A written file is UTF-8 without a BOM, indented by 2 spaces, with LF and a line end after the object: `id`, then `version`, then the content in the caller's order. Non-ASCII is written as it is (`JavaScriptEncoder.UnsafeRelaxedJsonEscaping`; the file never goes into a page as it is). `Document.Content` is the object without `id` and `version`: the layer owns them, and a write drops them from the caller's content, in any case.
  - Note: the API is `Document` (`Key`, `Version`, `Content`), `DocumentRead` (`Document` or `Damage`), `DocumentDamage` (`TooLarge`, `NotJson`, `NotAnObject`, `WrongId`, `WrongVersion`), `DocumentFormat` (public `MaxSize` and `MaxDepth`; internal `New`, `Next(key, changes, content)`, and `Read` of bytes or of a stream), and the internal `DataFolder.Read` and `IFileSystem.OpenRead`. M2.2 makes the bytes and reads a file. Writing the file is M2.3, so "version 1 on create, one more on a write" is tested here on the bytes.
  - Note: a read is strict. A BOM at the start is skipped, as RFC 8259 allows. Damaged: invalid UTF-8, a comment, a trailing comma, a second value, a name twice in one object at any level (`AllowDuplicateProperties = false`, escaped names too), nesting over `MaxDepth`, an escaped lone surrogate in a string or a name, and a top-level name that is `id` or `version` in another case (`ID`), which an upper layer that ignores case would take for the layer's own. `version` must be a whole number in the text, from 1 to `int.MaxValue`: `1.0`, `1e0` and `"1"` are not. Measured: `JsonNode.Parse` does not skip a BOM, does not check the UTF-8 inside strings, and leaves an escaped lone surrogate in a value until the string is first read. A lone surrogate in a name throws `InvalidOperationException`, not `JsonException`. The writer puts U+FFFD in place of a lone surrogate in the content and throws nothing.
  - Note: `MaxDepth` is 32, half of the serializer's default of 64, so an upper layer can still wrap a document in a response of its own (security review).
  - Note (deviation): no `JsonSerializerContext` yet, as no type of the layer goes through the serializer. The content goes through `JsonNode`, `Utf8JsonWriter` and `Utf8JsonReader`. The first such type is expected with the index of the local copy (M2.7).
  - Note: a `version` of `int.MaxValue` is read, but it has no next version, and `Next` refuses it. Both reviewers proposed to make it damaged. That does not help: the version before it would then be good but could not be followed, and any limit has such a last version. Someone who sets it on the share stops the writes of that document; M2.9 decides how a restore writes over it. The second pass of `security-reviewer` agreed.
  - Note: `code-reviewer` and `security-reviewer` found nothing critical or major. Fixed: the names that are `id` or `version` in another case, the depth limit, and the comments on what a reader blocks and what `OpenRead` throws. New tests: the stream read at the limit and one byte at a time, an empty and a zeroed file, a folder in place of the file, a lone surrogate in the content, Cyrillic and escaped names, and an escaped duplicate `id`. Both reviewers found that one test row was the same as the row above it: the Write tool had turned the escape `\u0069` into `i`. The skill has it now. The second pass of `security-reviewer`, on the fixes, found nothing in the code and corrected two notes below: the worst case of memory, and the writes over `int.MaxValue`.
  - For the next tasks:
    - M2.3: a rename over a file that another handle holds open to read fails with access denied, even with `FileShare.Delete` (measured on the local disk). On SMB, the read of another Kiler, which comes within about 10 s of every change, can do the same. Decide the retry of the rename, and what becomes of the history slot when the rename still fails; M2.11 checks it on the share. Also test "version 1 on create, one more on a write" on the files;
    - M2.3: .NET 10 has `File.SetCreationTimeUtc`, `GetCreationTimeUtc`, `GetLastWriteTimeUtc` and `GetAttributes` on a `SafeFileHandle`. `FILE_FLAG_OPEN_REPARSE_POINT` refuses only the last part of the path, so a `records\` swapped for a junction is still followed, and the folder must be held too (`PinnedFolder`, M1.11);
    - M2.6: `IFileSystem.OpenRead` gives a `Stream`, and `TestFileSystem` wraps it in `CountingStream`, so the handle cannot be reached through it. Reading the owner through the handle needs a change of that interface;
    - M2.7: the local copy needs the bytes as they are, and `DocumentFormat.Read(key, Stream)` drops them. Split the read of the bytes (at most `MaxSize` + 1) from the parse. `Content` is a mutable `JsonObject`, not safe across threads, and its nodes keep the parsed `JsonDocument` alive. Measured on a 1 MiB file: 3 to 4 MiB after the parse, and once every node has been reached, as an upper layer that walks the content reaches them, 15 MiB for 100,000 names and 30 MiB for an array of 500,000 zeros. The bytes come from `Next` before the history slot is made, so a refused write leaves no slot. M2.9 decides how a restore writes over such a document;

Content stays within `DocumentFormat.MaxSize` and `MaxDepth`; over them, `New` and `Next` throw `ArgumentException`.

- [x] **M2.3 Atomic write and the file times**
  - What (PLAN M2 step 3):
    - creating a document: a temporary file in the same folder, then a rename that does not replace. An id that exists gives "exists";
    - replacing a document: a temporary file, the old version into its history slot (M2.4), then a rename over the file;
    - after the rename, the creation time of the new file is set equal to its write time, through its handle. On a rename over a name, NTFS can give the new file the creation time of the old one (file tunneling, 15 s). Both values then come from one clock, the file system's;
    - the info of a file that the layer gives: size, creation time, write time, and "edited in place" when the write time is later than the creation time (design 5.4 and 7.8);
    - a temporary file has a name that is never a document's (for example `<id>.<random>.tmp`). Readers skip it, and one older than a few minutes, which a crash leaves, is deleted;
    - once started, a write runs to its end: the caller's cancellation does not stop it between the steps, because the stop aborts requests after 5 s (M1.6).

    - a crash at each step, simulated through the file operations: the original stays intact and readable, and no file is half written under its real name;
    - after a write over an old file, within the 15 s of tunneling, the creation time equals the write time (on NTFS);
    - a file edited in place (opened and written outside the layer) is reported, and a file that the layer wrote is not;
    - a temporary file is not read as a document, and an old one is deleted.

- [x] **M2.4 Versions and conflicts**
  - What (PLAN M2 step 4, decided at the start of M2):
    - a write names the version it changes. When the version on disk is another, the result is "conflict" with the document from disk;
    - the lock is the history slot: the old version goes to `history\<folder>\<id>\vN.json` (for a root document `history\<name>\vN.json`) through a temporary file and a rename that does not replace (decided in M2.3), which is atomic also over SMB. A writer who cannot create the slot gets a conflict: the document has changed, or another write of it is under way;
    - a slot left by a crash between the slot and the rename: when it is older than a limit (about a minute) and has the same bytes as the document, the next write takes it over. Otherwise it is a conflict.
  - Tests (first): a conflict gives the version from disk; two writers of the same version at once, in many rounds: exactly one wins, the other gets a conflict, and every version has one slot; a fresh leftover slot refuses, and an old one is taken over (on a fake clock); a slot with other bytes is never taken over.
