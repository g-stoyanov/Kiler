# M6. User interface

The steps are in [PLAN.md, M6](../PLAN.md#m6-user-interface). How to work on the tasks is described in [README.md](README.md). The done tasks, with all their notes, are in [log/M6.md](log/M6.md).

Until the exam, the private records of steps 1 and 3, the two versions side by side of step 5, and steps 7 and 8 are deferred, and the theme of M1 stays ([PLAN.md, section 10](../PLAN.md#10-deferred-until-after-the-exam)). The history and the trash of step 6 and "Parameters" of step 4 are done only if there is time: M6.14 and M6.15. The tasks follow the [light cycle](README.md#light-cycle-until-the-exam): `security-reviewer` makes its one pass of M6.5 (it shows and copies the secret values) and M6.11 (what is activity for the automatic lock), and of a task that changes the Content Security Policy (kiler-ui, "The embedded build").

## Decisions for the module

Decided at the start of M6, on 2026-10-31. The rules that follow from them are in the `kiler-ui` skill.

| Question | Decision |
|---|---|
| The scope until the exam | Besides the deferred steps above: the "+" of the tree is only for a session with `canEdit`, as a user without it creates only private records with it (design 6.6). The open nodes of the tree are kept in `localStorage`, as the theme of M1 is: the origin has the port, which changes with every start, so both last one run of Kiler until the personal configuration (PLAN section 10, item 11). The request of a secret says its `use`, and the audit comes after the exam (item 1). |
| The padlocks (step 2) | A field above the session's levels shows "🔒 requires level X", with `levelName` of the field. Until the locking per level (PLAN section 10, item 6) the unlock button is the sign-in, for a guest; a signed-in user below the level has nothing to unlock, so the padlock has no button. |
| The shared folder in the UI (PLAN section 6, decided by the user) | Yes: every page shows the data folder of `GET /api/data` (`folder`) in a line at the foot of the frame (M6.2). It answers the risk of a start from a folder that someone else controls (M2, decisions). |
| `Clear-Site-Data` at the exchange (PLAN section 6, decided by the user) | After the exam, before the trial use: it needs a check in Edge with a test listener first (PLAN section 10). |
| A `url` to a loopback address (the M1.4 risk, decided by the user) | A `url` whose host is `localhost`, a name under `.localhost`, an address of `127.0.0.0/8` or `[::1]` shows as text with "Copy", not as a link, with a short sentence why: the browser sends the cookie of Kiler to every port of 127.0.0.1. Another `http` or `https` address opens in a new tab with `rel="noopener noreferrer"`; any other scheme is text (`docs/api.md`, "Values by type"). |
| The addresses | `/` is the main view. Its query is in the address as the query of `GET /api/records` (`q`, `stash`, `template`, `tag` once per tag, `field.<key>`), so the links of a stash path, Back and a reload keep the view. `/records/<id>` is a record, `/records/<id>/edit` its edit, `/new` a new record, with `?stash=<ids>` from a "+". `/trash` and `/records/<id>/history` are M6.14. |
| The texts (decided by the user; amends M1.7) | `texts.ts` stays the one place that the components read (`texts.browse.…`), but it takes each area of M6 from a file of its own in `src/ui/src/texts/`, which M6.2 makes: `browse.ts`, `record.ts`, `form.ts`, `code.ts` and `history.ts`. A task writes its texts only into the file of its area. |
| The styles | A screen of M6 keeps its CSS in a file of its own beside its component, which imports it, on the variables of `index.css`. `index.css` keeps the shared classes. |
| The changes of other users (step 9) | M6.2 gives the screens `useChanges()` (`changes.ts`): a number that M6.11 makes grow at each `changed` event of the stream, and 0 until then. A screen that reads records puts it among the dependencies of its read, so M6.11 changes no screen. |
| Parallel sessions | After M6.2, four areas can each go in a [parallel session](README.md#parallel-sessions) of their own: **A** the main view (M6.3, M6.4), **B** the record view (M6.5, then M6.14), **C** the form (M6.6, M6.7, M6.8), **D** the code (M6.9, then M6.15). The tasks of one area go one after another in its session. The main session does M6.10 and M6.11 meanwhile, and M6.12 and M6.13 once the branches are merged. Each task lists the files it owns under "Owns", and two tasks that run at the same time never change the same file. The shared files of `src/ui` (`api.ts`, `App.tsx`, `texts.ts`, `index.css`, the shared parts of M6.2, `package.json`, `package-lock.json`, `vite.config.ts` and the other configs) change only in the task that owns them; a parallel task that needs a change of one stops and asks the main session for it. |

- [ ] **M6.11 The changes of other users**
  - Session: main, after M6.10, while the parallel sessions run.
  - What (step 9; `docs/api.md`, the end):
    - Kiler sends `changed` on the event stream after a load that changed the records, the stashes, the templates or the trash, from `DataWatch.Loaded`, as one more source of the loop of `EventsApi.Events`; its format is decided here (host.md, "Heartbeat");
    - the worker passes it to every page as another `HubMessage`, and `useChanges()` grows at each, so the screens read again;
    - decided with the user before the code: how such a read is no activity for the automatic lock, as otherwise a page that the changes of others keep reading never locks.
  - Owns: `src/Kiler.App/EventsApi.cs` and what feeds it in Kiler.App, `events.ts`, `events-worker.ts`, `connection.ts`, `changes.ts`, `App.tsx`, `api.ts` when the read needs a mark, their tests, `docs/api.md`.

  - Done: the tests pass; in dev mode a change made in one browser shows in the list of another without a reload. Review also by `security-reviewer`.
  - From earlier tasks:
    - (M1.7) `changed` goes through the worker as another `HubMessage` type.
    - (M4.5b) The `changed` event is one more source of the loop of `EventsApi.Events` (host.md, "Automatic lock").
    - (M2.8) `DataWatch.Loaded` gives each load (`Changed`, `Gone`, `Outside`, `Skipped`, `TrashChanged`); the rules for a handler, and the wait of each public member of `DataCopy` for a load under way, are in `kiler-dotnet`, core.md, "Calling the layer". M6 pushes its `changed` event from `Loaded`.
    - (M2.7a) The trash comes from the local copy (`DataCopy.Trash()`), read again when a load says that it changed (`LoadResult.TrashChanged`, M2.8).
    - (M2.8a) While the share cannot be reached, the copy is offline, and its writes are refused (`kiler-dotnet`, core.md, "Calling the layer"). `DataWatch.OfflineChanged` says each change, and a page that connects reads `DataCopy.Offline`; at each change, read `Documents()` and `Trash()` again, as after `Failed`. The page shows the state since M4.7 (`DataGate`), and Kiler reads the records again at each change since M5.6 (`KilerData`), so the screens need the `changed` of it too. A start whose share cannot be reached works from the copy.
    - (M2.8b) `LoadResult.Changed` does not repeat a document whose times alone changed. A document that the copy has good, whose times anyone touches on every pass with the same bytes, is read again at most every 5 minutes, so a real change of the same size of it can show up to 5 minutes late.
