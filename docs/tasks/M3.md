## Decisions for the module

Decided at the start of M3, on 2026-10-29. The rules that follow from them are in the `kiler-crypto` skill.

| Question | Decision |
|---|---|
| The format of an encrypted value (step 2) | Decided by the user: base64 (the standard alphabet, with padding) of one version byte, the 12-byte nonce, the ciphertext and the 16-byte tag. Version 1 is AES-256-GCM. A value of version 1 is at least 29 bytes. |
| The associated data | The version byte, then what the value is for (its purpose) and its context, each part as UTF-8 with its length before it (4 bytes, big-endian). So a value cannot be moved to another place or read as something else. The purposes: `group` (a group of fields of a shared record: the record id and the level, decided by the user before M3, PLAN section 6), `check` (the check value of a level: the level), `level-key` (a level key locked with a password or the recovery key: the level). The private records add theirs after the exam (the owner and the record id, design 7.10). |
| The salt | 16 random bytes, new at every lock, also when the same keys are locked again with a new password. |
| The recovery key (step 7) | Decided by the user: 20 random bytes (160 bits) as 32 characters of Crockford Base32 (`0123456789ABCDEFGHJKMNPQRSTVWXYZ`), shown in 8 groups of 4 joined by `-`. A typed key is read without regard to case, hyphens and spaces, with O read as 0 and I and L as 1; any other character, or another length, is refused. The 32 characters in upper case are the secret, which locks the level keys through PBKDF2 with a salt as a password does. The personal recovery code of design 7.10 takes the same format after the exam. |
| What Kiler.Crypto knows | Bytes and base64 strings: no files, no JSON, no models. Kiler.Core (M4, M5) gives it the UTF-8 of a group of fields and keeps what it returns. |
| Deferred with their steps (PLAN section 10) | The key of the admin seal and what the seal signs (step 6). |
| Where the signing key of the updates is kept (step 11) | Decided by the user on 2026-11-11: a file locked with a password, on the maintainer's machine, with a copy of the file and its password in the company password manager. Never in the repo, the share, the exe, a test or CI. The release tool asks for the password. Chosen over a key of the Windows store that cannot be exported and over a file under DPAPI, as only a file can have a backup: without the key no new version is taken by the local copies, and every user would put the next one in place by hand. The file is locked with the primitives of M3.1 (PBKDF2 and AES-GCM), not as the encrypted PKCS#8 PEM of .NET, whose PBES2 is AES-CBC without a MAC, which `kiler-crypto` forbids; its format is decided in M3.4. |
| What an update signature covers (step 11) | Decided by the user on 2026-11-11, an addition to design 4.1: the version and the SHA-256 of `Kiler.exe` together, not the exe alone, and a local copy takes only a version higher than its own. A signature of the exe alone leaves the version in `version.json` unsigned: anyone who can write the share could put an older signed exe there under a higher number, which takes everyone back to it, and it then restarts in a loop, as it too sees a "newer" version. |
| The formats of the signature and of the key file (step 11) | Decided by the user in M3.4, on 2026-11-11, each as suggested: the labels `update` and `signing-key`; the public key as the base64 of its SubjectPublicKeyInfo, and the signature as the base64 of 64 bytes IEEE P1363; the key file as one line that Kiler.Crypto makes and reads, so it fits one field of a password manager; a signing password of at least 16 characters. The details are in the `kiler-crypto` skill, "Formats". |
| When a local copy looks for a new version (step 11) | Decided by the user in M3.6, on 2026-11-12: in the background, once the page of the start is open, never on the way of the start, so a shared folder that does not answer holds up neither the start nor the stop. A checked new version goes into place right after the check, without a restart: the running Kiler goes on with its version, and the new one runs from the next start. Design 4.1 said that the copy restarts; it is corrected. Chosen over a check at the start with a time limit, which makes every start wait for the share up to the limit and the start of a new version wait for the copy of 22 MB, and over a swap at the next start, which keeps the `.new` and its signed `version.json` between two runs and checks them again. |
| How `version.json` carries a change of key (step 11) | Decided by the user in M3.6, on 2026-11-12: `signatures`, a list of one or two signatures, in place of `signature`; a copy takes the release when one of them verifies with the key built into it. During a change of key, `sign` signs each release with the old key and the new one until the old one is retired, so the copies with the old key take the release that brings the new one, a first start of it (M3.8) takes it with the new key, and a copy that missed it still takes the later ones. No copy read `version.json` before M3.6, so the format changed without a migration. `sign` with a second key file is M3.8a. |
| When the old signing key is retired (step 11) | Decided by the user in M3.8a, on 2026-11-12, each as suggested. Each release is signed with the old key and the new one until each user's Kiler shows in its foot line the version of the first release with the new key, or a higher one; the maintainer asks the team. Then the old key signs no more and is destroyed: every copy of its file and of its entry in the password manager is deleted for good, as a copy that still has only it would take whatever it signs. Chosen over a fixed time, and over keeping the old key for a late copy, which is installed by hand as for a lost key. A key that has leaked never signs again, not even next to a new one. The steps are in `docs/release.md`, "Change the key". |
| The leftovers of the updates (step 11) | Decided by the user in M3.7a, on 2026-11-12, each as suggested. The local copy deletes them at each start in the background, first in the task of the check, so the swap finds no `.old` of an earlier version and the start waits for nothing; chosen over a clean before the server, which a held file would hold up. A start from the shared folder without a copy first moves back a `.old` that a swap cut off between its two renames left alone, and starts that copy, which takes only a version higher than its own; chosen over leaving it to a new first copy, which takes whatever the shared folder holds, an older signed version too. A `.tmp` of a first copy goes once the later of its two times is an hour old, and only when no one holds it. |
| The check of the first copy (step 11) | Decided by the user on 2026-11-11: yes. The exe started from the share checks the copy it made against the signed `version.json` before it starts it, and sets `NoRemoteImages` (the M1.8 note in [log/M1.md](log/M1.md), and the checkpoint in [M1.md](M1.md#checkpoint-in-the-real-environment)), so that no DLL loads from a network path after that. Whether `NoRemoteImages` holds there is checked in the real environment in the trial use. |
| The first copy without `version.json`, and when `NoRemoteImages` is set (step 11) | Decided by the user in M3.8, on 2026-11-12, each as suggested. A shared folder without `version.json` is refused, as whoever can delete it would otherwise skip the check; chosen over a copy with a warning. The policy is set at every start, as the first statement of `Program`, in every mode, so every run of the published exe in the smoke and E2E tests has it; a failure is a line, and from a network folder exit code 1. Chosen over the policy only from a network folder, which no automated test would run. A refusal of the check writes nothing else: no `share.json`, no shortcut, no start; the shortcut and the start of the copy stay as they were. They loaded DLLs of the shared folder too (the checkpoint after M1), which the policy now refuses; a DLL loaded after it came from System32 in the measurement of M3.8, and the trial use checks the shortcut and the browser. |
| The static imports that load before the policy (step 11) | Decided by the user in M3.8, on 2026-11-12, after its measurement: a task of its own, M3.8b, rather than a residual risk. Windows took `NTASN1.dll` and `SspiCli.dll` from the folder of the exe before `Main`, where `NoRemoteImages` cannot reach them, so a copy of either planted next to the exe in the shared folder ran in every start from there, past the check of the first copy and the check of the hash by hand. M3.8 put it down to the imports of `ncrypt.dll` and `CRYPT32.dll`; M3.8b found the real chain: `SspiCli.dll` is where `Secur32!GetUserNameExW`, which the exe imports, forwards, and `NTASN1.dll` is a delay load of `ncrypt.dll`; neither is a static import of the two. |
| How the exe loads `ncrypt.dll`, `CRYPT32.dll` and `Secur32.dll` (step 11) | Decided by the user in M3.8b, on 2026-11-12, in two steps. (1) As suggested: the linker delay-loads the three (`/DELAYLOAD` and `delayimp.lib` in Kiler.App.csproj), so nothing loads them before `Main`; chosen over taking their lines out of the `WindowsAPIs.txt` of the ILCompiler package, which makes them lazy P/Invokes of the runtime, whose search for a framework P/Invoke tries the folder of the exe by its full path first. (2) After the measurement: right after the policy, `RemoteImages` loads `SspiCli.dll`, `NTASN1.dll` and the three from System32 (`LOAD_LIBRARY_SEARCH_SYSTEM32`), so the `LoadLibraryEx(name, NULL, 0)` of `delayimp.lib`, the forwarder and the delay load of `ncrypt.dll` find them loaded and search nothing (the DLL search order of the Windows docs). `PreferSystem32Images` with the policy, chosen first, was dropped: set after the start it changed none of these loads, and a planted copy that `NoRemoteImages` refuses ends the search, so a planted `Secur32.dll`, `SspiCli.dll` or `NTASN1.dll` made a start from the shared folder end with the exception of a failed delay load (0xC06D007E, 0xC06D007F), and a first copy leave its `.tmp`. |
| The accepted limits | Accepted by the user after the security review of M3.2, as deliberate edits that design 7.8 detects but does not prevent. (1) A group does not carry the version of its record, so someone who can write the share can put back an older group of the same record and level from `history\`, or mix groups of different versions; they read nothing and can only bring back a value that was there before. Binding the version would make every save encrypt the groups of every level again, which an editor of a lower level cannot, as the groups are independent (design 5.2). The edit is marked by the file owner and the dates (design 7.8), and an admin restores it. (2) A check needs only a key, so whoever can write `levels.json` can put in a check of a key of their own: with a user file of their own their Kiler shows them that level but decrypts nothing of the real key, and a replaced check refuses the sign-in to that level for everyone until an admin restores `levels.json`. Kiler never writes a new check or new level keys after a failed check (M4, "For later modules"), and the admin seal is to cover `levels.json` too (PLAN section 10). |
