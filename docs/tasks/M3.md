## Decisions for the module

Decided at the start of M3, on 2026-10-29. The rules that follow from them are in the `kiler-crypto` skill.

| Question | Decision |
|---|---|
| The format of an encrypted value (step 2) | Decided by the user: base64 (the standard alphabet, with padding) of one version byte, the 12-byte nonce, the ciphertext and the 16-byte tag. Version 1 is AES-256-GCM. A value of version 1 is at least 29 bytes. |
| The associated data | The version byte, then what the value is for (its purpose) and its context, each part as UTF-8 with its length before it (4 bytes, big-endian). So a value cannot be moved to another place or read as something else. The purposes: `group` (a group of fields of a shared record: the record id and the level, decided by the user before M3, PLAN section 6), `check` (the check value of a level: the level), `level-key` (a level key locked with a password or the recovery key: the level). The private records add theirs after the exam (the owner and the record id, design 7.10). |
| The salt | 16 random bytes, new at every lock, also when the same keys are locked again with a new password. |
| The recovery key (step 7) | Decided by the user: 20 random bytes (160 bits) as 32 characters of Crockford Base32 (`0123456789ABCDEFGHJKMNPQRSTVWXYZ`), shown in 8 groups of 4 joined by `-`. A typed key is read without regard to case, hyphens and spaces, with O read as 0 and I and L as 1; any other character, or another length, is refused. The 32 characters in upper case are the secret, which locks the level keys through PBKDF2 with a salt as a password does. The personal recovery code of design 7.10 takes the same format after the exam. |
| What Kiler.Crypto knows | Bytes and base64 strings: no files, no JSON, no models. Kiler.Core (M4, M5) gives it the UTF-8 of a group of fields and keeps what it returns. |
| Deferred with their steps (PLAN section 10) | The key of the admin seal and what the seal signs (step 6), the signing key of the updates and the check of the first copy (step 11). |

  - What: PLAN M3 steps 4 and 7, without restoring admin access (PLAN section 10). Locking a set of level keys with a secret: a new salt, a key from PBKDF2, each level key encrypted with purpose `level-key` and its level as context (the user file of design 7.3: `salt` and `keys`); unlocking them; locking them again with a new password keeps the same level keys, with a new salt. The recovery key: a new one, its format, reading a typed key (the decisions above), and locking and unlocking the level keys with it.
  - Tests (first): a wrong password unlocks no key; a locked key moved to another level does not unlock; a new password keeps the same level keys; recovery with the recovery key, typed in lower case, with spaces and with O, I and L; a new recovery key has 8 groups of 4 characters of the alphabet, and two differ; a typed key with another character or another length is refused.
  - Done: the tests pass; Kiler.Crypto has full tests and no dependency on the other projects (PLAN M3, "Done").

The level key as the plaintext of a lock is read through `SecretKey.Use`.
    - (M3.1) `PasswordKey.Derive` throws `ArgumentException` for a salt that is not 16 bytes and a secret over `PasswordKey.MaxLength` (1024 characters). A salt comes from the user file on the share, so the unlock checks its length first and fails as a wrong password does.

## For later modules

Notes of the done tasks for the modules after M3. "Start of a module" collects the ones that name the module ([README.md](README.md)).

- (start of M3) M4: the wizard makes the recovery key, shows it once, and locks all the level keys with it (M3.3). Where the locked set is kept on the share (`levels.json`, `settings.json` or a file of its own) is decided in M4; restoring admin access with it comes after the exam (PLAN section 10).
- (M3.1) M4: a password has at most 1024 characters (`PasswordKey.MaxLength`), so the password screens and the API limit it there. The automatic locking may dispose a level key while a request uses it: the use under way ends with the key, and a use after it throws `ObjectDisposedException` (`SecretKey.Use`), which M4 treats as locked, not as an error.
- (M3.2) M4: the wizard makes each level key with `SecretKey.New()` and its check for `levels.json` with `LevelCheck.Create(key, level)`. The sign-in keeps an unlocked key only when `LevelCheck.Verify(key, check, level)` is true (design 7.5). `levels.json` is on the share, so a missing check, or one that is not a string, counts as not verified and is never passed to `Verify` as null, which throws `ArgumentNullException`. A failed check never makes Kiler write a new check or new level keys: whoever can write `levels.json` could put in a check of a key of their own, and the data of the real key would be lost (security review).
- (M3.2) M5: a group is `FieldGroup.Encrypt(key, fields, recordId, level)`, with the UTF-8 of the fields of that level, and is read with `FieldGroup.Decrypt`, whose bytes are zeroed once they are parsed. The record id is one that passed `StorageName.Check`, as an empty id or one with a lone surrogate is an `ArgumentException`, and a group that is missing or not a string is not passed as null. A `CryptographicException` is caught per group, so one damaged or moved group does not fail the record or the list (security review).
