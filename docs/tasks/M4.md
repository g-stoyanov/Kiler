# M4. Users and permissions

The steps are in [PLAN.md, M4](../PLAN.md#m4-users-and-permissions). How to work on the tasks is described in [README.md](README.md). The done tasks, with all their notes, are in [log/M4.md](log/M4.md).

Until the exam, steps 6, 8, 10, 11 and 12 are deferred, with what serves them in steps 3, 5, 7 and 13: unlocking the personal key at sign-in, the locking per level, the seal of the user files, and the screens of the personal key ([PLAN.md, section 10](../PLAN.md#10-deferred-until-after-the-exam)). The tasks follow the [light cycle](README.md#light-cycle-until-the-exam): `security-reviewer` makes its one pass of M4.3 to M4.6 (the keys, the sign-in, the session and the admin actions).

## Decisions for the module

Decided at the start of M4, on 2026-10-29. The rules that follow from them are in the `kiler-dotnet` skill ([core.md](../../.claude/skills/kiler-dotnet/core.md)), `kiler-crypto` and `kiler-ui`.

| Question | Decision |
|---|---|
| The scope until the exam (decided by the user) | Besides the deferred steps above: the levels screen only renames a level, as a new level needs the recovery key for the recovery set and new temporary passwords for its users (design 13), so adding one comes after the exam (PLAN section 10). Deleting a user is not in step 7 and is not done. The E2E test of the module moves to M6, with the screenshots (M8 step 5). The demo data with the levels and the users is the last task. |
| The account | The Windows user name without the domain, in lowercase: the id of `users\<account>.json`, and after the exam the name of `private\<account>\`. A name that does not pass `StorageName.Check` cannot sign in, and the screen says so. The current account is an interface of Kiler.Core, implemented in Kiler.App. |
| `--account <name>` (decided by the user) | A start option in every build, for the demo, the screenshots and the tests (the E2E of M6 signs in as a second user): it only picks the user file, and the password is still asked. It gives nothing new, as anyone can copy a user file under their own name in `users\`. A deviation from design 7.5 ("the exe recognizes the account"); the design is updated. |
| `levels.json` | `{ "id": "levels", "version": N, "levels": [...], "recovery": {...} }`, not the bare array of design 7.1, as every document has `id` and `version` (M2). Each level has `level`, `name` and, from level 1, `check`. Levels 0 to N, N from 1 to 9, without gaps; a name of 1 to 40 characters, unique without regard to case. `remember` and the `autoLockMinutes` of a level come after the exam. |
| The recovery set | The level keys locked with the recovery key (M3.3) are `recovery` in `levels.json`, with `salt` and `keys` as in a user file: they change with the levels, and the admin seal is to cover `levels.json` (PLAN section 10). Restoring admin access with it comes after the exam. |
| `settings.json` | `{ "id": "settings", "version": N, "guestMode": false, "autoLockMinutes": 30 }`, set by the wizard. The screen of the general settings comes after the exam (PLAN section 10). |
| A user file | `users\<account>.json` with `displayName`, `level`, `canEdit`, `isAdmin`, `mustChangePassword`, `salt` and `keys`. The `user` of design 7.3 is the `id`; `stamp` comes with the seal after the exam. |
| Passwords (decided by the user) | At least 8 characters, at most 1024 (`PasswordKey.MaxLength`). Kiler makes the temporary password; the admin does not type it (a deviation from design 7.6, decided by the user; the design is updated): 16 random characters of the lowercase Crockford Base32 alphabet (`0123456789abcdefghjkmnpqrstvwxyz`), used as shown. It is shown to the admin once, with a copy button, and the admin hands it over in person or by chat: Kiler sends nothing. The user file gets `mustChangePassword: true`, so the sign-in knows that the password is temporary and asks for a new one before anything else. |
| The session | One per process: a Kiler runs for one Windows account, so all its pages share it. The levels that a session reads and writes are the keys that unlocked and passed `LevelCheck.Verify`, never the `level` of the file. `canEdit` and `isAdmin` come from the file: a user who writes them into their own file gets the screens, not the keys (design 7.8), until the seal after the exam. So a user of the top level who writes `isAdmin` gets the admin actions, which give at most the keys they hold, no worse than telling their password (design 7.8; accepted until the seal). An admin has the top level: making someone an admin raises their level with a new temporary password. A guest (only with `guestMode`) reads level 0 and writes nothing. |
| The wizard | It runs only when the data folder is chosen and is not there, or holds nothing but the empty folders of the layout (`DataFolder.Create`). A missing `levels.json` beside other files is damage that an admin restores, never a new Kiler: a failed check never makes new keys (`kiler-crypto`, "Rules"). `levels.json` is written first, as a create, so the second of two wizards at once meets it and stops. The first admin is the current account. The recovery key is shown once, with a copy button and an "I have saved it" checkbox. |
| A change of password | The forced change after a temporary password uses the keys of the sign-in just made. A voluntary change asks for the current password. Either refuses when a level of the file did not unlock or verify (the M3.3 note under M4.5). |
| The automatic locking | Only the overall one: after `autoLockMinutes` of `settings.json` without activity, which is any request of a page other than `/api/events` and `/api/health`. A lock disposes the keys and drops the decrypted data, and the event stream sends `session` (no data), so every page drops what it shows and shows the lock screen. A "Lock" button locks at once. |
| The state of the data | `KilerData` is always in DI and gives its state with the reason (no data folder chosen, not there, another Kiler has the copy, the index cannot be read, opening, open, offline), which the screens show (the M2.10 lines under M4.2). A start whose file server does not answer keeps the 37 s before the copy opens (the M2.11b line under M4.2), and the screen says meanwhile that the data folder is opening. Opening the copy first is a change of the API of Kiler.Storage, after the exam. |
| Offline | The sign-in works from the local copy. The writes (the wizard, a change of password, the admin actions) say that the shared folder cannot be reached (`WriteOutcome.Offline`, core.md). |
| The UI (the questions of M6, decided by the user, as the screens of M4 come first) | No component library: own CSS on the variables of M1.7. React Router for the addresses, with no dot in their last segment (M1.8). The data through `api.ts` and React state, with no data library. The versions come from `docs-researcher` in M4.7. |

## Tasks

- [ ] **M4.1 Models and the account**
  - What (PLAN M4 step 1):
    - the models of `levels.json`, `settings.json` and `users\<account>.json` in Kiler.Core, as the decisions say. Each is read from a `Document` and written to its content with a case-sensitive, source-generated JSON context, and checked: a document that does not fit (a missing name, a level out of order or twice, a name of `keys` that is not the digits of a level, values out of their limits) is invalid, with a reason, not an exception;
    - the current account behind an interface of Kiler.Core: the Windows user name without the domain, in lowercase, checked with `StorageName.Check`. Its implementation is in Kiler.App, with `--account <name>` in `StartOptions` and `--help`, and the tests use a fake.
  - Tests: each model reads what it writes; each invalid case above, and a name in another case; the account without the domain and in lowercase, a name that fails the check refused; `--account` parsed, and refused without a name or with a bad one.
  - Done: the tests of Kiler.Core and Kiler.App pass.
  - From earlier tasks:
    - (M3.3) the property names of `keys` are the digits of the levels (`"1"`, `"2"`); a name that is not the digits of a level is left out, and M4.4 gives the rest to `LockedKeys`.
- [ ] **M4.2 The state of the data and the team in memory**
  - What:
    - `KilerData` always in DI, with a state and its reason (the decisions) instead of only lines on the console, and an endpoint that gives the state to the page;
    - a service of Kiler.Core that keeps the levels, the settings and the users of the local copy. It is made when the copy opens, follows each load that changes them (`DataWatch.Loaded`), and reads the documents again after `Failed` and `OfflineChanged` (core.md, "Calling the layer").
  - Tests: each state of `KilerData`; the team follows a load (a user file new, changed, damaged, gone); the state through the API.
  - Done: the tests of Kiler.Core and Kiler.App pass.
  - From earlier tasks:
    - (M2.10) the upper layers reach the local copy through `KilerData.Copy`, null until the copy is open and while Kiler runs without data. `KilerData` opens `DataCopy.Open` without an account, and stays so until the private records (PLAN section 10). Its handlers of `Failed` and `OfflineChanged` only write a line on the console; the read of the documents after them comes with this task. The rules of the data in the host are in `kiler-dotnet`, `host.md`, "Data".
    - (M2.10) Kiler runs without data when no data folder can be chosen (never started from the shared folder, no `--data`), when the data folder is not there or is a link, when another Kiler of the user has its local copy open, and when the index of the copy cannot be read now; only the console says so today. The wizard (M4.3) starts from the state "not there".
    - (M2.11b) at a start whose file server does not answer, `KilerData.Copy` stays null for about 37 s, as `DataFolder.Open` looks at the data folder before the local copy opens (measured with an address that no one answers; a name that does not resolve fails in 0.2 s). The first load then says offline at once. The state meanwhile is "opening" (decided at the start of M4). Whether the network off behaves so is a check of the trial use ([real-environment-checks.md](../real-environment-checks.md#the-trial-use-phase-4)).
- [ ] **M4.3 The wizard**
  - What (step 2): an endpoint that makes a new Kiler, only in the states that the decisions allow:
    - the data folder (`DataFolder.Create`);
    - the level keys with their checks, the recovery key and the recovery set;
    - the user file of the first admin, locked with their password;
    - the writes go through the local copy, `levels.json` first, then `settings.json` and the user file, and `KilerData` then opens the copy of the new folder.

    The answer gives the recovery key once; the admin then signs in (M4.4).
  - Tests:
    - a wizard in a folder that is not there makes the documents; the admin's keys unlock with the password and verify against each check; the recovery set unlocks with the recovery key to the same keys;
    - refused: documents in the folder, `levels.json` there, no data folder chosen, offline; a password of 7 or 1025 characters; a bad level name, a gap, two equal names, too many levels;
    - of two wizards at once, one makes Kiler and the other is refused;
    - the recovery key is in no file and no line of the console.
  - Done: the tests of Kiler.Core and Kiler.App pass.
  - From earlier tasks:
    - (M2.1) `DataFolder.Create` takes an existing folder only when it holds nothing but empty folders of the layout; opening one creates nothing.
    - (start of M3, M3.2) each level key is `SecretKey.New()`, with its check `LevelCheck.Create(key, level)`; the recovery key is `RecoveryKey.New()`, shown with `ToDisplayString()`, and locks all the level keys with `LevelKeys.Lock(keys, recoveryKey)`. Its lifetime is one request (`kiler-crypto`, "Rules").
- [ ] **M4.4 Sign-in, guest and the permissions**
  - What (steps 3, 4 and 9, and the session of step 5):
    - the session of the decisions. The sign-in finds the user file of the current account, unlocks its keys with the password and keeps only those that verify; with none it answers "No access. Contact an admin." `mustChangePassword` gives a session that can only change the password (M4.5);
    - guest mode as `settings.json` says;
    - signing out and the "Lock" button dispose the keys;
    - every endpoint states what it needs: nothing (the state and the sign-in), a guest or a session, a session that can edit, or an admin with every level. The session endpoint gives the page what it shows: the account, the display name, the levels held, `canEdit`, `isAdmin`, `mustChangePassword` and guest mode.
  - Tests:
    - a correct and a wrong password;
    - a self-added user (no keys, or keys of another key) does not get in;
    - a user who raised their own `level` or `isAdmin` reads only the levels of their keys, and the admin endpoints refuse them without the key of the top level;
    - a missing or damaged check counts as not verified;
    - without guest mode only the state and the sign-in answer; with it, level 0 only;
    - after a lock, a key in use answers as locked;
    - each kind of endpoint refuses whom it must.
  - Done: the tests of Kiler.Core and Kiler.App pass.
  - From earlier tasks:
    - (M3.3) the sign-in reads the `salt` and `keys` of the user file into `new LockedKeys(salt, keys)` and calls `LevelKeys.Unlock(locked, password)`. It gives only the keys that unlock, which the caller disposes: none for a wrong password or a salt that is not 16 bytes of base64, and not the entries that are damaged, moved to another level or of a level below 1. A user file with no `salt` or `keys`, or with no keys, unlocks nothing and so signs in no one (design 7.5).
    - (M3.2) the sign-in keeps an unlocked key only when `LevelCheck.Verify(key, check, level)` is true, and disposes the rest. `levels.json` is on the share, so a missing check, or one that is not a string, counts as not verified and is never passed to `Verify` as null, which throws `ArgumentNullException`.
    - (M3.1) a lock may dispose a level key while a request uses it: the use under way ends with the key, and a use after it throws `ObjectDisposedException` (`SecretKey.Use`), which is a locked level, not an error (core.md).
- [ ] **M4.5 Change of password and the automatic locking**
  - What (steps 3 and 5):
    - the change of password of the decisions. It locks the keys of the session again with `LevelKeys.Lock`, writes the user file through the copy (a conflict and offline are shown, not repeated) and clears `mustChangePassword`;
    - the overall automatic locking on `TimeProvider`, with the `session` event on the stream (host.md, "Heartbeat").
  - Tests:
    - the forced change after a temporary password;
    - a voluntary change with a wrong current password is refused;
    - the keys after a change are the same: a group made before reads after it;
    - a level of the file that did not unlock or verify refuses the change;
    - 7 and 1025 characters are refused;
    - the lock after the minutes without activity: a request puts it off, the stream and the health check do not;
    - the stream gives `session` at a lock, and a request after it is locked.
  - Done: the tests of Kiler.Core and Kiler.App pass.
  - From earlier tasks:
    - (M3.3) a change of password locks again with `LevelKeys.Lock` the keys that unlocked and verified, so a level whose entry did not unlock would drop out of the user file for good: the change refuses then (decided at the start of M4), and the admin list marks such a file (M4.6). A new password does not revoke the old one: the copies of the user file in `history\` and in the local copies keep the keys locked with the old password, so after a leak only a new level key cuts the access (design 7.9, after the exam).
- [ ] **M4.6 Admin actions**
  - What (step 7 without the seal):
    - the list of users, with a mark for a file whose keys do not match its `level` (a level without its key, or a key above it), and the warning while there is only one admin (design 7.7);
    - a new user (account, display name, level, editor) with a temporary password;
    - a change of level, with a new temporary password;
    - a new temporary password;
    - the editor and admin rights (an admin has the top level, the decisions);
    - renaming a level.

    Each action that gives keys locks the admin's keys up to the user's level with the temporary password that Kiler makes, and writes through the copy.
  - Tests:
    - the admin creates a user, who signs in with the temporary password and must change it (through the API: the flow of the E2E test of M6, with `--account` there);
    - a change of level gives the keys up to the new level only;
    - an existing account and a bad account name are refused;
    - a user, an editor, a guest and a locked admin are refused;
    - the mark and the warning;
    - a rename keeps the checks;
    - the temporary password is in the answer once, and in no file and no line.
  - Done: the tests of Kiler.Core and Kiler.App pass.
- [ ] **M4.7 The base of the screens and the wizard**
  - What (step 13, with the UI decisions of the module):
    - React Router and the layout: the account, "Lock", and "Sign in" for a guest;
    - the session in the page, from its endpoint and from the `session` event. The event goes through the SharedWorker as another `HubMessage` type, and the page drops its data on it;
    - the screen of the state of the data: its reason, opening, offline;
    - the wizard: the levels, the admin's display name and password (twice), guest mode and the minutes of the lock. Then the recovery key once, with a copy button and the "I have saved it" checkbox, then the sign-in.
  - Tests (Vitest): the session and the event; the checks of the wizard's form; the recovery key leaves the state once it is confirmed.
  - Done: `check-ui.ps1` passes; the wizard works in `npm run dev` against a `dev-data` that is not there, and in the published exe without a CSP violation.
- [ ] **M4.8 Sign-in, password and lock screens**
  - What (step 13): the sign-in (the password, "No access", an account that cannot sign in, offline), the forced and the voluntary change of password, the lock screen (unlocking is a sign-in), and guest mode with "Sign in".
  - Tests (Vitest): the forms and their messages; a password leaves the state after its request.
  - Done: `check-ui.ps1` passes; each screen works in `npm run dev`.
- [ ] **M4.9 Admin screens: users and levels**
  - What (step 13): the list of users with the marks and the warning; a new user, a change of level, a new temporary password, the editor and admin rights; the temporary password shown once with a copy button; renaming a level.
  - Tests (Vitest): the forms; the temporary password leaves the state when its screen closes.
  - Done: `check-ui.ps1` passes; in `npm run dev`: the wizard, the sign-in, the admin creates a user, and that user (a second start with `--account`) signs in with the temporary password and changes it.
- [ ] **M4.10 Demo data: levels and users, and the end of M4**
  - What (PLAN M8 step 4, its first part): `tools/Kiler.DemoData` in `Kiler.slnx`. It makes a data folder through the Kiler libraries, with made-up levels (Guest, Team, Test, Prod), settings, an admin and two users with demo passwords, and it can make `dev-data` for `npm run dev`. Then the end of the module ([README.md](README.md#end-of-a-module)).
  - Tests: the folder it makes opens, and each demo user signs in with their demo password.
  - Done: the full check passes; `npm run dev` starts on the demo data and the demo users sign in with `--account`.
  - From earlier tasks:
    - (M2.10) the dev mode gives `--data dev-data`, which nothing makes yet, so it runs without data and says so on its console until the demo data or the wizard makes it a data folder.
