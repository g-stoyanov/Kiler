# M4. Users and permissions

The steps are in [PLAN.md, M4](../PLAN.md#m4-users-and-permissions). How to work on the tasks is described in [README.md](README.md). The done tasks, with all their notes, are in [log/M4.md](log/M4.md).

Until the exam, steps 6, 8, 10, 11 and 12 are deferred, with what serves them in steps 3, 5, 7 and 13: unlocking the personal key at sign-in, the locking per level, the seal of the user files, and the screens of the personal key ([PLAN.md, section 10](../PLAN.md#10-deferred-until-after-the-exam)). The tasks follow the [light cycle](README.md#light-cycle-until-the-exam): `security-reviewer` makes its one pass of M4.3 to M4.6 (the keys, the sign-in, the session and the admin actions).

After the exam the module comes back, one item of PLAN section 10 at a time ([README.md](README.md#start-of-a-module), "A module that comes back"), with the full cycle: step 8 and the seal of step 7, item 3, are M4.11 to M4.20, after M3.9 in [M3.md](M3.md). The other deferred steps stay until their items.

## Decisions for the module

Decided at the start of M4, on 2026-10-29. The rules that follow from them are in the `kiler-dotnet` skill ([core.md](../../.claude/skills/kiler-dotnet/core.md)), `kiler-crypto` and `kiler-ui`.

| Question | Decision |
|---|---|
| The scope until the exam (decided by the user) | Besides the deferred steps above: the levels screen only renames a level, as a new level needs the recovery key for the recovery set and new temporary passwords for its users (design 13), so adding one comes after the exam (PLAN section 10). Deleting a user is not in step 7 and is not done. The E2E test of the module moves to M6, with the screenshots (M8 step 5). The demo data with the levels and the users is the last task. |
| The account | The Windows user name without the domain, in lowercase: the id of `users\<account>.json`, and after the exam the name of `private\<account>\`. A name that does not pass `StorageName.Check` cannot sign in, and the screen says so. The current account is an interface of Kiler.Core, implemented in Kiler.App. |
| `--account <name>` (decided by the user) | A start option in every build, for the demo, the screenshots and the tests (the E2E of M6 signs in as a second user): it only picks the user file, and the password is still asked. It gives nothing new, as anyone can copy a user file under their own name in `users\`. A deviation from design 7.5 ("the exe recognizes the account"); the design is updated. |
| `levels.json` | `{ "id": "levels", "version": N, "levels": [...], "recovery": {...} }`, not the bare array of design 7.1, as every document has `id` and `version` (M2). Each level has `level`, `name` and, from level 1, `check`. Levels 0 to N, N from 1 to 9, without gaps; a name of 1 to 40 characters, not blank, unique without regard to case. `remember` and the `autoLockMinutes` of a level come after the exam. |
| The recovery set | The level keys locked with the recovery key (M3.3) are `recovery` in `levels.json`, with `salt` and `keys` as in a user file: they change with the levels, and the admin seal is to cover `levels.json` (PLAN section 10). Restoring admin access with it comes after the exam. |
| `settings.json` | `{ "id": "settings", "version": N, "guestMode": false, "autoLockMinutes": 30 }`, set by the wizard; `autoLockMinutes` from 1 to 1440 (decided by the user in M4.1). The screen of the general settings comes after the exam (PLAN section 10). |
| A user file | `users\<account>.json` with `displayName`, `level`, `canEdit`, `isAdmin`, `mustChangePassword`, `salt` and `keys`. The `user` of design 7.3 is the `id`; `stamp` comes with the seal after the exam. `displayName` of 1 to 100 characters, not blank; `level` from 0 to 9. The names of `keys`, here and in `recovery`, are the digits of the levels, `"1"` to the top level, and any other name makes the document invalid (decided by the user in M4.1). |
| Passwords (decided by the user) | At least 8 characters, at most 1024 (`PasswordKey.MaxLength`). Kiler makes the temporary password; the admin does not type it (a deviation from design 7.6, decided by the user; the design is updated): 16 random characters of the lowercase Crockford Base32 alphabet (`0123456789abcdefghjkmnpqrstvwxyz`), used as shown. It is shown to the admin once, with a copy button, and the admin hands it over in person or by chat: Kiler sends nothing. The user file gets `mustChangePassword: true`, so the sign-in knows that the password is temporary and asks for a new one before anything else. |
| The session | One per process: a Kiler runs for one Windows account, so all its pages share it. The levels that a session reads and writes are the keys that unlocked and passed `LevelCheck.Verify`, never the `level` of the file. `canEdit` and `isAdmin` come from the file: a user who writes them into their own file gets the screens, not the keys (design 7.8), until the seal after the exam. So a user of the top level who writes `isAdmin` gets the admin actions, which give at most the keys they hold, no worse than telling their password (design 7.8; accepted until the seal). An admin has the top level: making someone an admin raises their level with a new temporary password. A guest (only with `guestMode`) reads level 0 and writes nothing. |
| The wizard | It runs only when the data folder is chosen and is not there, or holds nothing but the empty folders of the layout (`DataFolder.Create`). A missing `levels.json` beside other files is damage that an admin restores, never a new Kiler: a failed check never makes new keys (`kiler-crypto`, "Rules"). `levels.json` is written first, as a create, so the second of two wizards at once meets it and stops. The first admin is the current account. The recovery key is shown once, with a copy button and an "I have saved it" checkbox. |
| A change of password | The forced change after a temporary password uses the keys of the sign-in just made. A voluntary change asks for the current password. Either refuses when a level of the file did not unlock or verify (M3.3, kiler-crypto, "Rules"), and when the user file is at another version than at the sign-in, as the admin may have changed its level or given a new temporary password meanwhile: the page asks for a new sign-in (decided by the user in M4.5). |
| The admin actions (decided by the user in M4.6) | No action changes the admin's own user file: another admin does, and the admin's own password is changed on the password screen. An admin's level is not lowered below the top level: the admin right goes first. A user has a level from 1 to the top level, as level 0 has no key, and the sign-in refuses a file without keys (M4.4). A new temporary password always has a level that the admin gives, for a forgotten password too, never the `level` of the user file, which its user can write (security review). |
| The automatic locking | Only the overall one: after `autoLockMinutes` of `settings.json` without activity, which is any request of a page other than `/api/events`, `/api/health` and `/api/data`, as a page may ask the state of the data again and again (`/api/data` decided by the user in M4.5). Without a `settings.json` that fits, 30 minutes (decided by the user in M4.5). A lock disposes the keys and drops the decrypted data, and the event stream sends `session` (no data), so every page drops what it shows and shows the lock screen. A "Lock" button locks at once. |
| The state of the data | `KilerData` is always in DI and gives its state with the reason (no data folder chosen, not there, another Kiler has the copy, the index cannot be read, opening, open, offline), which the screens show (the M2.10 lines under M4.2). A start whose file server does not answer keeps the 37 s before the copy opens (the M2.11b line under M4.2), and the screen says meanwhile that the data folder is opening. Opening the copy first is a change of the API of Kiler.Storage, after the exam. M4.2 added `unusable` and `failed`; the states are in host.md, "Data". |
| Offline | The sign-in works from the local copy. The writes (the wizard, a change of password, the admin actions) say that the shared folder cannot be reached (`WriteOutcome.Offline`, core.md). |
| The seal in the session (item 3) | Decided by the user on 2026-11-12, with the seal of M3 ([M3.md](M3.md), "The admin seal"). The sign-in unlocks the admin public key, and an admin's private key, with the level keys. `canEdit`, `isAdmin` and the level that the screens show come only from a user file whose seal verifies with that public key; a file whose seal fails signs in with its keys, as a reader, and the screen says why. The admin right is a private key that matches the public key, never `isAdmin` alone. This replaces, for a forged flag, "screens, not keys" of the decision "The session". |
| A seal that fails (item 3) | Decided by the user on 2026-11-12. For `levels.json`, `settings.json` and a template, Kiler takes the newest version that an admin sealed: the one on the share, else the newest that the local copy keeps; an admin sees it in Alerts and puts the sealed version back. Without one: no sign-in for `levels.json`, an admin's too, until someone copies a sealed version back from `history\levels\`; 30 minutes of the automatic lock for `settings.json`; and a template's records are read, but no new record or edit takes it. |
| No migration (item 3) | Decided by the user on 2026-11-12, a deviation from PLAN section 10, item 3, which sealed the files made before it once from an admin's Kiler. No team uses Kiler before item 3, as the trial use comes after it, so the wizard and the demo data make the admin key from the start. A `levels.json` without it is a changed file, as a forged one, and Kiler never makes a new admin key on its own, as it makes no new level key (kiler-crypto, "Rules"): otherwise whoever deletes it from `levels.json` would have the next admin seal every file as it is, a forged one too. `dev-data` is made again with the demo data tool. |
| The marks (step 8, item 3) | Decided by the user on 2026-11-12: only an admin session sees them. A user file not sealed, or whose owner is neither its user nor a sealed admin; `levels.json`, `settings.json` or a template not sealed (with the version that Kiler takes instead), or whose owner is not a sealed admin; a record or a stash whose owner is not its `updatedBy` and not a sealed admin, or whose owner has no sealed `canEdit`; a document that the local copy reports changed outside Kiler (edited in place, damaged, gone outside the trash, out of order: `DataCopy.ToRestore`); an owner that cannot be read or made an account ("owner unknown"); and an audit file whose owner is not its account. A file whose owner is a sealed admin is not marked for its author, as a write back of an admin (the M2.9a and M2.9c notes in [M2.md](M2.md)) has the admin as its owner and the author in `updatedBy`; it is still marked when it is not sealed or was changed outside Kiler. A file in a private folder whose owner is not that of the folder comes with item 4, with the private records. The extra signals of the M2.6 note (a number of links over 1) are not taken. |
| The Alerts screen (item 3) | Decided by the user on 2026-11-12: an admin screen `/alerts`, named so rather than "suspicious users", as it shows more than the users, with the link "Alerts (n)" beside "Users", "Levels", "Stashes" and "Audit": each marked file with its reasons and a link, and "Put back the sealed version" for `levels.json`, `settings.json` and a template. The users screen shows the marks of each user in its column "Marks", and the record page shows an admin the marks of the record. The audit screen marks the entries of a file whose owner is not its account, as Alerts would read up to 31 days of the audit at each opening. The restore of the other files is item 11. |
| The owner of a file (item 3) | Decided by the user on 2026-11-12: the SID of the owner becomes `DOMAIN\user` through Windows (`SecurityIdentifier.Translate`), and an account by `AccountName.From`, as at the sign-in; cached by SID, as a team has few owners. An owner that cannot be read (`null`), cannot be translated or is a well-known group (`S-1-5-32-…`) is "owner unknown", never equal to an account. Through an interface of Kiler.Core, implemented in Kiler.App. A start with `--account` has no marks by the owner, as the demo and the tests run every user under one Windows account; the marks by the seal stay. The SID of the developer's account translated in 5 ms on 2026-11-12; the trial use checks the owners of the files of the other users on the shared folder. Chosen over the SID in the user file, which only the user's own Kiler can write and an admin seals only at a later action. |
| The UI (the questions of M6, decided by the user, as the screens of M4 come first) | No component library: own CSS on the variables of M1.7. React Router for the addresses, with no dot in their last segment (M1.8). The data through `api.ts` and React state, with no data library. The versions come from `docs-researcher` in M4.7. |

### The admin seal and the marks (PLAN section 10, item 3)

Step 8 of PLAN M4, and the seal of step 7, with the decisions above from "The seal in the session" to "The owner of a file", after M3.9 ([M3.md](M3.md)), which makes the admin key. - [ ] **M4.11 The seal in the files**
  - What: `stamp` in the user file, `levels.json`, `settings.json` and the templates, and the locked admin key of M3.9 in the user file and in `recovery`; the text that a seal covers for each file (M3, "What the seal covers"): of a user file its account, display name, level, `canEdit` and `isAdmin`; of the others every member but `stamp`, also those that the model does not know, with the id and the version, so a member that a later Kiler adds does not break the seal for an older one. A file without `stamp` is still a valid model, not sealed, so the build and the demo work until M4.15. A model checks its seal with a public key and is sealed with the admin key. The JSON names are decided in the task.
  - Tests: the seal of each file verifies; a changed member of the text refuses, a changed `salt`, `keys` or `mustChangePassword` of a user file does not; a member that the model does not know is covered; a file without `stamp`, or with one that is not a seal, reads as not sealed.
  - Done: the tests of Kiler.Core pass.
  - From earlier tasks: (M3.9) the API of the admin key, with its formats in kiler-crypto, "Formats", "The admin seal": `AdminSeal.Verify(publicKey, purpose, text, seal)` and `AdminKey.Seal(purpose, text)` take the bytes of the text, with a `SealPurpose` of `UserFile`, `Levels`, `Settings` or `Template`. `LockedKeys` has `AdminPublicKey` and `AdminPrivateKey`, two encrypted values beside `Salt` and `Keys`, null in a set without them; their JSON names, in the user file and in `recovery`, are decided here. `recovery` holds both (decided by the user in M3.9), as the context of the private key is its public key.

- [ ] **M4.12 The wizard seals**
  - What: `NewKiler` makes the admin key, locks its public and private key for the first admin with the password, and its private key in `recovery` with the recovery key, and seals `levels.json`, `settings.json`, the templates and the admin's user file. The demo data takes them through `NewKiler`; `dev-data` is made again.
  - Tests: each file of a new Kiler is sealed; the admin's password unlocks the private key, and so does the recovery key; another Kiler's key does not verify them.
  - Done: the tests pass; a new `dev-data` signs in.
  - From earlier tasks: (M3.9) the admin's file is locked with `LevelKeys.Lock(keys, admin.PublicKey, admin, password)`, and `recovery` with `LevelKeys.Lock(keys, admin.PublicKey, admin, recoveryKey)`, so it holds the public key too.

- [ ] **M4.13 The admin key in the session**
  - What: the sign-in unlocks the public key, and an admin's private key, with the level keys (one PBKDF2), and the session keeps them and disposes them at the lock, as the level keys; a private key that does not match the public key is not kept. The change of password locks them again with the new password and refuses a user file whose public key did not unlock, as for a level (M3.3). No right changes yet.
  - Tests: an admin's session holds both keys, a user's only the public key; a lock disposes them; a change of password keeps them; a file whose public key does not unlock refuses the change.
  - Done: the tests of Kiler.Core and the API tests of the sign-in and the password pass.
  - From earlier tasks: (M3.9) `LevelKeys.UnlockAll(locked, password)` gives an `UnlockedKeys` with `Levels`, `AdminPublicKey` and `AdminKey` through one PBKDF2, and leaves out what does not unlock; `AdminKey` is given only with the public key it matches. Its level keys are not verified: the session keeps one only when `LevelCheck.Verify` of its level is true, as now. It is not disposable, so a `using` never disposes what the session took: the caller disposes the level keys and the `AdminKey` that it does not keep. The change of password locks again with `LevelKeys.Lock(levels, adminPublicKey, adminKey, newPassword)`. The `Lock(keys, password)` and `Unlock` of M3.3 lock and unlock without the admin key; once the sign-in, the change of password (here) and the actions (M4.14) take the new ones, they can go.

- [ ] **M4.14 The admin actions seal**
