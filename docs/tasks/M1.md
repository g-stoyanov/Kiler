# M1. Host and skeleton

The steps are in [PLAN.md, M1](../PLAN.md#m1-host-and-skeleton). How to work on the tasks is described in [README.md](README.md).

## Decisions for the module

| Question | Decision |
|---|---|
| How the exe is built | Native AOT, decided after the checks in M1.0b: 8 MB instead of 99 MB, and a faster start and update. No reflection, JSON with source generation, trim and AOT analyzers enabled. |
| Where the exe runs | Each user runs a local copy in `%LOCALAPPDATA%\Programs\Kiler`. Started from the shared folder, `Kiler.exe` copies itself there (M1.5a). Updates are signed and checked by the local copy (M3). Decided after M1.0b: everyone can write in the shared folder, so anyone could replace the exe there. |
| Heartbeat | SSE (`/api/events`). Closing the last connection starts a wait, after which the exe stops. Later the same channel carries the change notifications (M6). |
| The checks from section 14 | A probe exe before the real code (M1.0b). Later the `--diag` mode of `Kiler.exe` (M1.11) takes over its logic. The results are in the notes under M1.0b. |
| Commits outside Claude | Git hooks that call the same `data-guard` script (M1.0a). |
| CI | The workflow calls scripts from the repo, so CI can move to Bitbucket after the exam (PLAN section 9). |
| GitHub Release | Dropped (M1.10). |

- [x] **M1.0a Git hooks for commits outside Claude**
  - What:
    - `.githooks/pre-commit` checks the index (what the commit will contain) and the author;
    - `.githooks/commit-msg` checks the commit message, which `pre-commit` does not see;
    - `.githooks/pre-push` checks the commits that are being pushed;
    - all three call `.claude/hooks/data-guard.ps1` in a git mode, so the terms and the matching rules stay in one place; the script gets a mode that works without the Claude JSON input;
    - the hooks are enabled for this clone with `git config core.hooksPath .githooks`; this is a local setting, and CLAUDE.md says how to turn it on.
  - Tests: in a temporary git repo with the hooks enabled and made-up terms:
    - a clean commit passes;
    - a staged term blocks the commit;
    - a term in the message blocks the commit;
    - a local commit with a term blocks the push;
    - the existing 18 tests of the Claude hook still pass.
  - Done: the tests pass. By hand: a commit with a made-up term from a terminal is blocked.
  - Note: the script got the parameter `-Mode pre-commit|commit-msg|pre-push`. Without it, it is the Claude hook as before. Beyond the description:
    - in a linked worktree the hooks use the terms file of the main working tree, because the ignored file is not there;
    - pre-push also checks the pushed ref names and the messages of annotated tags;
    - commit-msg skips the diff that `commit -v` puts below the scissors line, so removing a term is not blocked.
  - Note: the reviews by `code-reviewer` and `security-reviewer`, used as real agents for the first time, found gaps in the diff scan that both modes share, so the Claude hook had them too since M1.0:
    - with `color.ui=always`, the added lines start with colour codes, and nothing was found;
    - file names without added lines (empty files, binary files, renames) were not checked;
    - git treats UTF-16 text as binary, and PowerShell 5.1 writes UTF-16 with `>`. Binary files are now scanned as text without NUL characters;
    - an external diff tool or a textconv filter could hide the content;
    - a failed git call printed all its arguments, which can include a push URL with a password.

    Declined:
    - trusting `git ls-remote` instead of the remote-tracking branches;
    - more hooks (`pre-merge-commit`, `applypatch-msg`). The docs now say that pre-push is the last gate for commits made by merge, cherry-pick or rebase.
  - Note: `.gitattributes` keeps LF in `.githooks/*`. Git for Windows 2.33 runs the hooks with CRLF too (checked), but other git builds may not.
  - Note: 39 tests: the 18 old ones and 21 git hook tests, with real commits and pushes in a temporary repository that has a space in its path. The tests for colour, empty files, renames and `commit -v` were checked to fail with the fixes taken out.
  - Note: `core.hooksPath` is set for this clone. A checkout without `.githooks`, such as a commit from before this task, runs no hooks.

- [x] **M1.0b Probe exe for the environment checks**
  - What:
    - `tools/Kiler.Probe`: a standalone console project, not in the solution, published like `Kiler.exe`: self-contained single-file for `win-x64`. Antivirus tools judge the kind of file, so the probe must be the same kind.
    - normal start: a minimal web server on `127.0.0.1` on a free port, and the default browser opens a "Probe OK" page;
    - `--diag <folder>`: in a temporary subfolder it writes 2000 small JSON files and measures the writing, the listing with names and dates, and reading all of them; it checks the owner of a new file; it deletes the subfolder; the report goes to the console and to a file next to the exe;
    - short instructions for the manual checks: Previous Versions, DFS and Security in the folder's Properties.
  - Tests: no unit tests, because the probe is thrown away in M1.11, where its logic gets tests. Both modes are run locally, and the cleanup is checked.
  - Done:
    - Claude runs the probe from the shared folder (the user gives the path) and from the local disk;
    - the user does the manual checks;
    - a summary of the results, without internal paths, goes into a note under this task and into the course notes;
    - it is decided whether the architecture holds (design section 14).
  - Note: results from 2026-10-21, from the shared folder and from the local disk. The shared folder is an ordinary Windows file share, not DFS.
    - **Start.** Antivirus, AppLocker and SmartScreen did not react, either from the console or by a double click in Explorer, from the share or locally.
    - **Time to the page in the browser.**

      | Variant | Size | From the share | Locally |
      |---|---|---|---|
      | single-file | 98.6 MB | ~5.9 s | ~1.1 s |
      | single-file, compressed | 47.8 MB | ~13.6 s | ~0.8 s |
      | Native AOT | 8.4 MB | ~3.6 s | ~0.55 s |

      From the share, about 2.5–3 s pass before `Main`, whatever the size. Compression is the slowest from the share, because the whole bundle is unpacked at start.
    - **2000 files of about 440 bytes on the share:**
      - listing with names and dates: 0.1–0.2 s;
      - reading one by one: about 12.5 ms per file, about 25 s for all;
      - reading 8 at a time: about 1 ms per file; 16 at a time: about 0.5 ms; 32 at a time is no better;
      - a second read is not faster;
      - writing: about 30 ms per file; deleting: about 12 ms per file;
      - replacing a file by renaming a temporary file over it works.
    - **Owner.** The share records the creating account as the owner, also after a rename over an old file. Checked with one account only.
    - **Manual checks by the user:**
      - no Previous Versions, also in the parent folder;
      - no DFS tab;
      - in Security, Everyone has Full control, inherited from the parent folder.
    - **Copy to the profile and self-update**, added after the decisions below. A double click on the probe in the share:
      - copies it to `%LOCALAPPDATA%\Programs\Kiler.Probe` (98 MB in about 10 s);
      - the copy writes the new exe next to itself, renames its own running exe, moves the new one into place and starts it;
      - the new exe deletes the old one.

      The antivirus did not react.
  - Note: decisions from 2026-10-22, also in PLAN.md and in the design:
    - **The architecture holds:** a local server on `127.0.0.1` and JSON files in the shared folder.
    - **The exe is published with Native AOT.**
    - **Each user runs a local copy** in `%LOCALAPPDATA%\Programs\Kiler`. Started from the share, `Kiler.exe` copies itself there (M1.5a). With Full control for Everyone, anyone could replace the exe in the share and capture the passwords of everyone who starts it. Updates are signed with ECDSA and checked by the local copy (M3). Only the first copy trusts the share.
    - **The first full read of the records is parallel**, about 16 at a time (M2).
    - **Restore from the local copy.** The share keeps no automatic copies, and `history\` and `trash\` are in the same folder. An admin can restore missing or damaged files from the local copy of the data (M2, the screen in M6).
    - **Detection of edits in place.** Detection by the owner misses them: an editor such as Notepad writes into the same file, and the owner stays the old author. On every write Kiler sets the creation time equal to the write time. A file with a later write time was changed outside Kiler and is marked (M2, M4).
  - Note: the reviews by `code-reviewer` and `security-reviewer` found nothing critical. Fixed:
    - an error gives a `[FAIL]` line and a saved report instead of a crash;
    - the saved report has no folder paths and no account names;
    - it is created with `CreateNew` and a random suffix;
    - the cleanup deletes nothing if the subfolder became a link;
    - a second Ctrl+C ends the process.

    Declined: a warm-up before the reads; JIT costs milliseconds, the difference is 12 ms against 0.5 ms per file. Not exercised: Ctrl+C in the middle of a run, and a delete that fails.
  - Note: the second review, of the copy to the profile, found that a failed step could put the profile path and the user name into the report on the share. Fixed:
    - the report hides them too;
    - the self-update writes `.new` first, then renames and moves, and moves the old exe back on a failure;
    - the self-update and the delete of the old exe work only in the profile folder;
    - the delete is tried several times;
    - a failed copy deletes its temporary file.

    Checked with a forced failure (a read-only exe in the profile) and with a full run from the share. The lessons for the real update are in PLAN.md, M3.
  - Note: the Web SDK leaves `web.config`, `aspnetcorev2_inprocess.dll` and `*.staticwebassets.endpoints.json` next to the published exe. They are not needed (M1.8). Native AOT needs the Visual Studio C++ tools and `vswhere.exe` on PATH.

- [ ] **M1.4 Token, cookie and Host**
  - What:
    - on startup a random 32-byte token is generated;
    - `/?t=<token>` sets an HttpOnly cookie with `SameSite=Strict` and redirects to `/`;
    - every request, including for the static files, requires a valid cookie;
    - the comparison is constant-time (`CryptographicOperations.FixedTimeEquals`);
    - `Host` must be `127.0.0.1:<port>` or `localhost:<port>`, otherwise the request is rejected.
  - Tests (first):
    - no token → 401;
    - wrong token → 401;
    - correct token → cookie and redirect;
    - with cookie → 200;
    - foreign `Host` → 400.
  - Done: the tests pass, and the address with the token, opened by hand, shows the page.

- [ ] **M1.5a Local copy in the profile**
  - What (decided after M1.0b):
    - when `Kiler.exe` runs from a network folder (a UNC path or a mapped network drive), it looks for `%LOCALAPPDATA%\Programs\Kiler\Kiler.exe`;

    - if a copy exists, it only starts it and does not overwrite it, because only the local copy checks the signature of a new version (M3);
    - the single instance (M1.5) is checked first.
  - Tests: unit tests of the decision: started locally, no copy yet, a copy exists. Copying and starting a process are behind interfaces.
  - Done: the tests pass. By hand: a double click on the published exe in a network folder starts the local copy, and the browser opens.

- [ ] **M1.6 Heartbeat via SSE and shutdown**
  - What:
    - `GET /api/events` holds a `text/event-stream` connection and sends `ping` about every 15 s;
    - the server counts the open connections;
    - at zero connections, a wait of about 10 s starts, and a new connection cancels it;
    - after the wait, the exe stops;
    - an initial wait for the first connection of about 60 s;
    - the times are set with parameters for the tests;
    - the event format allows adding new ones later, for example `changed` for M6.
  - Tests:
    - unit tests of the counting and the timers with a fake clock (`FakeTimeProvider`);
    - API test: the connection opens and closes, then the exe stops after the wait;
    - API test: closing and reopening within the wait does not stop the exe.
  - Done: the tests pass.
