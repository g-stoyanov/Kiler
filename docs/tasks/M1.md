## Decisions for the module

| Question | Decision |
|---|---|
| How the exe is built | Native AOT, decided after the checks in M1.0b: 8 MB instead of 99 MB, and a faster start and update. No reflection, JSON with source generation, trim and AOT analyzers enabled. |
| Where the exe runs | Each user runs a local copy in `%LOCALAPPDATA%\Programs\Kiler`. Started from the shared folder, `Kiler.exe` copies itself there (M1.5a). Updates are signed and checked by the local copy (M3). Decided after M1.0b: everyone can write in the shared folder, so anyone could replace the exe there. |
| Heartbeat | SSE (`/api/events`). Closing the last connection starts a wait, after which the exe stops. Later the same channel carries the change notifications (M6). |
| The checks from section 14 | A probe exe before the real code (M1.0b). The `--diag` mode of `Kiler.exe` (M1.11) took over its logic, and the probe is deleted. The results are in the notes under M1.0b ([log/M1.md](log/M1.md)), and the instructions for the checkpoint after M1 in [real-environment-checks.md](../real-environment-checks.md). |
| Commits outside Claude | Git hooks that call the same `data-guard` script (M1.0a). |
| CI | The workflow calls scripts from the repo, so CI can move to Bitbucket after the exam (PLAN section 9). |
| Smoke tests | In Kiler.App.Tests, run only when `KILER_SMOKE_EXE` names the published exe: `smoke.ps1` after `publish.ps1` (M1.9). |
| GitHub Release | Dropped (M1.10). |

## For later modules

Notes of the done tasks for the modules after M1. "Start of a module" collects the ones that name the module ([README.md](README.md)). The open questions are in [PLAN.md, section 6](../PLAN.md#6-open-questions).

- (M1.4) a residual risk that both reviews found, left as it is for now. Cookies are not separated by port, so the browser sends `kiler` to every port of 127.0.0.1 it talks to: a typed address, a link from a Kiler page, the files of a page served there. Whatever listens on that port gets the token and can call Kiler outside the browser, where there is no `Sec-Fetch-Site`. This matters on a machine that several users share; for one user, another process of the same user is not a boundary anyway. A token per origin (for example in `sessionStorage`, sent as a header) would close it, but it changes the cookie model of the plan. For M6/M7: links to loopback addresses in records and documents.
- (M1.8) **A full Content Security Policy now** on every UI file: `default-src 'self'; img-src 'self' data:; object-src 'none'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'`, plus `X-Frame-Options: DENY`, `nosniff` and a referrer policy. M6 and M7 change it in their own tasks if CodeMirror or Mermaid need more.
- (M1.7) M6: the theme moves to the personal configuration; CodeMirror and Mermaid need the resolved theme. `changed` goes through the worker as another `HubMessage` type.
- (M1.7) M4 (E2E): check early that Playwright's browser lets a SharedWorker reach the network, which the Claude Code in-app browser does not.
- (M1.8) M4 (E2E): the tests run against the embedded build, where the policy applies, and fail on a `securitypolicyviolation` event.
- (M1.8) M6: the addresses of the UI's routing have no dot in their last segment; a change of the policy goes with a security review; nothing goes into `public/assets/`.
- (M1.9) M4 (E2E): `KilerExe` starts the published exe with a data folder of its own and gives the `Open:` line; the E2E tests can start Kiler the same way.

## Checkpoint in the real environment

Done on 2026-10-26 with the `Kiler.exe` of the CI push run of `a0ecf12` (SHA-256 checked, also on the shared folder), on the shared folder of M1.0b, from the developer machine, as a normal user. The steps are those of [real-environment-checks.md](../real-environment-checks.md). Claude ran them and watched them with a script. The user made the first and the second start with a double click in Explorer and looked at the browser tabs.

- **Start from the shared folder.**
  - No SmartScreen, "Open File – Security Warning", AppLocker or antivirus reaction. The exe was copied from the downloaded artifact without the "downloaded from the internet" mark (`Zone.Identifier`), so the reaction to a file with that mark was not checked.
  - The first start copied Kiler, wrote `share.json`, made the shortcut and started the copy. The copy was written 7.7 s after the start of the process in the shared folder, and it answered `/api/health` at 8.4 s. The page showed "Connected".
  - The copy is the same file (SHA-256), the shortcut points to it, and `%LOCALAPPDATA%\Kiler` has a protected ACL with the user and SYSTEM.
  - A second double click while Kiler ran: exit code 0 after 5.4 s, no new copy, the same instance, and a new tab with "Connected".
  - After the tabs closed, Kiler stopped with exit code 0 and without its instance file.
  - The Start menu shortcut started the copy in 0.25 s, and it answered after 1.04 s, without copying. The page showed "Connected".
- **`--diag` from the shared folder:** exit code 0 in 105 s, every check `[OK]`. Against the probe of M1.0b:

  | Measure | Now | M1.0b |
  |---|---|---|
  | process start to `Main` | 4.5 s | 2.5–3 s |
  | write, one by one | 31 ms per file | about 30 ms |
  | list with names and dates | 0.06–0.09 ms per file | 0.05–0.1 ms |
  | read one by one | 12.3 ms per file | about 12.5 ms |
  | read 8, 16, 32 at a time | 1.22, 0.62, 0.45 ms per file | about 1, about 0.5, no better than 16 |
  | delete | 12.2 ms per file | about 12 ms |

  The owner of the new subfolder, of a new file and of a file replaced by a rename is the current user.
- **The folder.** Not DFS (`NetDfsGetClientInfo` gives NERR_DfsNoSuchVolume). Everyone has Full control, inherited, and the owner is the user who made the folder. Previous Versions was not checked again; M1.0b found none.
- **DLLs next to the exe.** Process Monitor needs administrator rights, which the developer machine does not have. Instead, copies of the 58 System32 DLLs that the runs had loaded were put next to `Kiler.exe` in the shared folder. The module list of each process started there was read about every 15 ms (`EnumProcessModules`), and the copies were deleted afterwards. Modules from the shared folder:

  | Run | Only from the shared folder | Beside the one from System32 |
  |---|---|---|
  | `--diag` | `NTASN1`, `SSPICLI`, `shell32` | `ntdll`, `advapi32` |
  | a start when the local copy exists | `NTASN1`, `SSPICLI`, `shell32` | `ntdll`, `advapi32` |
  | the first copy | `NTASN1`, `SSPICLI` | `ntdll`, `advapi32`, `shell32` |
  | a second start, which opens the browser | `NTASN1`, `SSPICLI`, `MLANG`, `msIso`, `WININET` | `ntdll`, `advapi32`, `kernel32`, `shell32` |

  So a DLL planted in the shared folder replaces a system DLL in every start from there, more than the local measurement of M1.8 showed (`BCrypt.dll`, `ntdll.dll`, `NTASN1.dll`). The method sees what was loaded, not what was looked for. It can miss a module that loads and unloads between two reads, and it does not show whether a second copy beside the System32 one ran any code. Today this adds nothing, because whoever can write to the shared folder can replace `Kiler.exe` itself. It is input for the check of the first copy in M3 (PLAN section 6), where the candidate fix is `NoRemoteImages` (M1.8).
- **Cleanup.** The exe was deleted from the shared folder, which is as it was before. The local copy, `share.json` and the shortcut were deleted from the profile.

Nothing here changes a decision of M1.0b.
