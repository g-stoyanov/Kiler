# M1. Host and skeleton

The steps are in [PLAN.md, M1](../PLAN.md#m1-host-and-skeleton). How to work on the tasks is described in [README.md](README.md).

## Decisions for the module

| Question | Decision |
|---|---|
| How the exe is built | Native AOT, decided after the checks in M1.0b: 8 MB instead of 99 MB, and a faster start and update. No reflection, JSON with source generation, trim and AOT analyzers enabled. |
| Where the exe runs | Each user runs a local copy in `%LOCALAPPDATA%\Programs\Kiler`. Started from the shared folder, `Kiler.exe` copies itself there (M1.5a). Updates are signed and checked by the local copy (M3). Decided after M1.0b: everyone can write in the shared folder, so anyone could replace the exe there. |
| Heartbeat | SSE (`/api/events`). Closing the last connection starts a wait, after which the exe stops. Later the same channel carries the change notifications (M6). |
| The checks from section 14 | A probe exe before the real code (M1.0b). Later the `--diag` mode of `Kiler.exe` (M1.11) takes over its logic. The results are in the notes under M1.0b. |
| Commits outside Claude | Git hooks that call the same `data-guard` script (M1.0a). |
| CI | The workflow calls scripts from the repo, so CI can move to Bitbucket after the exam (PLAN section 9). |
| GitHub Release | Dropped (M1.10). |

The flags themselves and the heredoc's own line stay. A value is one shell word, read with the quoting rules of the tool, bash or PowerShell.

    - **Start.** Antivirus, AppLocker and SmartScreen did not react, either from the console or by a double click in Explorer, from the share or locally.
    - **Time to the page in the browser.**

      | Variant | Size | From the share | Locally |

      | single-file | 98.6 MB | ~5.9 s | ~1.1 s |
      | single-file, compressed | 47.8 MB | ~13.6 s | ~0.8 s |

      - listing with names and dates: 0.1–0.2 s;
      - reading one by one: about 12.5 ms per file, about 25 s for all;
      - reading 8 at a time: about 1 ms per file; 16 at a time: about 0.5 ms; 32 at a time is no better;
      - a second read is not faster;
      - writing: about 30 ms per file; deleting: about 12 ms per file;

      - no Previous Versions, also in the parent folder;
      - no DFS tab;
      - in Security, Everyone has Full control, inherited from the parent folder.

      - copies it to `%LOCALAPPDATA%\Programs\Kiler.Probe` (98 MB in about 10 s);
      - the copy writes the new exe next to itself, renames its own running exe, moves the new one into place and starts it;
      - the new exe deletes the old one.

      The antivirus did not react.
  - Note: decisions from 2026-10-22, also in PLAN.md and in the design:
    - **The architecture holds:** a local server on `127.0.0.1` and JSON files in the shared folder.
    - **The exe is published with Native AOT.**
    - **Each user runs a local copy** in `%LOCALAPPDATA%\Programs\Kiler`. Started from the share, `Kiler.exe` copies itself there (M1.5a). With Full control for Everyone, anyone could replace the exe in the share and capture the passwords of everyone who starts it. Updates are signed with ECDSA and checked by the local copy (M3). Only the first copy trusts the share.
    - **The first full read of the records is parallel**, about 16 at a time (M2).
    - **Restore from the local copy.** The share keeps no automatic copies, and `history\` and `trash\` are in the same folder. An admin can restore missing or damaged files from the local copy of the data (M2, the screen in M6).
    - **Detection of edits in place.** Detection by the owner misses them: an editor such as Notepad writes into the same file, and the owner stays the old author. On every write Kiler sets the creation time equal to the write time. A file with a later write time was changed outside Kiler and is marked (M2, M4).
  - Note: the reviews by `code-reviewer` and `security-reviewer` found nothing critical. Fixed:
    - an error gives a `[FAIL]` line and a saved report instead of a crash;
    - the saved report has no folder paths and no account names;
    - it is created with `CreateNew` and a random suffix;
    - the cleanup deletes nothing if the subfolder became a link;
    - a second Ctrl+C ends the process.

    Declined: a warm-up before the reads; JIT costs milliseconds, the difference is 12 ms against 0.5 ms per file. Not exercised: Ctrl+C in the middle of a run, and a delete that fails.
  - Note: the second review, of the copy to the profile, found that a failed step could put the profile path and the user name into the report on the share. Fixed:
    - the report hides them too;
    - the self-update writes `.new` first, then renames and moves, and moves the old exe back on a failure;
    - the self-update and the delete of the old exe work only in the profile folder;
    - the delete is tried several times;
    - a failed copy deletes its temporary file.

    Checked with a forced failure (a read-only exe in the profile) and with a full run from the share. The lessons for the real update are in PLAN.md, M3.
  - Note: the Web SDK leaves `web.config`, `aspnetcorev2_inprocess.dll` and `*.staticwebassets.endpoints.json` next to the published exe. They are not needed (M1.8). Native AOT needs the Visual Studio C++ tools and `vswhere.exe` on PATH.
