# M2. Data layer

The steps are in [PLAN.md, M2](../PLAN.md#m2-data-layer). How to work on the tasks is described in [README.md](README.md). The done tasks, with all their notes, are in [log/M2.md](log/M2.md).

## Decisions for the module

Decided at the start of M2, on 2026-10-26.

| Question | Decision |
|---|---|
| What the local copy keeps for restore (PLAN section 6) | The last good version. The local copy follows the changes that Kiler makes: new versions, new history slots and moves to `trash\`. A file that disappears outside the trash, is damaged, or was edited in place keeps its last good copy apart in the local copy, and the layer reports it for restore. The upper layers see the share as it is. |
| Whether `share.json` is checked again when it is read (PLAN section 6) | No. Kiler writes only a network folder there, and the file is in the protected `%LOCALAPPDATA%\Kiler`. A check would catch only a mapped drive letter that later became a local drive. The risk that the M1.5a review named, a network folder that someone else controls, passes such a check; showing the shared folder in the UI (PLAN section 6, M6) is the answer to it. |
| Two writes of one file at once | The history slot is the lock. The old version goes to `history\<folder>\<id>\vN.json` with create-new, which is atomic also over SMB. A second writer of the same version fails there and gets a conflict. A slot left by a crash, older than a limit and with the same bytes as the file, is taken over by the next write. Changed in M2.3, by the user: the slot is written whole under a temporary name and renamed to `vN.json` without replacing, also atomic over SMB, so a crash or a full disk never leaves it half written under its name. Decided in M2.4, by the user: the limit is 2 minutes, on the clock of the file server (the write time of the slot against that of the write's own new temporary file). |
| Which files have a version and history | Every JSON file that Kiler writes in `data\`: records, users, templates, stashes, `settings.json`, `levels.json` and `key.json`. `history\` and `trash\` repeat the folders: `history\records\8f3a1c\v6.json`, `history\settings\v3.json`, `trash\records\8f3a1c.json`. The example in design 5.1 (`history\8f3a1c\v6.json`) is updated. |
| What Kiler.Storage knows of the content | Only `id` and `version`; the rest stays JSON as it is. The layer sets `version` on every write. The models of records, users, templates, stashes and settings come with their modules (M4, M5) in Kiler.Core, with their own source-generated JSON. PLAN M2 step 2 covers only the layer's own types. |
| Where the file owner is read | Through an interface in Kiler.Storage, implemented in Kiler.App with `FileOwner` (M1.11). Storage reads the owner through the handle it reads the content with, and keeps it in the local copy with the file, so a start from the local copy does not ask the share for 2000 owners. The exception to "the Windows parts are interfaces in Kiler.Core" (PLAN section 3). |

From the notes of M1:

- the first full read is parallel, about 16 at a time (M1.0b);
- the stop aborts requests after 5 s, so a write to the shared folder must be safe to abort (M1.6);
- the watching ignores unknown folders, such as the `kiler-diag-*` subfolder that a stopped `--diag` can leave in `data\` (M1.11);
- `--diag` never creates `data\`, and neither does the layer when it opens a data folder (M1.11).

The limits of the local copy, in line with design 7.8, which catches careless changes and not deliberate ones (the threat model of `security-reviewer`):

- (M2.7) when a document of the share does not fit, the last good bytes of gone documents that were in the copy for less than a day (`DataCopy.BriefStay`, from when the copy took the document to when it went, on the clock of this machine), those that went first first, make room for it, only as many as it takes, and none when even all would not do (third security review). Without it, one round of junk put on the share and taken away blocked every new document for good. A document that was in the copy for a day keeps its last good bytes for a restore; junk kept on the share for a day blocks the new documents until the admin forgets it (M2.9). A document listed again after it went counts only the time that the share listed it (`TakenAt`, fourth security review), as junk put back for one load a day later would otherwise count as old. The limit (fourth security review): a real document that is less than a day in a copy, a new one, or any one in a new copy, loses its last good bytes there when someone deletes it and fills the share with junk at the same time; a restore then has only the copies where it is older.
- (M2.7a) four passes of `security-reviewer` each found new ways for someone who writes both a folder and the trash to make the copy follow a move that did not happen. The rules now hold for a late listing of a real move and for careless changes; someone who plants files on purpose can still confuse the copy within the 30 s of a late listing, or make it report a false restore candidate, but not make it drop the last good bytes of a document that it has had longer, or that this Kiler wrote. M2.9 restores only what an admin chooses.
- (M2.7c) the brief leftovers of a private folder of another user make room only in that folder (decided by the user). So someone who fills the private folders of 16 users that an admin's copy is given with 4 MiB of junk each for one load, and takes it away, fills the budget of all the others with leftovers: the new documents of the other private folders stay out of the admin's copy, reported `OverBudget` at every load, until their own folders take new documents or the admin forgets the leftovers (M2.9). Nothing good is lost, and the documents are in the copies of their owners (security review, accepted by the user).

- [ ] **M2.8 Watching for changes**
  - What (PLAN M2 steps 7 and 8):
    - about every 10 s, on `TimeProvider`, one listing per folder. The new, changed and deleted documents are read again and reported to the upper layers as events in the process; the `changed` event of the page is M6;
    - unknown folders (`kiler-diag-*`, M1.11), temporary files and files without `.json` are ignored;
    - a damaged file is skipped and reported, without a crash;
    - when the share cannot be reached, the layer works from the local copy, says that it is offline, refuses writes, and comes back by itself. The UI that shows it is M6.
  - Tests (first), on a fake clock: a new, a changed and a deleted document give their events; a damaged file is reported once and does not stop the others; offline (the file operations fail) and back; a write while offline is refused; an unknown folder is ignored.
  - Done: the tests pass.
  - From earlier tasks (in full in [log/M2.md](log/M2.md)):
    - (M2.1) the file operations go through an internal interface of the layer, with the real implementation on `System.IO`. Tests can then make one step fail (M2.3), count the reads at a time (M2.7) or take the share away (M2.8).
    - (M2.2) a file that is not valid JSON, is not an object, has no matching `id`, has no whole `version` of 1 or more, or is larger than a limit is damaged. Reading it gives "damaged" with the reason, not an exception (M2.8 reports it).
    - (M2.2) M2.7 and M2.8: a file that cannot be opened throws from `Read`: a folder in its place, a deny ACL, a file held without sharing, a byte-range lock. It is reported for that file. It does not stop the others and does not make the layer offline.
    - (M2.3) M2.7: `Read` holds the root and the document folder on every call and checks them through their handles after the open, four requests more per document, so the load holds them once, reads through them, and checks them after its reads. `List` still checks its folder by its attributes. Nothing calls `DeleteOldTemporaryFiles` or `InPlaceEdits` yet: the listings of M2.7 and M2.8 do, with the clock. The `FileStamp` that a write returns is not proof of the share: someone can rename the temporary file away and put a file of their own under its name before the rename (security review), so the local copy keeps the bytes it wrote and reads the share as it is.
    - (M2.7) M2.8: `Load` takes no cancellation and a read can block for about 60 s over SMB; the threads of `Workers` are background threads, but the stop must not wait for a load beyond `KilerHost.ShutdownTimeout`. A root that cannot be held or listed throws (`IOException` or `UnauthorizedAccessException`): offline. `Unreadable` carries no cause; decide whether a report needs one (an HResult or a small enum, never the message). A document whose times anyone touches on every pass is read again every pass (only its bytes are not written again): back off. `Changed` of a whole load is held at once, up to the budget.
    - (M2.7a) the writes of this Kiler go through `DataCopy`: the public `Create`, `Replace`, `Delete` and `RestoreFromTrash` write through the share and then take into the copy what they wrote. That is the bytes as this Kiler's own (`CopyEntry.Own`, never evicted as brief leftovers), the old version into the slot of the copy, and the move to the trash or back. The stamp and the owner stay unknown (`CopyEntry.Unseen`, owner `null`) until the next load reads the file back and compares its hash. `DataCopy` is the entry of the layer for the upper layers; M2.8 adds the refusal while offline there.
    - (M2.7a) M2.8: `DataCopy` is not safe across threads; the writes come from requests and the loads from the loop, so keep them apart there (a lock, or the writes queued to the loop), and refuse the writes while offline. Each write through the copy writes the whole index, and a replace writes it twice; with 20 000 entries and slots, measure it (M2.10, M2.11). `LoadResult` gives no changes of the trash; M6 reads `Trash()`, and M2.8 decides whether an event says that the trash changed. A history folder that cannot be listed, or a slot that cannot be read, is tried again by every load, after the folders that have not failed and within the caps of one load (`CopyLimits.HistoryListings`, `HistoryReads`), with no back-off; after a long time offline many documents can have `HistoryFrom`, and the caps spread them over loads. `LoadResult.Outside` is capped at 1000 a load in the order of the index, with no count of the rest.
    - (M2.7b) a load also lists the private folder of the current user: `OpenPrivate` (three requests for the attributes) and, for each of its four listings, two holds more, of the data folder and `private\`; a write through the copy to the private folder opens it too. A private folder that cannot be opened or listed is reported and never makes a load throw; only the root of the data folder does, so it alone tells offline. A private folder that is not there makes its documents gone; `ListPrivate` runs while the root of the data folder is held, so a data folder that has gone is never taken for it.
    - (M2.7c) the load of an admin lists the private folder of every account given to `DataCopy.CopyOthers` too, one after the other, about 15 requests each even when it is empty, and a few walks of the whole index each: with 50 users, some 750 requests every 10 s from each admin. `CopyOthers` takes at most 200 accounts (`DataCopy.MaxOthers`). Decide whether the loop loads them less often, as they are only for a restore (for example once a minute, with a load that takes the others or not). `CopyOthers` comes from a request after the sign-in (M4) while the loop loads, so it goes under the same lock as the writes. The documents of the other private folders give no events: they are never in `Changed` or `Gone`, only in `Outside`.

FAT and exFAT change it with a move, so every move to the trash or back would be refused after it was done; ReFS has 128-bit ids (`FILE_ID_INFO`); a file system that gives 0 makes the check pass without telling anything (M2.11).
    - (M2.5) M2.11, on the shared folder: NtCreateFile to make and hold a folder (a link at the name, the anonymous SQOS, a DFS path if the share is one), and `HoldOrCreateFolder` on a folder that is there; the move to the trash and back (one step, `ERROR_NOT_SAME_DEVICE` rather than a copy), with the handle of `OpenTimes` open, and the tunneling of such a move; `OpenTimes` on a document of another account (whether `FILE_WRITE_ATTRIBUTES` is given); `TrashAndHistoryTests` with `KILER_TEST_FOLDER`; whether a reparse point can be set over SMB at all, and whether the file server then refuses a mount point on a folder that is not empty, as NTFS does, which the marker relies on; that the marker is deleted when its handle is closed and when the session of the client ends; that the file id of GetFileInformationByHandle stays the same across a move on the share and is not 0 (a file server that gives no stable index would make every delete and restore fail), and which file system the share has (NTFS, ReFS); whether the open of a marker of a client that lost its session lingers on the server until a durable handle times out, and that the file server makes a marker at all (only delete access with `FILE_FLAG_DELETE_ON_CLOSE`): one that refuses it makes every delete and restore fail, though it leaves nothing behind; and a delete woken after its client slept, as the M2.4 note on handles closed by the server: another write can then take over its slot after 2 minutes and write N+1, which the woken delete moves to the trash as N.
    - (M2.6) the owner proves who owns the folder, not that it is the folder that was made: someone could move in a folder that the same account owns, such as one of its `history\records\<id>\` (security review). So the new private folder must also have the id of the temporary folder (`PinnedFolder.ReadId`, the `FileId` of GetFileInformationByHandle), read through the same handles; on NTFS a rename keeps it (M2.11 checks a folder rename on the share). The temporary folder is held from its create through its subfolders until right before the rename, and the data folder and `private\` for the whole create. A refused create leaves the folder at the name as it is.
    - (M2.6) M2.11, on the shared folder: the owner through a handle (a file opened to read, a folder held with `readOwner`, the NtCreateFile handle of a new folder) is the user, not a group or one NAS account for all; holds with `READ_CONTROL` work, also on folders of another account; a folder keeps its id and owner across a rename and its id is not 0 (else every `CreatePrivate` is refused), and which file system the share has; `NtCreateFile` with `FILE_CREATE` on the share; `CreatePrivate` there; the time of `Versions` with 100 slots (the estimate of about a second). With the classic delete, a `Versions` slot open during a takeover keeps the name taken, and the takeover gives a short `Conflict`.
    - (M2.7) M2.11: the load of 2000 documents over SMB with the owner of each file, a listing of a large folder, and whether the file server keeps a time after 9999.
    - (M2.7b) M2.11: every hold of a private folder holds `private\` too, which needs the right to list it; check it on the share with the rights of an ordinary user (a folder with only traverse there makes the private loads and writes fail, reported and with nothing lost).
    - (M2.7c) M2.11: the load of an admin with the private folders of other users (`CopyOthers`): measure its time over SMB with, say, 20 made-up private folders, and check that an admin can list and read the private folders of other accounts there, with their rights as IT sets them. `DocumentFormat.Read` now parses a good file twice (the head through a pooled `JsonDocument`, then the nodes): measure it with the load of 2000 documents. ## For later modules

Notes of the done tasks for the modules after M2. "Start of a module" collects the ones that name the module ([README.md](README.md)).

- (M2.1) creating an empty data folder, for the wizard of M4, the demo data and the tests; opening an existing one, which creates nothing. A data folder that does not exist is an error, so nothing makes a `data\` by mistake.
- (M2.1) a check of every name that becomes part of a path: document ids, account names, folder names. ASCII letters and digits, `.`, `-` and `_`; no leading or trailing dot, no `..`, no reserved device name of Windows (`CON`, `NUL`, `COM1` and so on, also with an extension), a length limit. Names come from the share, which anyone can write, and become paths in the local copy in the profile (M2.7), so a name is checked before any path is built from it. How an account maps to a folder name is decided in M4.
- (M2.1) M4 and M5: the folder name of an account (`users\<account>.json`, `private\<account>\`) and every id are made in lowercase, so they pass the check.
- (M2.2) a document is a UTF-8 JSON object with `id` and `version` at the top. The layer reads only these two and keeps the rest of the object as it is; the models come in M4 and M5, in Kiler.Core.
- (M2.2) M4 and M5: the models read `Content` with case-sensitive JSON contexts. `KilerJsonContext` in Kiler.App uses the web defaults, which ignore case. `id` and `version` come only from `Document.Key` and `Document.Version`.
