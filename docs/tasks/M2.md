# M2. Data layer

The steps are in [PLAN.md, M2](../PLAN.md#m2-data-layer). How to work on the tasks is described in [README.md](README.md).

## Decisions for the module

Decided at the start of M2, on 2026-10-26.

| Question | Decision |
|---|---|
| What the local copy keeps for restore (PLAN section 6) | The last good version. The local copy follows the changes that Kiler makes: new versions, new history slots and moves to `trash\`. A file that disappears outside the trash, is damaged, or was edited in place keeps its last good copy apart in the local copy, and the layer reports it for restore. The upper layers see the share as it is. |
| Whether `share.json` is checked again when it is read (PLAN section 6) | No. Kiler writes only a network folder there, and the file is in the protected `%LOCALAPPDATA%\Kiler`. A check would catch only a mapped drive letter that later became a local drive. The risk that the M1.5a review named, a network folder that someone else controls, passes such a check; showing the shared folder in the UI (PLAN section 6, M6) is the answer to it. |
| Two writes of one file at once | The history slot is the lock. The old version goes to `history\<folder>\<id>\vN.json` with create-new, which is atomic also over SMB. A second writer of the same version fails there and gets a conflict. A slot left by a crash, older than a limit and with the same bytes as the file, is taken over by the next write. Changed in M2.3, by the user: the slot is written whole under a temporary name and renamed to `vN.json` without replacing, also atomic over SMB, so a crash or a full disk never leaves it half written under its name. Decided in M2.4, by the user: the limit is 2 minutes, on the clock of the file server (the write time of the slot against that of the write's own new temporary file). |
| Which files have a version and history | Every JSON file that Kiler writes in `data\`: records, users, templates, stashes, `settings.json`, `levels.json` and `key.json`. `history\` and `trash\` repeat the folders: `history\records\8f3a1c\v6.json`, `history\settings\v3.json`, `trash\records\8f3a1c.json`. The example in design 5.1 (`history\8f3a1c\v6.json`) is updated. |
| What Kiler.Storage knows of the content | Only `id` and `version`; the rest stays JSON as it is. The layer sets `version` on every write. The models of records, users, templates, stashes and settings come with their modules (M4, M5) in Kiler.Core, with their own source-generated JSON. PLAN M2 step 2 covers only the layer's own types. |
| Where the file owner is read | Through an interface in Kiler.Storage, implemented in Kiler.App with `FileOwner` (M1.11). Storage reads the owner through the handle it reads the content with, and keeps it in the local copy with the file, so a start from the local copy does not ask the share for 2000 owners. The exception to "the Windows parts are interfaces in Kiler.Core" (PLAN section 3). |

From the notes of M1:

- the first full read is parallel, about 16 at a time (M1.0b);
- the stop aborts requests after 5 s, so a write to the shared folder must be safe to abort (M1.6);
- the watching ignores unknown folders, such as the `kiler-diag-*` subfolder that a stopped `--diag` can leave in `data\` (M1.11);
- `--diag` never creates `data\`, and neither does the layer when it opens a data folder (M1.11).

## Tasks

- [x] **M2.1 Data folder and names**
  - What:
    - Kiler.Storage gets the layout of a data folder: the folders of design 5.1, with `history\` and `trash\` that repeat them (decided at the start of M2). A private folder `private\<account>\` (`key.json`, `records\`, `history\`, `trash\`) is a root of its own and uses the same code;
    - creating an empty data folder, for the wizard of M4, the demo data and the tests; opening an existing one, which creates nothing. A data folder that does not exist is an error, so nothing makes a `data\` by mistake;
    - a check of every name that becomes part of a path: document ids, account names, folder names. ASCII letters and digits, `.`, `-` and `_`; no leading or trailing dot, no `..`, no reserved device name of Windows (`CON`, `NUL`, `COM1` and so on, also with an extension), a length limit. Names come from the share, which anyone can write, and become paths in the local copy in the profile (M2.7), so a name is checked before any path is built from it. How an account maps to a folder name is decided in M4;
    - a folder or a file that is a link (a reparse point) is not followed. The listing gives the attributes, so this costs no extra request;
    - the file operations go through an internal interface of the layer, with the real implementation on `System.IO`. Tests can then make one step fail (M2.3), count the reads at a time (M2.7) or take the share away (M2.8);
    - the tests that touch the file system take their temporary folder from one place, so M2.11 can point them to a subfolder of the real shared folder.
  - Tests (first): the layout of a new data folder and of a private folder; opening a missing folder fails and creates nothing; refused names: empty, `.`, `..`, `a\b`, `a/b`, `C:x`, `con`, `NUL.json`, `com1`, a trailing dot or space, a control character, a non-ASCII letter, too long; accepted names: `8f3a1c`, `demo.user`, `db`; a folder that is a junction is not followed.

- [x] **M2.2 Documents**
  - What (PLAN M2 step 2, decided at the start of M2):
    - a document is a UTF-8 JSON object with `id` and `version` at the top. The layer reads only these two and keeps the rest of the object as it is; the models come in M4 and M5, in Kiler.Core;
    - the layer sets `version`: 1 on create, one more on every write. A `version` from the caller does not count;
    - `id` equals the file name without `.json`. A root document (`settings.json`, `levels.json`, `key.json`) has its name as `id`;
    - a file that is not valid JSON, is not an object, has no matching `id`, has no whole `version` of 1 or more, or is larger than a limit is damaged. Reading it gives "damaged" with the reason, not an exception (M2.8 reports it);
    - the format of a written file (for example UTF-8 without a BOM, indented, `id` and `version` first) and the size limit are decided in the task;
    - the layer's own types use a `JsonSerializerContext` with source generation in Kiler.Storage. The content goes through `JsonNode` or `Utf8JsonReader`, which need no reflection.
  - Tests (first): a round trip with Cyrillic and with fields the layer does not know, unchanged; `version` 1 on create and one more on a write, whatever the caller sent; every kind of damaged file; an `id` that does not match its file name; a file over the limit is not read whole.
  - Done: the tests pass. Kiler.Storage.Tests runs with reflection-based JSON turned off (`JsonSerializerIsReflectionEnabledByDefault`), as Kiler.App.Tests does.
  - Note (decided in the task, by the user): the limit is 1 MiB. A written file is UTF-8 without a BOM, indented by 2 spaces, with LF and a line end after the object: `id`, then `version`, then the content in the caller's order. Non-ASCII is written as it is (`JavaScriptEncoder.UnsafeRelaxedJsonEscaping`; the file never goes into a page as it is). `Document.Content` is the object without `id` and `version`: the layer owns them, and a write drops them from the caller's content, in any case.
  - Note: the API is `Document` (`Key`, `Version`, `Content`), `DocumentRead` (`Document` or `Damage`), `DocumentDamage` (`TooLarge`, `NotJson`, `NotAnObject`, `WrongId`, `WrongVersion`), `DocumentFormat` (public `MaxSize` and `MaxDepth`; internal `New`, `Next(key, changes, content)`, and `Read` of bytes or of a stream), and the internal `DataFolder.Read` and `IFileSystem.OpenRead`. M2.2 makes the bytes and reads a file. Writing the file is M2.3, so "version 1 on create, one more on a write" is tested here on the bytes.
  - Note: a read is strict. A BOM at the start is skipped, as RFC 8259 allows. Damaged: invalid UTF-8, a comment, a trailing comma, a second value, a name twice in one object at any level (`AllowDuplicateProperties = false`, escaped names too), nesting over `MaxDepth`, an escaped lone surrogate in a string or a name, and a top-level name that is `id` or `version` in another case (`ID`), which an upper layer that ignores case would take for the layer's own. `version` must be a whole number in the text, from 1 to `int.MaxValue`: `1.0`, `1e0` and `"1"` are not. Measured: `JsonNode.Parse` does not skip a BOM, does not check the UTF-8 inside strings, and leaves an escaped lone surrogate in a value until the string is first read. A lone surrogate in a name throws `InvalidOperationException`, not `JsonException`. The writer puts U+FFFD in place of a lone surrogate in the content and throws nothing.
  - Note: `MaxDepth` is 32, half of the serializer's default of 64, so an upper layer can still wrap a document in a response of its own (security review).
  - Note (deviation): no `JsonSerializerContext` yet, as no type of the layer goes through the serializer. The content goes through `JsonNode`, `Utf8JsonWriter` and `Utf8JsonReader`. The first such type is expected with the index of the local copy (M2.7).
  - Note: a `version` of `int.MaxValue` is read, but it has no next version, and `Next` refuses it. Both reviewers proposed to make it damaged. That does not help: the version before it would then be good but could not be followed, and any limit has such a last version. Someone who sets it on the share stops the writes of that document; M2.9 decides how a restore writes over it. The second pass of `security-reviewer` agreed.
  - Note: `code-reviewer` and `security-reviewer` found nothing critical or major. Fixed: the names that are `id` or `version` in another case, the depth limit, and the comments on what a reader blocks and what `OpenRead` throws. New tests: the stream read at the limit and one byte at a time, an empty and a zeroed file, a folder in place of the file, a lone surrogate in the content, Cyrillic and escaped names, and an escaped duplicate `id`. Both reviewers found that one test row was the same as the row above it: the Write tool had turned the escape `\u0069` into `i`. The skill has it now. The second pass of `security-reviewer`, on the fixes, found nothing in the code and corrected two notes below: the worst case of memory, and the writes over `int.MaxValue`.
  - For the next tasks:
    - M2.3: a rename over a file that another handle holds open to read fails with access denied, even with `FileShare.Delete` (measured on the local disk). On SMB, the read of another Kiler, which comes within about 10 s of every change, can do the same. Decide the retry of the rename, and what becomes of the history slot when the rename still fails; M2.11 checks it on the share. Also test "version 1 on create, one more on a write" on the files;
    - M2.3: .NET 10 has `File.SetCreationTimeUtc`, `GetCreationTimeUtc`, `GetLastWriteTimeUtc` and `GetAttributes` on a `SafeFileHandle`. `FILE_FLAG_OPEN_REPARSE_POINT` refuses only the last part of the path, so a `records\` swapped for a junction is still followed, and the folder must be held too (`PinnedFolder`, M1.11);
    - M2.6: `IFileSystem.OpenRead` gives a `Stream`, and `TestFileSystem` wraps it in `CountingStream`, so the handle cannot be reached through it. Reading the owner through the handle needs a change of that interface;
    - M2.7: the local copy needs the bytes as they are, and `DocumentFormat.Read(key, Stream)` drops them. Split the read of the bytes (at most `MaxSize` + 1) from the parse. `Content` is a mutable `JsonObject`, not safe across threads, and its nodes keep the parsed `JsonDocument` alive. Measured on a 1 MiB file: 3 to 4 MiB after the parse, and once every node has been reached, as an upper layer that walks the content reaches them, 15 MiB for 100,000 names and 30 MiB for an array of 500,000 zeros. Anyone on the share chooses the shape, so a budget counts the worst case. Keep the bytes and give each caller a fresh `Document`, or decide a budget. The counters of `TestFileSystem` need `Interlocked` once the reads run in parallel. The check for names twice took 54 ms on 1 MiB with 100,000 names;
    - M2.7 and M2.8: a file that cannot be opened throws from `Read`: a folder in its place, a deny ACL, a file held without sharing, a byte-range lock. It is reported for that file. It does not stop the others and does not make the layer offline;
    - M2.3, M2.4, M2.5 and M2.9: a document whose `version` is `int.MaxValue` cannot be written, and anyone on the share can set it. Every write over it gives a defined result, "cannot be written", not the `ArgumentOutOfRangeException` of `Next`: a change (M2.3), keeping one's own version after a conflict (M2.4), restoring an old version (M2.5), a restore from the local copy (M2.9). The bytes come from `Next` before the history slot is made, so a refused write leaves no slot. M2.9 decides how a restore writes over such a document;
    - M4 and M5: the models read `Content` with case-sensitive JSON contexts. `KilerJsonContext` in Kiler.App uses the web defaults, which ignore case. `id` and `version` come only from `Document.Key` and `Document.Version`. Content stays within `DocumentFormat.MaxSize` and `MaxDepth`; over them, `New` and `Next` throw `ArgumentException`.

- [x] **M2.3 Atomic write and the file times**
  - What (PLAN M2 step 3):
    - creating a document: a temporary file in the same folder, then a rename that does not replace. An id that exists gives "exists";
    - replacing a document: a temporary file, the old version into its history slot (M2.4), then a rename over the file;
    - after the rename, the creation time of the new file is set equal to its write time, through its handle. On a rename over a name, NTFS can give the new file the creation time of the old one (file tunneling, 15 s). Both values then come from one clock, the file system's;
    - the info of a file that the layer gives: size, creation time, write time, and "edited in place" when the write time is later than the creation time (design 5.4 and 7.8);
    - a temporary file has a name that is never a document's (for example `<id>.<random>.tmp`). Readers skip it, and one older than a few minutes, which a crash leaves, is deleted;
    - once started, a write runs to its end: the caller's cancellation does not stop it between the steps, because the stop aborts requests after 5 s (M1.6).
  - Tests (first):
    - a crash at each step, simulated through the file operations: the original stays intact and readable, and no file is half written under its real name;
    - after a write over an old file, within the 15 s of tunneling, the creation time equals the write time (on NTFS);
    - a file edited in place (opened and written outside the layer) is reported, and a file that the layer wrote is not;
    - a temporary file is not read as a document, and an old one is deleted.
  - Done: the tests pass.
  - Note (before the start): between the rename and the set time, a reader can see a write time later than the creation time, so a write of Kiler looks like an edit in place for a moment. The SMB client also caches file information and directory listings for about 10 s, so another machine can see that moment for longer. The rule that keeps it from being reported, for example the same state in two listings far enough apart, is decided in the task and tested on a fake clock.
  - Note (before the start): the review is also done by `security-reviewer` (writes on the shared folder).
  - Note (decided in the task, by the user):
    - Kiler.Storage holds the folders of a path itself, from the root down, each opened as itself through its handle, and opens a document to read as itself, so a link is refused through the handle. `PinnedFolder` moved from Kiler.App to Kiler.Storage, and `NativeFiles` opens with `CreateFileW` (`FILE_FLAG_OPEN_REPARSE_POINT`) behind `OperatingSystem.IsWindows()`: the one exception to a platform-neutral Kiler.Storage (PLAN section 3). Kiler.Storage got `AllowUnsafeBlocks` and `DefaultDllImportSearchPaths(System32)`, with a test as in Kiler.App;
    - the layer stays synchronous, and a write takes no `CancellationToken`, so the stop cannot cut it between the steps;
    - a rename over a document that someone holds open is tried again after 25, 50, 100, 200, 400 and 800 ms (`DataFolder.RenameWaits`, about 1.6 s), on access denied or a sharing violation. When it is still refused, the outcome is `Busy`, and the temporary file and the write's own history slot are deleted. On any other failure the slot stays: if the rename was done and its answer lost, it is the right history, and if not, M2.4 takes it over;
    - an edit in place is reported only when the same size and times, with the write time later than the creation time, have been seen for 30 s on the clock of this machine (`InPlaceEdits.SettleTime`), more than the SMB cache of about 10 s and the watching of about every 10 s together.
  - Note (decided after the reviews, by the user):
    - the history slot is written whole as `v<N>.<8 hex digits>.tmp` in its folder and renamed to `vN.json` without replacing, which is atomic also over SMB and still the lock. A slot written straight under its name with create-new, as decided at the start of M2, is left half written by a crash or a full disk, and M2.4 never takes over a slot with other bytes, so the document could never be written again (`code-reviewer`). The decisions above and M2.4 say so now;
    - an empty held folder can be made a mount point in place, as the hold shares writes, which a rename into the folder needs (`security-reviewer`, measured). So a write checks its held folders through their handles before its renames (`PinnedFolder.ThrowIfLink`). On the developer machine the create-new of the temporary file through such a folder failed already (measured), so the check is for machines and file servers where it goes through (`TestFileSystem.CreateThroughLinks` simulates one), and a folder made a link and back between two steps is still not seen. After the second pass of `security-reviewer`, the check also comes after each read, which goes through such a folder, and before `Busy` deletes the slot by its path: nothing holds the slot during the waits, so someone can delete it and make its emptied folder a link.
  - Note: the API is internal `DataFolder.CreateDocument(key, content)`, `ReplaceDocument(key, version, content)` and `DeleteOldTemporaryFiles(folder, listing, now)`; public `WriteResult` with `WriteOutcome` (`Written`, `Exists`, `Missing`, `Damaged`, `Conflict`, `NoNextVersion`, `Busy`), `Version`, `Stamp`, `OnDisk` and `Damage`; public `FileStamp` (`Size`, `CreationTime`, `LastWriteTime`, `LooksEditedInPlace`) and `PinnedFolder` (`Open`, `ThrowIfLink`); internal `InPlaceEdits` (`ShouldReport`, `Forget`) and `NewFile`. `IFileSystem` got `HoldFolder`, `CreateFile` (create-new as itself through `NativeFiles.CreateNewFile`, shared to read and delete, flushed to the disk, held open), `SetCreationToWriteTime` (through the handle), `MoveFile`, `DeleteFile` and `Wait`, and `OpenRead` opens as itself. `FolderListing.Temporary` gives the temporary files of a listing, `FileEntry.Stamp` the stamp. `DocumentFormat.TryReadBytes` is split from the parse, as M2.7 asked: the write puts the exact old bytes into the slot.
  - Note: a write never writes into a file that is there. Its bytes go into `<id>.<8 hex digits>.tmp` beside the document (`CreatePrivate` names its temporary folder the same way), and a rename puts it in place. The times are set through the handle of that file before the rename and again after it, so a write that stops after the rename leaves the right times when the rename brought back no old creation time. A temporary file older than 10 minutes by its write time is a leftover (`DataFolder.TemporaryFileAge`): the server's clock against this machine's, with room for a difference. `NativeFiles` gives `CreateFileW` the full path, with the `\\?\` prefix from 248 characters, as .NET does; without it a path over 260 characters gave error 3, and a document looked missing (`code-reviewer`). Shorter paths stay without it, as M1.11 and M2.1 measured them (second pass).

  - Note: measured on the local NTFS disk (Windows 11):
    - a rename over a file does not tunnel; a name removed (deleted or renamed away) in the last 15 s does, on the next create or rename into it, so the tests make it so;

- [x] **M2.4 Versions and conflicts**
  - What (PLAN M2 step 4, decided at the start of M2):
