# M2. Data layer

The steps are in [PLAN.md, M2](../PLAN.md#m2-data-layer). How to work on the tasks is described in [README.md](README.md). The done tasks, with all their notes, are in [log/M2.md](log/M2.md).

## Decisions for the module

Decided at the start of M2, on 2026-10-26.

| Question | Decision |
|---|---|
| What the local copy keeps for restore (PLAN section 6) | The last good version. The local copy follows the changes that Kiler makes: new versions, new history slots and moves to `trash\`. A file that disappears outside the trash, is damaged, or was edited in place keeps its last good copy apart in the local copy, and the layer reports it for restore. The upper layers see the share as it is. |
| Whether `share.json` is checked again when it is read (PLAN section 6) | No. Kiler writes only a network folder there, and the file is in the protected `%LOCALAPPDATA%\Kiler`. A check would catch only a mapped drive letter that later became a local drive. The risk that the M1.5a review named, a network folder that someone else controls, passes such a check; showing the shared folder in the UI (PLAN section 6, M6) is the answer to it. |
| Two writes of one file at once | The history slot is the lock. The old version goes to `history\<folder>\<id>\vN.json` with create-new, which is atomic also over SMB. A second writer of the same version fails there and gets a conflict. A slot left by a crash, older than a limit and with the same bytes as the file, is taken over by the next write. Changed in M2.3, by the user: the slot is written whole under a temporary name and renamed to `vN.json` without replacing, also atomic over SMB, so a crash or a full disk never leaves it half written under its name. Decided in M2.4, by the user: the limit is 2 minutes, on the clock of the file server (the write time of the slot against that of the write's own new temporary file). |
| Which files have a version and history | Every JSON file that Kiler writes in `data\`: records, users, templates, stashes, `settings.json`, `levels.json` and `key.json`. `history\` and `trash\` repeat the folders: `history\records\8f3a1c\v6.json`, `history\settings\v3.json`, `trash\records\8f3a1c.json`. The example in design 5.1 (`history\8f3a1c\v6.json`) is updated. |
| What Kiler.Storage knows of the content | Only `id` and `version`; the rest stays JSON as it is. The layer sets `version` on every write. The models of records, users, templates, stashes and settings come with their modules (M4, M5) in Kiler.Core, with their own source-generated JSON. PLAN M2 step 2 covers only the layer's own types. |
| Where the file owner is read | Through an interface in Kiler.Storage, implemented in Kiler.App with `FileOwner` (M1.11). Storage reads the owner through the handle it reads the content with, and keeps it in the local copy with the file, so a start from the local copy does not ask the share for 2000 owners. The exception to "the Windows parts are interfaces in Kiler.Core" (PLAN section 3). |

From the notes of M1:

- the first full read is parallel, about 16 at a time (M1.0b);
- the stop aborts requests after 5 s, so a write to the shared folder must be safe to abort (M1.6);
- the watching ignores unknown folders, such as the `kiler-diag-*` subfolder that a stopped `--diag` can leave in `data\` (M1.11);
- `--diag` never creates `data\`, and neither does the layer when it opens a data folder (M1.11).

The limits of the local copy, in line with design 7.8, which catches careless changes and not deliberate ones (the threat model of `security-reviewer`):

- (M2.7) when a document of the share does not fit, the last good bytes of gone documents that were in the copy for less than a day (`DataCopy.BriefStay`, from when the copy took the document to when it went, on the clock of this machine), those that went first first, make room for it, only as many as it takes, and none when even all would not do (third security review). Without it, one round of junk put on the share and taken away blocked every new document for good. A document that was in the copy for a day keeps its last good bytes for a restore; junk kept on the share for a day blocks the new documents until the admin forgets it (M2.9). A document listed again after it went counts only the time that the share listed it (`TakenAt`, fourth security review), as junk put back for one load a day later would otherwise count as old. The limit (fourth security review): a real document that is less than a day in a copy, a new one, or any one in a new copy, loses its last good bytes there when someone deletes it and fills the share with junk at the same time; a restore then has only the copies where it is older.
- (M2.7a) four passes of `security-reviewer` each found new ways for someone who writes both a folder and the trash to make the copy follow a move that did not happen. The rules now hold for a late listing of a real move and for careless changes; someone who plants files on purpose can still confuse the copy within the 30 s of a late listing, or make it report a false restore candidate, but not make it drop the last good bytes of a document that it has had longer, or that this Kiler wrote. M2.9a to M2.9c restore only what an admin chooses.
- (M2.7c) the brief leftovers of a private folder of another user make room only in that folder (decided by the user). So someone who fills the private folders of 16 users that an admin's copy is given with 4 MiB of junk each for one load, and takes it away, fills the budget of all the others with leftovers: the new documents of the other private folders stay out of the admin's copy, reported `OverBudget` at every load, until their own folders take new documents or the admin forgets the leftovers (M2.9). Nothing good is lost, and the documents are in the copies of their owners (security review, accepted by the user).
- (M2.7d) a private folder is checked against what the copy made or first saw of it (decided by the user). So a copy that has never seen it takes the first folder at the name as it is: a new copy (a new machine, a lost index), a copy whose user has no private folder yet, and one whose user's create was refused because a folder was there (security review). A real change of the folder (IT moves the share, restores it from a backup, or switches the DFS target, all of which change the id; an admin restores it, M2.9c, which changes the owner) is reported until someone accepts it (`DataCopy.AcceptPrivateFolder`), which takes whatever folder is at the name at the next load, not the one that was reported. Accepting covers only the root (decided by the user after the review): a folder in it of another owner than the root, such as a `trash\records\` that anyone made before the user's first delete, blocks the writes that need it until it is put right on the share, by its owner or by IT: a folder of the history or the trash is deleted, and the next write that needs it makes it again; `records\`, which only the create makes, is put back as a folder of the user (second review; out of the model of `security-reviewer`; within it, when Kiler itself makes such a folder, the M2.7d line under M2.9c).

## For later modules

Notes of the done tasks for the modules after M2. "Start of a module" collects the ones that name the module ([README.md](README.md)).

- (M2.1) creating an empty data folder, for the wizard of M4, the demo data and the tests; opening an existing one, which creates nothing. A data folder that does not exist is an error, so nothing makes a `data\` by mistake.
- (M2.1) a check of every name that becomes part of a path: document ids, account names, folder names. ASCII letters and digits, `.`, `-` and `_`; no leading or trailing dot, no `..`, no reserved device name of Windows (`CON`, `NUL`, `COM1` and so on, also with an extension), a length limit. Names come from the share, which anyone can write, and become paths in the local copy in the profile (M2.7), so a name is checked before any path is built from it. How an account maps to a folder name is decided in M4.
- (M2.1) M4 and M5: the folder name of an account (`users\<account>.json`, `private\<account>\`) and every id are made in lowercase, so they pass the check.
- (M2.2) a document is a UTF-8 JSON object with `id` and `version` at the top. The layer reads only these two and keeps the rest of the object as it is; the models come in M4 and M5, in Kiler.Core.
- (M2.2) M4 and M5: the models read `Content` with case-sensitive JSON contexts. `KilerJsonContext` in Kiler.App uses the web defaults, which ignore case. `id` and `version` come only from `Document.Key` and `Document.Version`. Content stays within `DocumentFormat.MaxSize` and `MaxDepth`; over them, `New` and `Next` throw `ArgumentException`.
- (M2.4) M4, M5 and M6: a `Conflict` whose `OnDisk.Version` is the version the write changes means a slot in the way: another write under way, a leftover younger than 2 minutes, or one that is never taken over. "Keep mine" with that version meets it again, so an upper layer does not repeat it in a loop, and the screen asks to try again in a moment rather than show two equal versions.
- (M2.5) restoring an old version is `ReadVersion` and then `ReplaceDocument` of the current version by the caller, without a method of its own (deviation from the wording of "What"): M5 sets who changed it (`updatedBy`, `updatedAt`) before the write, or the check of design 7.8 marks the record.
- (M2.5) M4 and M5: a deleted id is not created again (`Exists`): it is restored from the trash and written over, as a user removed and added again (M4), or a new id is taken; M5 makes new record ids. Deleting the private folder of someone who left (design 7.9) is not a document delete: M4 decides how it goes on the share, and then forgets it in the admin's copy (`DataCopy.ForgetPrivate`, the M2.9 line).
- (M2.6) M4 uses it: a change by someone without `canEdit`, a record whose `updatedBy` is not the owner of its file, a file in a private folder whose owner is not the owner of the folder (design 7.8).
- (M2.6) M6: when a document has no readable current version (deleted or damaged), or one that someone set to a very high `version`, names such as `v2000000000.json` can still push the real slots out of the 100 with owners; they get none, never a wrong one.
- (M2.6) M4: a slot's owner is who wrote the version after it (`DocumentVersion`). An admin process gives new files to the Administrators group on a local disk (M1.11), so decide what `updatedBy` is compared with, the user's SID or the owner of the token, and what a `null` owner means for the marks: it never matches anything (in C#, `null == null` is true). An owner that is a well-known group (S-1-5-32-…) proves nothing; flag it. With "Everyone: Full control" anyone can take ownership of any file: noise, but no one can give a file another user's SID. A `NumberOfLinks` over 1, read through the same handle, and a version lower than in the local copy are cheap extra signals of a file moved or linked in.
- (M2.7) the layer keeps only the index in memory, and the bytes are in the local copy on the disk. A start gives a new `Document` for every document of the local copy, and each load one for each new and changed document; M4 and M5 make their models and keep no `Document` (the M2.2 note on memory).
- (M2.7) M4 and M5: the budget bounds the bytes; a crafted 1 MiB document can take about 30 times as much once its nodes are walked (M2.2 note), so up to about 2 GB in the worst case. A limit of the names in `DocumentFormat` is not decided. Convert each `Document` to the model and drop it.
- (M2.7) `audit\` comes with M4: the load of the local copy takes the root documents and the document folders, `trash\`, `history\` and `private\`, not `audit\`. M4 decides what the load and the local copy do with it.
- (M2.7) M6: show `OverBudget`, `NotCopied` and `Unreadable`; an escaped name can hold `<`, `&`, quotes and braces, so show it as text and give it to a log as an argument, never in the template.
- (M2.7a) M6 shows the trash from the local copy (`DataCopy.Trash()`), and reads it again when a load says that it changed (`LoadResult.TrashChanged`, M2.8).
- (M2.7b) M4, M5 and M6: `DocumentKey.Account` names the private folder of a document, `null` for the data folder. `Documents()`, `Trash()`, and `LoadResult.Changed`, `Gone` and `Outside` give the private documents of the current user with it, and a write through the copy takes `key.InPrivate(account)`. M4 makes the account the folder name, in lowercase, and gives it to `DataCopy.Open` at every open (the M2.7b line under M2.10); M5 makes a private record with `InPrivate`; M6 shows a report of a private folder as `private\<account>\…`.
- (M2.7c) M4: after each sign-in of an admin, give `DataCopy.CopyOthers` the accounts of the other users whose private folders the copy keeps for a restore; decide which (all in `users\`, or only those with the seal of an admin, as anyone can add a user file). A user who is not an admin needs no call: the copies stay as they are until the next call. M6: the reports of these folders name them `private\<account>\…`, and only an admin's copy makes them; their documents are never given, so the screens show only that a restore is possible.
- (M2.7d) M4: make the private folder through `DataCopy.CreatePrivate`, not `DataFolder.CreatePrivate`, so the copy keeps the folder it made; doing it early, such as at the user's first sign-in, and showing a refused create, shortens the time in which a folder that someone else puts at the name is taken as first seen (the limit under the decisions of the module, security review). A create refused because a folder is there leaves the copy to take that folder as first seen at the next load; the mark of design 7.8 of a file whose owner is not that of its folder then marks the user's own files in a folder that someone else made first. The owner of a private folder that M4 compares its files with is the one the copy keeps (`FolderIdentity.Owner` in `_roots`): give it through `DataCopy` when M4 needs it. A write through the copy that throws `ForeignFolderException` is shown, not tried again. M4 and M6: show `SkipReason.ForeignFolder`, and decide who calls `DataCopy.AcceptPrivateFolder` (the user for their own folder, an admin for the others), with a warning that the documents that the folder at the name does not have become gone, kept for a restore. `AcceptPrivateFolder` takes whatever folder is at the name at the next load, not the one that was reported: carrying the identity that was seen and accepting only that one (`AcceptPrivateFolder(account, seen)`) closes it; for the user's own folder, moving the foreign folder aside and making it again (`CreatePrivate`) is safer than accepting a folder that someone planted (security review). Accepting covers only the root: a folder in it reported `ForeignFolder` is put right on the share, so the screen says so instead of offering an accept.
- (M2.7e) M6: show `SkipReason.StoppedCreate` (the folder `private` and the name of the temporary folder): a create of the user's private folder stopped and left a folder that Kiler did not delete, as it holds more than empty folders, has another owner, or the copy knows no private folder of the user yet; the user or IT deletes it on the share. M4: a stopped create waits until a create through the copy (`DataCopy.CreatePrivate`) succeeds, as its owner is compared with that of the private folder the copy knows.
- (M2.7a) M4 and M5: write through `DataCopy`, not `DataFolder`, whose writes are internal. `LoadResult.Outside` is where an edit in place, a version out of order and a damaged file show; an owner of `null` after a write of this Kiler means unknown until the next load.
- (M2.8) M4, M5 and M6: `DataWatch.Loaded` gives each load (`Changed`, `Gone`, `Outside`, `Skipped`, `TrashChanged`) on the thread of the watch, after the load has let go of the copy, so a handler may call it; a handler does not throw (that ends the process) and keeps its work short. After `Failed`, read `Documents()` and `Trash()` again: what the failed load took is in the copy, and no later load gives it. Each public member of `DataCopy` waits for a load under way, up to about 60 s for a read blocked over SMB, `CopyOthers` after a sign-in too; while offline, only for the load that found the share gone (the M2.8c line). The `Skipped` of each load is the state of the share as the copy knows it (a file that cannot be read is tried, and reported, by every load; the stopped creates of the last look by every load until the next), so a screen shows the last one. M6 pushes its `changed` event from `Loaded`.
- (M2.8b) M4, M5 and M6: `LoadResult.Changed` no longer repeats a document whose times alone changed: one read again with the bytes that the copy has comes again only when its owner differs or cannot be read, so M4 sees each change of an owner. A document that the copy has good, whose times anyone touches on every pass with the same bytes, is read again at most every 5 minutes, so a real change of the same size of it can show up to 5 minutes late; a damaged one, one changed outside Kiler and one of another size are still read, and a damaged one given, on every pass. A history folder that fails is reported by every load with the failures of its last try, and tried again at most every 5 minutes.
- (M2.8a) M4, M5 and M6: while the share cannot be reached, the copy is offline (`DataCopy.Offline`), and its writes give `WriteOutcome.Offline`, and `CreatePrivate` throws `OfflineException` (an `IOException`), before they touch the share: the screen says that the shared folder cannot be reached and the change can be made once it is back, and nothing repeats it in a loop. A write that cannot reach the share before a load has said so still throws, as before. M6 shows the state: `DataWatch.OfflineChanged` says each change, and a page that connects reads `DataCopy.Offline`; at each change, read `Documents()` and `Trash()` again, as after `Failed`. A start whose share cannot be reached works from the copy (the M2.8a line under M2.10).
- (M2.8c) M4 and M6: an admin's load takes the private folders of other users once a minute (`DataCopy.OthersInterval`), so their changes outside Kiler (`LoadResult.Outside`) and their skipped entries come up to a minute late (the loads in between repeat what the last pass skipped, so the `Skipped` of each load is still the state as the copy knows it), and each call of `CopyOthers` makes the next load take them all: M4 calls it after a sign-in, not on every request. `AcceptPrivateFolder` of such a folder has the next load take it. While the copy is offline, `Documents()`, `Trash()`, `CopyOthers`, `AcceptPrivateFolder`, and since M2.9 `ToRestore`, `Forget` and `ForgetPrivate`, wait only for the load that found the share gone, not for the tries after it.
- (M2.9) M4 and M6: the restore screen of an admin lists `DataCopy.ToRestore()` (each reported change outside Kiler with the version of its last good bytes, of the private folders of other users too) and forgets with `Forget(changes)`, in bulk, giving the changes back as the list gave them: one that is no longer so is left, and the count says how many went. Forgetting takes the file on the share as it is (decided by the user): one edited in place or out of order becomes the last good, and a damaged one stays damaged. After M4 deletes the private folder of someone who left on the share (design 7.9), it calls `DataCopy.ForgetPrivate(account)` in the admin's copy and no longer gives the account to `CopyOthers`, as a call that gives it copies the folder again while the share has it. The writes back are M2.9a to M2.9c.
