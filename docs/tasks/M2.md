# M2. Data layer

The steps are in [PLAN.md, M2](../PLAN.md#m2-data-layer). How to work on the tasks is described in [README.md](README.md).

## Decisions for the module

Decided at the start of M2, on 2026-10-26.

| Question | Decision |
|---|---|
| What the local copy keeps for restore (PLAN section 6) | The last good version. The local copy follows the changes that Kiler makes: new versions, new history slots and moves to `trash\`. A file that disappears outside the trash, is damaged, or was edited in place keeps its last good copy apart in the local copy, and the layer reports it for restore. The upper layers see the share as it is. |
| Whether `share.json` is checked again when it is read (PLAN section 6) | No. Kiler writes only a network folder there, and the file is in the protected `%LOCALAPPDATA%\Kiler`. A check would catch only a mapped drive letter that later became a local drive. The risk that the M1.5a review named, a network folder that someone else controls, passes such a check; showing the shared folder in the UI (PLAN section 6, M6) is the answer to it. |
| Two writes of one file at once | The history slot is the lock. The old version goes to `history\<folder>\<id>\vN.json` with create-new, which is atomic also over SMB. A second writer of the same version fails there and gets a conflict. A slot left by a crash, older than a limit and with the same bytes as the file, is taken over by the next write. |
| Which files have a version and history | Every JSON file that Kiler writes in `data\`: records, users, templates, stashes, `settings.json`, `levels.json` and `key.json`. `history\` and `trash\` repeat the folders: `history\records\8f3a1c\v6.json`, `history\settings\v3.json`, `trash\records\8f3a1c.json`. The example in design 5.1 (`history\8f3a1c\v6.json`) is updated. |
| What Kiler.Storage knows of the content | Only `id` and `version`; the rest stays JSON as it is. The layer sets `version` on every write. The models of records, users, templates, stashes and settings come with their modules (M4, M5) in Kiler.Core, with their own source-generated JSON. PLAN M2 step 2 covers only the layer's own types. |
| Where the file owner is read | Through an interface in Kiler.Storage, implemented in Kiler.App with `FileOwner` (M1.11). Storage reads the owner through the handle it reads the content with, and keeps it in the local copy with the file, so a start from the local copy does not ask the share for 2000 owners. The exception to "the Windows parts are interfaces in Kiler.Core" (PLAN section 3). |

From the notes of M1:

- the first full read is parallel, about 16 at a time (M1.0b);
- the stop aborts requests after 5 s, so a write to the shared folder must be safe to abort (M1.6);
- the watching ignores unknown folders, such as the `kiler-diag-*` subfolder that a stopped `--diag` can leave in `data\` (M1.11);
- `--diag` never creates `data\`, and neither does the layer when it opens a data folder (M1.11).

## Tasks

- [x] **M2.1 Data folder and names**
  - What:
    - Kiler.Storage gets the layout of a data folder: the folders of design 5.1, with `history\` and `trash\` that repeat them (decided at the start of M2). A private folder `private\<account>\` (`key.json`, `records\`, `history\`, `trash\`) is a root of its own and uses the same code;
    - creating an empty data folder, for the wizard of M4, the demo data and the tests; opening an existing one, which creates nothing. A data folder that does not exist is an error, so nothing makes a `data\` by mistake;
    - a check of every name that becomes part of a path: document ids, account names, folder names. ASCII letters and digits, `.`, `-` and `_`; no leading or trailing dot, no `..`, no reserved device name of Windows (`CON`, `NUL`, `COM1` and so on, also with an extension), a length limit. Names come from the share, which anyone can write, and become paths in the local copy in the profile (M2.7), so a name is checked before any path is built from it. How an account maps to a folder name is decided in M4;
    - a folder or a file that is a link (a reparse point) is not followed. The listing gives the attributes, so this costs no extra request;
    - the file operations go through an internal interface of the layer, with the real implementation on `System.IO`. Tests can then make one step fail (M2.3), count the reads at a time (M2.7) or take the share away (M2.8);
    - the tests that touch the file system take their temporary folder from one place, so M2.11 can point them to a subfolder of the real shared folder.
  - Tests (first): the layout of a new data folder and of a private folder; opening a missing folder fails and creates nothing; refused names: empty, `.`, `..`, `a\b`, `a/b`, `C:x`, `con`, `NUL.json`, `com1`, a trailing dot or space, a control character, a non-ASCII letter, too long; accepted names: `8f3a1c`, `demo.user`, `db`; a folder that is a junction is not followed.
  - Done: the tests pass.
  - Note (before the start): the review is also done by `security-reviewer` (paths).
  - Note (decided in the task, by the user): a name has only lowercase ASCII letters, digits, `.`, `-` and `_`, because a NAS may tell case apart and the local copy in the profile cannot; the limit is 64 characters. The check also refuses a name that ends with `.tmp`, the ending of the layer's temporary files and folders, so a leftover one is never taken for a document or an account.
  - Note (decided in the task, by the user): `DataFolder.Create` needs the folder above, which may be a link (the user chose it), while the data folder itself may not. An existing folder is taken when it holds nothing but empty folders of the layout, so a create that stopped halfway runs again. A new root gets only its top folders; `history\<folder>\` and `trash\<folder>\` come with the first write or delete.
  - Note (decided after the security review, by the user): `CreatePrivate` refuses a private folder that exists, even an empty one: anyone can make it on the share before the first private record, would be its owner, and the owner check of design 7.8 would then mark the user's own files. It makes `private\<account>.<random>.tmp\` with the folders and renames it without replacing, so a create that stops halfway leaves only the temporary folder. Still open (second security review): nothing holds the temporary folder, so someone who watches `private\` can rename it away and put a folder of their own under its name in the few requests before the rename; the owner check of M2.6 closes it (below).
  - Note: the API is `StorageName`, `DocumentKey` (`InFolder`, `AtRoot`), `DataFolder` (`Create`, `Open`, `CreatePrivate`, `OpenPrivate`, `DocumentPath`, `HistoryPath`, `TrashPath`, and the internal `List`, which gives the documents of a folder and apart its links and bad names), and the internal `IFileSystem` (`Attributes`, `List`, `CreateFolder` of one folder, `MoveFolder` without replacing) with `FileSystem` on System.IO. Tests: `TestFolder` and `TestFileSystem`, the real operations with hooks.
  - Note: a link is any reparse point, as the task says. A file that is a reparse point without being a link, such as a file from 32 KB on a volume with data deduplication or a cloud placeholder, is skipped too. M2.11 checks that the documents on the real shared folder are not reparse points.
  - Note: `Directory.Delete` with `recursive` fails on a junction for a user who is not an administrator (it calls `DeleteVolumeMountPoint`), so `TestFolder` deletes the links first. The skill has it.
  - Note: `code-reviewer` and `security-reviewer` found nothing critical or major; `security-reviewer` looked twice, the second time at the fixes. Fixed: `CreatePrivate` checks the data folder, and `CreateFolder` makes one folder, never a chain, so a data folder that has gone does not come back; `List(null)` checks the root; `CreateFolder` refuses a link or a file that is already where it makes a folder; `DataFolder.Path` became `Root`; with `KILER_TEST_FOLDER` the test folders go right into it; a test that makes a junction inside the code under test skips before it starts, as a skip there would be the wrong exception; the decisions above. The second pass of `security-reviewer` wrote the internal terms into a temporary file to grep them; the file was deleted, and both reviewer agents now check the terms with Grep and write nothing. Moved to later tasks: holding the folders during a write, the display of raw names, and async (below).
  - For the next tasks:
    - M2.3 (security review): a folder is checked for a link before the work, so one swapped for a link between the check and a write is followed. M2.3 decides how a write holds its folders. `PinnedFolder` (M1.11) is in Kiler.App and needs kernel32, and Kiler.Storage is platform-neutral today. It also decides how a document is opened so that a link is refused through the handle. `mklink` makes no junction on a network folder, and Windows does not follow remote symbolic links by default, so the risk looks limited to someone with local access to the file server; M2.11 checks whether a junction can be set over SMB at all (`FSCTL_SET_REPARSE_POINT` with the mount point tag, through a handle on the share);
    - M2.3 and M2.7: `IFileSystem` is synchronous, as .NET has no async listing or attributes. M2.3 decides whether reads and writes are async (a write runs to its end anyway), and M2.7 how the 16 reads at a time run;
    - M2.4 and M2.5: `CreateFolder` makes one folder and refuses a link in its place, so `history\<folder>\` comes before `history\<folder>\<id>\`, and a missing `history\<folder>\` or `trash\<folder>\` is empty;
    - M2.6 (second security review): read the owner of a new private folder through its handle (opened as itself, so not through a link) and refuse it when it is not the current user. It closes the race in `CreatePrivate`, and catches a folder made in advance or an owner changed later;
    - M2.7 (security review): `FolderListing.Links` and `BadNames` carry the raw name from the share, which can hold control characters, bidi marks and up to 255 characters. Report an escaped form with a length limit. A `*.tmp` folder in `private\` is a create that stopped (`CreatePrivate`): skip it, and delete an old one;
    - M2.11: `KILER_TEST_FOLDER` names a temporary subfolder of the real shared folder, and the junction tests skip there;
    - M4 and M5: the folder name of an account (`users\<account>.json`, `private\<account>\`) and every id are made in lowercase, so they pass the check.

- [ ] **M2.2 Documents**
  - What (PLAN M2 step 2, decided at the start of M2):
    - a document is a UTF-8 JSON object with `id` and `version` at the top. The layer reads only these two and keeps the rest of the object as it is; the models come in M4 and M5, in Kiler.Core;
    - the layer sets `version`: 1 on create, one more on every write. A `version` from the caller does not count;
    - `id` equals the file name without `.json`. A root document (`settings.json`, `levels.json`, `key.json`) has its name as `id`;
    - a file that is not valid JSON, is not an object, has no matching `id`, has no whole `version` of 1 or more, or is larger than a limit is damaged. Reading it gives "damaged" with the reason, not an exception (M2.8 reports it);
    - the format of a written file (for example UTF-8 without a BOM, indented, `id` and `version` first) and the size limit are decided in the task;
    - the layer's own types use a `JsonSerializerContext` with source generation in Kiler.Storage. The content goes through `JsonNode` or `Utf8JsonReader`, which need no reflection.
  - Tests (first): a round trip with Cyrillic and with fields the layer does not know, unchanged; `version` 1 on create and one more on a write, whatever the caller sent; every kind of damaged file; an `id` that does not match its file name; a file over the limit is not read whole.
  - Done: the tests pass. Kiler.Storage.Tests runs with reflection-based JSON turned off (`JsonSerializerIsReflectionEnabledByDefault`), as Kiler.App.Tests does.

- [ ] **M2.3 Atomic write and the file times**
  - What (PLAN M2 step 3):
    - creating a document: a temporary file in the same folder, then a rename that does not replace. An id that exists gives "exists";
    - replacing a document: a temporary file, the old version into its history slot (M2.4), then a rename over the file;
    - after the rename, the creation time of the new file is set equal to its write time, through its handle. On a rename over a name, NTFS can give the new file the creation time of the old one (file tunneling, 15 s). Both values then come from one clock, the file system's;
    - the info of a file that the layer gives: size, creation time, write time, and "edited in place" when the write time is later than the creation time (design 5.4 and 7.8);
    - a temporary file has a name that is never a document's (for example `<id>.<random>.tmp`). Readers skip it, and one older than a few minutes, which a crash leaves, is deleted;
    - once started, a write runs to its end: the caller's cancellation does not stop it between the steps, because the stop aborts requests after 5 s (M1.6).
  - Tests (first):
    - a crash at each step, simulated through the file operations: the original stays intact and readable, and no file is half written under its real name;
    - after a write over an old file, within the 15 s of tunneling, the creation time equals the write time (on NTFS);
    - a file edited in place (opened and written outside the layer) is reported, and a file that the layer wrote is not;
    - a temporary file is not read as a document, and an old one is deleted.
  - Done: the tests pass.
  - Note (before the start): between the rename and the set time, a reader can see a write time later than the creation time, so a write of Kiler looks like an edit in place for a moment. The SMB client also caches file information and directory listings for about 10 s, so another machine can see that moment for longer. The rule that keeps it from being reported, for example the same state in two listings far enough apart, is decided in the task and tested on a fake clock.
  - Note (before the start): the review is also done by `security-reviewer` (writes on the shared folder).

- [ ] **M2.4 Versions and conflicts**
  - What (PLAN M2 step 4, decided at the start of M2):
    - a write names the version it changes. When the version on disk is another, the result is "conflict" with the document from disk;
    - the lock is the history slot: the old version goes to `history\<folder>\<id>\vN.json` (for a root document `history\<name>\vN.json`) with create-new, which is atomic also over SMB. A writer who cannot create the slot gets a conflict: the document has changed, or another write of it is under way;
    - a slot left by a crash between the slot and the rename: when it is older than a limit (about a minute) and has the same bytes as the document, the next write takes it over. Otherwise it is a conflict.
  - Tests (first): a conflict gives the version from disk; two writers of the same version at once, in many rounds: exactly one wins, the other gets a conflict, and every version has one slot; a fresh leftover slot refuses, and an old one is taken over (on a fake clock); a slot with other bytes is never taken over.
  - Done: the tests pass.
  - Note (before the start): the age of a slot compares its write time, from the clock of the file server, with the clock of this machine. The limit allows for a difference between them.
  - Note (before the start): the review is also done by `security-reviewer`.

- [ ] **M2.5 Trash and history**
  - What (PLAN M2 step 5, design 5.6):
    - deleting with the version: the check and the slot of M2.4, then a move to `trash\<folder>\<id>.json`. An older copy there is replaced, because its version is in history;
    - restoring from the trash: a move back that does not replace. When a document with that id exists, it is an error;
    - the versions of a document: its history slots and its current version, with their times and owners (the owners come from M2.6);
    - reading an old version, and restoring it as a new write of its content: version N+1, with the conflict check.
  - Tests (first): a delete moves the file to the trash and keeps the deleted version in history; a delete with an old version is a conflict; restore from the trash; a restore over a live document is refused; the versions in order; restoring an old version gives N+1 with the old content; all of it also in a private folder.
  - Done: the tests pass.

- [ ] **M2.6 File owner**
  - What (PLAN M2 step 9, decided at the start of M2):
    - an interface in Kiler.Storage that gives the owner of an open file, through its handle, as a SID string, or nothing when it cannot be read. The layer reads the owner through the handle it reads the content with, and gives it in the file's info. This is the exception to "the Windows parts are interfaces in Kiler.Core" (PLAN section 3);
    - the Windows implementation in Kiler.App through `FileOwner` (M1.11), which gets an overload for a handle. The comment in `Kiler.Core.csproj` that puts all the Windows parts in Kiler.Core names the exception;
    - M4 uses it: a change by someone without `canEdit`, a record whose `updatedBy` is not the owner of its file, a file in a private folder whose owner is not the owner of the folder (design 7.8).
  - Tests: in Kiler.Storage (first), with a fake: the owner of each file that is read; an owner that cannot be read gives nothing, not an error. In Kiler.App: the owner of a new file on the local disk, as `FileDiagTests.OwnerIsTheUser` expects it.
  - Done: the tests pass.

- [ ] **M2.7 Local copy and loading**
  - What (PLAN M2 steps 6, 7 and 10, decided at the start of M2):
    - the local copy of a data folder lives in a folder that is given to the layer (Kiler.App gives it in M2.10): the files and an index with their info (size, times, owner);
    - a start gives the documents from the local copy at once, then lists each folder of the share once and reads only the new and changed files, about 16 at a time (M1.0b);
    - the local copy follows the changes that Kiler makes: new versions, new history slots and moves to `trash\`. A file that disappears outside the trash, is damaged, or was edited in place keeps its last good copy apart in the local copy, and the layer reports it for restore (M2.9). The upper layers see the share as it is;
    - a history folder is listed only when its document has changed, not on every pass;
    - only the private folder of the current user is loaded. The other private folders, when the layer is told so (an admin, M4), are copied with only their head read, for restore;
    - `audit\` comes with M4.
  - Tests (first): the first start with an empty local copy reads everything; the second reads only what changed (counted through the file operations); 2000 files: at most 16 reads at a time, all of them loaded, and the time written to the test output; the last good copy of a file deleted outside the trash, damaged or edited in place stays and is reported; a move to the trash is followed; the other private folders are copied and their content is not parsed; names that fail the check of M2.1 are skipped and reported.
  - Done: the tests pass.
  - Note (before the start): the review is also done by `security-reviewer`: names from the share become paths in the profile.

- [ ] **M2.8 Watching for changes**
  - What (PLAN M2 steps 7 and 8):
    - about every 10 s, on `TimeProvider`, one listing per folder. The new, changed and deleted documents are read again and reported to the upper layers as events in the process; the `changed` event of the page is M6;
    - unknown folders (`kiler-diag-*`, M1.11), temporary files and files without `.json` are ignored;
    - a damaged file is skipped and reported, without a crash;
    - when the share cannot be reached, the layer works from the local copy, says that it is offline, refuses writes, and comes back by itself. The UI that shows it is M6.
  - Tests (first), on a fake clock: a new, a changed and a deleted document give their events; a damaged file is reported once and does not stop the others; offline (the file operations fail) and back; a write while offline is refused; an unknown folder is ignored.
  - Done: the tests pass.

- [ ] **M2.9 Restore from the local copy**
  - What (PLAN M2 step 10):
    - the files to restore (missing, damaged, edited in place), each with its last good copy;
    - writing one back through the layer's write;
    - forgetting one that should not come back, such as the private folder of a person who has left (design 7.9);
    - the screen is M6, and the check that only an admin restores is M4.
  - Tests (first): a document deleted outside Kiler is listed and comes back with its bytes; a damaged one and one edited in place come back as their last good version; a document moved to the trash is not listed; another user's private folder comes back from an admin's local copy; a forgotten file is no longer listed.
  - Done: the tests pass.
  - Note (before the start): decided in the task: what becomes of the damaged or edited file that a restore replaces (kept for a look, for example beside the history slots), and its version. A restored file is new, so its owner is the admin who restored it; M4 must not mark it for that (PLAN M4 step 8).
  - Note (before the start): the review is also done by `security-reviewer`.

- [ ] **M2.10 The data folder in Kiler.exe**
  - What:
    - Kiler.App chooses the data folder: `--data`, else `data\` in the folder of `share.json`. It is the rule of `DiagTarget`, kept in one place with it. `share.json` is not checked again (decided at the start of M2). Without a data folder, Kiler runs without data and says so; the screens are M4 and M6;
    - a data folder that does not exist is not created; the wizard of M4 creates it;
    - the local copy goes into a folder per data folder under `%LOCALAPPDATA%\Kiler`, made with `PrivateFolder.Create`;
    - the layer gets the Windows owner and `TimeProvider`, starts with the host and stops on `ApplicationStopping`;
    - the smoke tests leave no local copy in the real profile.
  - Tests: the choice of the folder, as `DiagTargetTests`; on the real Kestrel, a start with a temporary data folder of made-up documents fills its local copy; smoke: the published exe does the same and leaves nothing behind.
  - Done: the tests pass. By hand: the published exe with `--data` on a folder of made-up documents fills its local copy, and a second start reads only what changed.
  - Note (before the start): decided in the task: the name of the folder of the local copy, and how the smoke tests keep it out of the real profile (deleting it as they delete the instance file, or an option for tests).
