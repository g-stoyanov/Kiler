# Kiler.Core: models, the session and permissions

Part of the `kiler-dotnet` skill. Read it with [SKILL.md](SKILL.md) when a task changes Kiler.Core or its tests. Kiler.Core calls the data layer, so read the bullets of [storage.md](storage.md) that the task needs too, such as "Documents in the upper layers", "The name check", "Watching and threads" and "Offline". The cryptographic rules are in the `kiler-crypto` skill.

## The project (M4)

- Kiler.Core connects Kiler.Crypto and Kiler.Storage: the models of the documents (M4: levels, settings, users; M5: templates, records, stashes), the session and the permissions. It has no Windows code: the current account, DPAPI and Explorer are interfaces here, implemented in Kiler.App (SKILL.md, "Windows parts"), and the tests use fakes.
- The tests are written in the same task, after the code; TDD is for Kiler.Crypto and Kiler.Storage. The API tests of the endpoints are in Kiler.App.Tests (host.md).

## Models

- A model is read from a `Document` and written to its content with a source-generated JSON context of Kiler.Core, case-sensitive, not the web defaults of `KilerJsonContext` (storage.md, "Documents in the upper layers"). `id` and `version` come only from `Document.Key` and `Document.Version`. Content stays within `DocumentFormat.MaxSize` and `MaxDepth`; over them, `New` and `Next` throw `ArgumentException`.
- Convert each `Document` to its model and drop it. The layer keeps only its index in memory and the bytes on the disk, and a start or a load gives a new `Document` for each document (M2.7). The budget of the copy bounds the bytes, but a crafted 1 MiB document can take about 30 times as much once its nodes are walked (M2.2), so keep no `JsonNode` of it.
- A document of the share that does not fit its model is invalid, with a reason, not an exception: anyone can write the share (the threat model in the `security-reviewer` agent).
- Every id, and the name of an account, is made in lowercase and passes `StorageName.Check` before a key is built from it (storage.md, "The name check").
- A record type that holds a password, a key or a decrypted value overrides `ToString()` (SKILL.md, "Style").
- The shape of a model (M4.1: `LevelsFile`, `SettingsFile`, `UserFile`): a sealed class with get-only properties, so no `with` makes an invalid one. Its constructor checks the values and throws `ArgumentException` with the reason; `TryRead(Document, out model, out invalid)` gives the same reasons for a content from the share, and `ToContent()` gives the `JsonObject` for `DataCopy.Create` or `Replace`. Its key is `Key` (`levels`, `settings`) or `KeyOf(account)`, and `TryRead` throws `ArgumentException` for another document, a bug of the caller. A model keeps no `version`: the caller keeps `Document.Version` for the `Replace`.
- The JSON types of the models are in `CoreJsonContext` (`ModelJson.cs`): every member nullable, so a missing one is a reason and not an exception; a value of another type is `ModelJson.WrongType`, and the message of the `JsonException` is dropped, as its path can hold a name from the share. A member that a model does not know is skipped when read and left out when written. A reason names the JSON field and never repeats a value from the share.
- A locked set of level keys (`salt` and `keys` of a user file or of `recovery`) goes through `KeySets`: each name is the one digit of a level, `"1"` to the top level (not `"01"`, `"0"` or `"+1"`), and a key has a value; anything else makes the document invalid (decided by the user in M4.1). The model holds the `LockedKeys` of Kiler.Crypto, copied.
- Tests: `TestData` in Kiler.Core.Tests writes a content through a real `DataFolder` and `DataCopy` in a temporary folder and gives the `Document` back, for "reads what it writes". The cases of a content that does not fit call the internal `TryRead(DocumentKey, JsonObject, …)` with the JSON as text, as only the layer makes a `Document`.

## Calling the layer

- Write through `DataCopy` (`Create`, `Replace`, `Delete`, `RestoreFromTrash`), never through `DataFolder`, whose writes are internal: the copy takes what it wrote as its own (M2.7a). `LoadResult.Outside` is where an edit in place, a version out of order and a damaged file show. An owner of `null` after a write of this Kiler means unknown until the next load.
- A `Conflict` whose `OnDisk.Version` is the version the write changes is a slot in the way: another write under way, a leftover younger than 2 minutes, or one that is never taken over. Writing again with that version meets it again, so nothing repeats it in a loop, and the answer asks to try again in a moment rather than give two equal versions (M2.4).
- While the share cannot be reached (`DataCopy.Offline`), the writes give `WriteOutcome.Offline` before they touch it. The answer says that the shared folder cannot be reached and that the change can be made once it is back, and nothing repeats it. A write that cannot reach the share before a load has said so still throws (M2.8a).
- A deleted id is not created again (`Exists`): it comes back from the trash and is written over, or a new id is taken (M2.5).
- `DataWatch.Loaded` gives each load on the thread of the watch, after the load has let go of the copy, so a handler may call the copy. A handler does not throw, which ends the process, and keeps its work short. After `Failed`, and at each `OfflineChanged`, read `Documents()` and `Trash()` again: what the load took is in the copy, and no later load gives it. Each public member of `DataCopy` waits for a load under way, up to about 60 s for a read blocked over SMB; while offline, only for the load that found the share gone (M2.8, M2.8c).

## The team (M4.2)

- `Team` keeps `levels.json`, `settings.json`, `users\*.json` and, from M5.2, `templates\*.json` (`TeamFiles.Templates`, by id) of the local copy as models: each a `TeamFile<T>` with the model and its `Version`, or `Invalid` with a reason (a damaged file has no version). It is made when the copy opens (`KilerData`, host.md), follows each load (`Follow`) and reads the whole copy again after `Failed` and at `OfflineChanged` (`Reload`), all on the thread of the watch. `Files` is one `TeamFiles`, never changed, that each update replaces: a request reads it once and uses what it got.
- A write of this Kiler through the copy is given by no later load, as the copy takes what it wrote as its own (M2.7a): the writer brings it into the team itself. A user file goes through `Team.Replace(user, version)` (M4.5a), which writes through the copy without the lock of the team, as the write can wait for a load, then takes it under the lock, unless a load has brought in a newer version meanwhile; a new user file through `Team.Create(user)` and `levels.json` through `Team.Replace(levels, version)` the same way (M4.6). The wizard (M4.3) calls `Reload` instead, as it writes only into a copy without the files of the team, so the read is short and no load before it can have any of them. A `Replace` takes the `Version` of the `TeamFile` it changes, so a write over a change that the team has not followed yet is a `Conflict`. The watch raises a load after it has let go of the copy, so a load that ended before a write can be followed after it: the team must not take that load's older document over the write. That can happen to a document whose owner alone changed, at the version that the write replaced (M2.8b). So `Team` keeps the versions it wrote (`_written`) until the next `Follow`, which skips an older version of them: the watch runs one load at a time and raises its events before the next, so only that one load can have ended before the write. The limit: a version put back by hand that the first load after the write gives is skipped too.

## Keys and the session (M4)

- The decisions are in `docs/tasks/M4.md`, "Decisions for the module": one session per process, whose levels are the keys it holds, never the `level` of the user file.
- A level key of the session is a `SecretKey`, disposed by a lock, a sign-out and the stop. A request that meets `ObjectDisposedException` from a key (`SecretKey.Use`) answers as locked, not as an error (M3.1); a decryption that answers yes or no catches only `CryptographicException` (crypto.md).
- The caller owns the keys that `LevelKeys.Unlock` gives: keep each one only after `LevelCheck.Verify`, and dispose the rest (`kiler-crypto`, "Rules").
- A password from a request is checked with `Password.Invalid` (8 to 1024 characters) before any key is derived; `Password.MaxLength` is the limit of Kiler.Crypto, which throws over it (M4.3).
- The session (M4.4) is `Session` (`Session.cs`): the keys that verified at the sign-in, and the display name and rights of the user file then (`CanEdit`, `IsAdmin`, `MustChangePassword`), until a lock; a change of the user file reaches it at the next sign-in. `CurrentSession`, in DI, is the one of the process: `Start` puts a new session in place and locks the one before, `Lock` is the sign-out and the "Lock" button alike, and `Dispose` at the stop also locks a session that a sign-in brings after it. A request reads `CurrentSession.Session` once.
- A key of the session is used only through `Session.Use(level, use)`: a lock before or during it is `SessionLockedException`, which the API answers as locked (host.md, "Rights"). `Dispose` sets the mark before it disposes a key, so an `ObjectDisposedException` while the session is not locked is a fault of the code and goes on. A member that hands keys to `LevelKeys.Lock` catches it the same way: `Session.LockKeys(password)` (M4.5a) locks every key, and `Session.LockKeys(top, password)` (M4.6) the keys of the levels 1 to `top`.
- `CurrentSession.Changed` (M4.5b) comes after each `Start` and each lock, once the keys are disposed, on the thread of the change; `Lock()` raises it also without a session, as the page that asks for the lock wants every page on the lock screen. The event stream gives it to the pages (host.md, "Automatic lock"). A cache of decrypted data (M5 on) is dropped at a lock, so it follows `Changed`. A handler of `Changed` does not throw: it runs on the thread of the change, the timer's at the automatic lock, where an exception ends the process and the handlers after it get nothing (M4.5b security review).
- The automatic lock (M4.5b) is `AutoLock`: the host calls `Activity()` for each request of a page. An activity sets the timer when none is set, and again when the minutes have become shorter than what is left of it, as the first request of a page can come before the copy has opened or the wizard has written `settings.json` (code review). When the timer comes, it locks if `AutoLock.MinutesOf(files)` minutes (those of `settings.json`, 30 without one that fits) have passed since the last activity, and else waits for the rest, so longer minutes count from then. It locks with `CurrentSession.Lock(session)`, the session it read under its own lock, which locks only while that session is in place: a sign-in is an activity before its `Start`, so a sign-in at the moment of the lock keeps its new session. The keys are disposed outside the lock of `AutoLock`, as a dispose waits for a use under way and `Activity` must not wait for it. `AutoLockTests` run it on `FakeTimeProvider`, with the sessions of `SessionTests.NewSession`.
- The sign-in is `SignIn.TryStart` over the `TeamFiles` read once (`KilerData.Files`, host.md): `NoUser`, `UserInvalid`, `LevelsInvalid`, `WrongPassword` (a file with keys, and the password unlocks none) and `NoAccess` (no keys, or none that verify).
- The rights are `Access.Check(need, session, files)`, `null` when the request gets what its endpoint needs (`Need`: `Nothing`, `SignedIn`, `Reader`, `Editor`, `Admin`). A guest is a request without a session while the settings have guest mode, and is only a reader of level 0. A session with `MustChangePassword` gets nothing that needs more than `Nothing`, but `SignedIn`, which only the change of password needs (M4.5a). An admin needs `isAdmin` and the key of every level of the current `levels.json`, each verified at the sign-in against the check that it has now: the session keeps the check of each key (`Session.HoldsEvery`, M4.6), and a check that differs (ordinal) is `AccessRefusal.LevelsChanged`, so the admin signs in again and no admin action writes a check planted after the sign-in back under the admin's name. `AccessTests.Matrix` holds each need against each kind of caller; a test session (`SessionTests.NewSession`) verified against the checks of the `levels` it is given, or against made-up ones.
- The change of password (M4.5a) is `PasswordChange.Run(session, team, current, password)`. The session keeps the version of its user file (`UserVersion`, from the sign-in), and the change refuses a file at another version (`UserChanged`, decided by the user), a level of the file whose key the session does not hold (`LevelNotUnlocked`, M3.3) and, in a voluntary change, a current password that unlocks no key (`WrongPassword`). It writes over the version that the session knows, so a newer one on the share is a `Conflict`, and the session's own `PasswordChanged(version)` clears the mark: a new `Session` over the same keys would have them disposed with the old one.
- The admin actions (M4.6) are `AdminActions`: `NewUser`, `ChangeLevel` (a new temporary password with a level, for a forgotten password too), `SetRights` and `RenameLevel`, each over the team's files read once and the version that the team has, and each refuses a session that does not hold every level of that `levels.json` (`LevelsChanged`), as it may have changed since the rights let the request through. An action that gives keys locks the admin's keys of the levels 1 to a level that the admin gave (`Session.LockKeys(top, password)`), never the `level` of a user file, which its user can write (security review); it uses `Password.NewTemporary()` and sets `mustChangePassword`, and the password is in its `AdminResult` only, for the one answer. Making an admin gives the top level the same way; the other changes of the rights keep the keys. The decisions of the user in M4.6 ("The admin actions" in `docs/tasks/M4.md`) are `OwnAccount`, `AdminLevel` and a user's level from 1. The list marks a file whose key names are not the levels 1 to its level (`KeysMatchLevel`), and warns while fewer than two user files that fit have `isAdmin` (`FewAdmins`).
- The wizard (M4.3) is `NewKiler`: `TryCheck` gives the reason of a value that does not fit, before a key is made, `Make` makes the documents and disposes the keys, and `Write` writes them through a `DataCopy`, `levels.json` first and the admin's user file last, after `settings.json` and the initial templates (M5.2), so a Kiler that someone signs in to has every document; it stops at the first that is not written. Whether the data folder may become a new Kiler is the caller's check (`KilerData.TryMakeNew`, host.md, "Data"). The demo data (M4.10) makes its Kiler with it too.

## Templates, stashes and records (M5)

- The decisions are in `docs/tasks/M5.md`, "Decisions for the module": the wizard writes the initial templates, the templates are read only until the exam, a record lists the keys of the fields of each protected group in clear (`fields`), and the ids of records and stashes are 8 characters of `Password.TemporaryAlphabet`.
- The template (M5.2) is `TemplateFile` (`templates\<id>.json`, the id the document's) with its `TemplateField`s, each a `FieldType` (`TemplateField.NameOf` gives the name of the JSON and the API). Beside the rules of `docs/api.md` ("Template"), the check refuses: a key that is not 1 to 40 ASCII letters and digits from a lowercase letter, a key of `TemplateField.Header` (design 6.1) or a key twice, both without regard to case; a field with neither `level` nor `levelByEnv`; a field `env` (`TemplateField.Env`) that is not at level 0 without `levelByEnv`, as it stays at 0; a `levelByEnv` without a field `env` of type `select`, or with a key that is not one of its options (ordinal); a setting on a type that it does not belong to; a `code` without exactly one of `language` and `languages`, and a `dialect` without `language`; options and languages blank or twice without regard to case. A reason names the entry of `fields` by its number, never its key. `ToContent` leaves out the settings that are null or false.
- The initial templates are `InitialTemplates.For(top)`, with every level capped at the top level of the new Kiler, so a Kiler of two levels can write the password of `prod`; `NewKiler.Make` takes them. The templates are read only until the exam, so only the wizard writes them, and a record finds its template in the `TeamFiles` that its request read once (`TeamFiles.Templates`).
- A group is `FieldGroup.Encrypt(key, fields, recordId, level)`, with the UTF-8 of the fields of that level, and is read with `FieldGroup.Decrypt`, whose bytes are zeroed once they are parsed. The record id is one that passed `StorageName.Check`, as an empty id or one with a lone surrogate is an `ArgumentException`, and a group that is missing or not a string is not passed as null. A `CryptographicException` is caught per group, so one damaged or moved group does not fail the record or the list (M3.2 security review).
- The models of M5.3 are `StashFile` (`stashes\<id>.json`) and `RecordFile` (`records\<id>.json`), each id an `ItemId`, so a file of another name does not fit. Both have an `Authorship`: the accounts pass `StorageName`, and the dates are UTC (`DateTime` of kind `Utc`), written as `yyyy-MM-ddTHH:mm:ss.FFFFFFFZ` and read only in that format. `RecordFile.Public` holds the fields of level 0 by key, the description among them (`RecordFile.Description`), read from the members of `public` that are not of the header (`[JsonExtensionData]`, written back by `ToContent`); `Protected` and `Fields` are by level, and the check refuses `fields` with other levels than `protected`, a key twice in `fields`, and a key of `fields` that `public` has. A value is a `FieldValue`: a text, a number or a code (`{ "language", "code" }`); a read takes any of these whatever the type of the field, as a template can change after its records, and `null` and `""` are no value.
- A record as a session reads it is `RecordView` (`RecordView.Read`): `Description` and the fields of the template in its order, each a `RecordField` with a `FieldKind` of `docs/api.md`. Each key is read at the highest level that has it: public, then each group in order, so a group that a key holder wrote takes the place of `public`, which anyone can write. A group of a level that the session holds is decrypted and is the truth; its lists are not read. The lists name the keys of the other groups, `Locked`, or `Unreadable` when the group does not decrypt or what it decrypts to does not fit (not UTF-8, a name or a text whose escape does not decode, not an object, a key twice, a value of no shape); a lock while it reads is `Locked`. The parse leaves the strings as the bytes have them, so the bytes are checked with `Utf8.IsValid` first and `InvalidOperationException` is caught beside `JsonException`, as `DocumentFormat` does for the share (M5.3 reviews). A field is a `secret` when its template says so or its group marks it, `{ "secret": "<value>" }` (`FieldValue.IsSecret`, decided by the user in M5.3, kiler-crypto), as the template is on the share; a `secret` is checked with `FieldValue.Fits` or `IsSecret` over the `JsonElement`, so its value never becomes a string; a key that the template does not have is checked the same way and dropped. A field without a value has `TemplateField.DefaultLevel(env)`, with the `env` of `public` only. Without a template that fits, only the description is read.
- The records in memory are `Records` (M5.3): a `RecordSet`, never changed, with every stash and each record as one session reads it, for every reader the same stashes. A request takes `Records.Read(session)` once, with the session it read once: it gives the set of that session, or reads one for it under the lock, and throws `SessionLockedException` for a locked session, which the API answers as locked. A set of another session is never given, as a sign-in that replaces a session raises `Changed` only after the new one is in place. `Records` follows `CurrentSession.Changed` (a sign-in reads for the new session, a lock for a guest, which drops what was decrypted); its handler has the guard of the M4.5b security review, so a fault while it decrypts reads for a guest instead of throwing. The host calls `Follow` with each load after `Team.Follow`, as it reads the templates of the team and reads again the records whose template entry changed (by reference), and `Reload` after `Team.Reload` (`KilerData`, host.md). `Dispose` drops the set too, so what was decrypted goes also when DI disposes it before the session. A request reads the values of a record only from its `RecordView`, never from `RecordFile.Public`, which keeps a `secret` that a file changed by hand has at level 0.
- The search (M5.6) is `RecordSearch.Find(set, query)` over one `RecordSet`, the rules of `docs/api.md` (`GET /api/records`): one pass without an index of words, which counts each record for the records, the tree and the facets by the one part of the query that it alone misses. The search text of each record and the texts of its fields with `filter` are made at the first search of a set and kept with it (`RecordSet.Index`, `SearchIndex`); each change of the share, sign-in and lock gives a new set, so they follow. They come only from the view (kind `Value`, and the type is checked too, so a `secret` never comes in), with `RecordSearch.TextOf` for a value; the search text and the words are in `ToUpperInvariant` and compared ordinal, the tags and the filters with `OrdinalIgnoreCase`. A record whose file does not fit is left out. `DemoVolumeTests` times it over the 2000 records of the volume mode; its numbers are in the M5.6 note of `docs/tasks/log/M5.md`.
- A write of this Kiler goes through `Records` (M5.4): `Create(record)` and `Create(stash)` write through the copy without the lock and take what was written into the set under it (`TakeWritten`), as `Team` does, unless a load has brought in a newer version meanwhile.
- The writes of an editor are `RecordActions` (M5.4): `NewRecord` over a `RecordDraft`, the request as it came, and `NewStash`, each a `RecordResult` with a `RecordOutcome`, the sentence for the user and the `field` of `docs/api.md`. A new record takes its template from the `TeamFiles` of the request, and its stashes and `ref`s from `Records.Read(author)`: a stash of the path fits its model, as `GET /api/stashes` gives only those, and a `ref` names a record whose file fits and whose template is the `refTemplate`, at any level. A field with a value takes the higher of `TemplateField.DefaultLevel(env)`, with the `env` of the draft, and the level asked; a level whose key the session does not hold (`Session.Reads`) is refused with that field, and a field without a value is in no group. A group is the UTF-8 of a JSON object of its fields, the description first and then in the order of the template, written with the encoder of the documents and zeroed once encrypted, each `secret` as `{ "secret": "<value>" }`. A new id that meets `Exists` takes another, up to five; a content larger than a document is the `ArgumentException` of the layer, refused with `field` null. The id, the dates (`TimeProvider`, UTC) and the authors come from the exe; the result has the record as `Records.Read(author)` gives it after the write.
