# tools/Kiler.Release: the release tool

Part of the `kiler-dotnet` skill. Read it with [SKILL.md](SKILL.md) when a task changes `tools/Kiler.Release` or its tests, or the format of `version.json` (`VersionFile` in Kiler.Core). The cryptographic rules and formats are in the `kiler-crypto` skill; how a release is made is in `docs/release.md`.

## The tool (M3.5)

- A console exe in `Kiler.slnx`, run on the maintainer's machine with `dotnet run --project tools\Kiler.Release -- <command>`, never published and never run in CI with a real key. `keygen <key file>` makes the signing key; `sign <exe> <key file> [<second key file>]` writes the signed `version.json` next to the exe. Exit code 0 when it did the work, 1 when it refused (nothing written), 2 for wrong arguments. `ReleaseTool.Run(args, IToolConsole)` holds the logic; `Program.cs` gives it `SystemConsole`.
- It references Kiler.Core for `VersionFile`, the one definition of `version.json` (`version`, `sha256` as lowercase hex, `signatures`, a list of one or two, M3.6; indented, LF, no BOM, the relaxed escaping of the data layer, so the `+` of base64 stays readable), which the local copies read too (`VersionFile.TryRead`, M3.6). `sign` writes one signature per key file, in the order of the arguments: two during a change of key (M3.8a). `VersionFile.MaxExeSize` is the one limit of the exe, for `sign` and for the copies, so the tool never signs an exe that the copies refuse. Kiler.App never uses `SigningKey` (a test of Kiler.App.Tests reads its type references).
- **A password** is read into a pinned `char[]` of `Password.MaxLength + 1` (Kiler.Core: `PasswordKey.MaxLength` is internal to Kiler.Crypto), passed as a span and zeroed in a `finally`; it never becomes a `string` and never reaches a line of the tool. A full buffer means a password that is too long. The prompts go to the standard error, so the standard output holds only the result.
  - From a console: `Console.ReadKey(intercept: true)`, without echo; Backspace takes a key back, other control keys are skipped.
  - With the input redirected, only with `--password-stdin` at the end of the command (`ReleaseTool.PasswordFromInput`), for the tests and a key made for a check: one line of the input as strict UTF-8, read a byte at a time so that `keygen` can read two lines, without the `\r\n` and without a byte order mark at its start. Windows PowerShell 5.1 with `$OutputEncoding` of UTF-8 puts one before what it pipes to an exe, and the first password then never matched (M3.5). Without the option a redirected input is refused before any prompt: in a terminal whose input is a pipe, such as the mintty of Git Bash, a typed password would be shown and kept in the scrollback (security review of M3.5).
- **Paths:** every file is on a local disk. A UNC path, a device path of one and a network drive are refused (`ReleaseTool.IsOnNetwork`, which repeats `CopyFiles.IsNetworkPath` of Kiler.App): an exe on the shared folder may have been changed by anyone in the team, and a key file there could be copied for an offline guess.
- **keygen** refuses, before it asks the password, a name that does not end with `.kilerkey` in lower case (`.gitignore` takes another case only while `core.ignorecase` is true), a file that is there and a folder that is not. It checks `SigningKey.MinPasswordLength` (16) and `Password.MaxLength` before it asks the second time, compares the two, and writes the one line of `SigningKey.Lock` with `FileMode.CreateNew` and a flush to the disk; a failed write deletes what it made.
- **sign** reads the exe once, whole, through a handle that lets no one write it, up to `VersionFile.MaxExeSize`, and takes both the version and the SHA-256 from those bytes. The key file is read up to `MaxKeyFileSize`, with a UTF-8 byte order mark taken off. It refuses an exe without a version, and a key file that is missing or too large, before it asks a password; then for each key file in turn a prompt that names it, `SigningKey.TryUnlock` and the zeroing of that password, so a wrong or missing password of either key refuses before the next is asked (M3.8a). Two key files of the same key are refused once both are unlocked, by their public keys, so a copy of the file or one locked again with another password is seen too. Then `Sign` with each key, a check of each new signature with `UpdateSignature.Verify`, and `version.json` over the one of an earlier release, through a temporary file and a rename, so no cut file is left next to the exe. It cannot compare a key with `UpdateKey.PublicKey` of Kiler.App, which it does not reference (the constant is in the native exe since the check of M3.6 uses it), so it prints the public key of each key file, one `Public key:` line each in their order, and `docs/release.md` has the maintainer compare them.
- **The version of an exe** (`ExeVersion`): the `ProductVersion` of its version resource, without the build metadata after `+`, through `ReleaseVersion.TryParse`. The compiler writes the informational version there, and Native AOT copies the Win32 resources of the managed assembly into the exe (`--win32resourcemodule` of ILCompiler; `IlcGenerateWin32Resources=false` would drop them), so it is the version that Kiler shows as its own (`HealthApi.Version`). `PEHeaders` reads the headers (bytes without `MZ` parse as COFF, with no `PEHeader`; it can throw `BadImageFormatException`, `IOException` or `ArgumentException`); the tool walks the resource directory (type 16, the first name, the first language) and the blocks of `VS_VERSIONINFO` itself, within the bounds of the bytes, and two string tables that differ give no version.

## Tests

- `Kiler.Release.Tests` runs the tool in process with `FakeConsole` (the passwords in order, the lines and the prompts, and `InputRedirected`), and `ToolProcessTests` runs `Kiler.Release.exe` from the test output with its input redirected and `--password-stdin`. The paths on the network in the tests are only strings: `IsOnNetwork` asks a drive type only of a drive letter, so no test reaches the network. A test checks that no line holds the password.
- The exe of the tests is a copy of `Kiler.Release.dll` as `Kiler.exe` (`ToolFolder.Exe`): a PE with the version resource of the compiler, whose version is the informational version of the build. `PeBytes` changes its bytes (no resource directory, another product version in its one UTF-16 place), and `VersionBlocks` makes version resources by hand for the cases the compiler does not make.
- `ToolFolder.KeyFile(name, password)` makes a key file of a test, and `ReadVersionFile` reads a `version.json` with all its signatures (`ReadVersionJson` asserts the one of a single key).
- The password of the tests (`ToolFolder.Password`) is public, as the source is: no key of the tests ever signs a release, and the built-in key is never one of them (`UpdateKeyTests` in Kiler.App.Tests).

## Manual check

- After a change of `ExeVersion` or of the publish, sign a copy of `artifacts\publish\Kiler.exe` in a temporary folder with a key made there for the check, the passwords piped from PowerShell with `--password-stdin`, and compare the `sha256` of `version.json` with `Get-FileHash` (upper case) and its `version` with `VersionPrefix`; delete the folder afterwards. In M3.5 the published 1.0.0 gave version 1.0.0 and the same hash.
