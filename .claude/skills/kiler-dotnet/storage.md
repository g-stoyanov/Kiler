# Kiler.Storage: the data layer

Part of the `kiler-dotnet` skill. Read it with [SKILL.md](SKILL.md) when a task changes Kiler.Storage or its tests, or code that calls the layer (M4, M5).

## Data layer (M2)

Decided at the start of M2 (`docs/tasks/M2.md`, "Decisions for the module"):

- **Documents.** Every JSON file that Kiler writes in `data\` is a document with `id` and `version` at the top: records, users, templates, stashes, `settings.json`, `levels.json`, `key.json`. Kiler.Storage reads only these two and keeps the rest as it is; it sets `version` itself on every write. The typed models (records, users, templates, stashes, settings) live in Kiler.Core with their modules (M4, M5) and their own source-generated JSON, not in Kiler.Storage.
- **Layout.** `history\` and `trash\` repeat the folders: `history\records\<id>\vN.json`, `history\settings\vN.json`, `trash\records\<id>.json`. A private folder `private\<account>\` is a root of its own with the same code.
- **Writes** (M2.3, `DataFolder.Writes.cs`): a temporary file, the old version into its history slot, a rename; the creation time is set equal to the write time through the handle of the new file, before the rename and again after it (file tunneling). Never write into a file that is there: every file is made with create-new as itself (`NativeFiles.CreateNewFile`, never `FileMode.CreateNew`) under `<name>.<8 hex digits>.tmp` (`TemporaryName`), shared to read and delete, flushed, and put in place by a rename. The layer is synchronous, and a write takes no `CancellationToken`: once started, it runs to its end, as the stop aborts requests after 5 s (M1.6). A rename over a document that someone holds open (access denied or a sharing violation) is tried again for about 1.6 s (`RenameWaits`, `TryMove`), then `Busy`, with the write's temporary file deleted and its slot deleted through the slot's own handle (`DeleteNewFile`, M2.5), never by its name: someone may have put another slot there during the waits. A slot that cannot be deleted stays, and is taken over later; on any other failure the slot stays. The outcomes are `WriteOutcome`; content over the limits is an `ArgumentException` before any file is made.
- **Trash and history** (M2.5, `DataFolder.History.cs`): a delete names its version, makes the slot of that version as a write does (`TryReadVersion`, `MakeSlot`, the same lock and takeover), holds `trash\<folder>\`, and moves the document there over an older copy (`Deleted`). A restore moves it back without replacing (`Exists` when an id is live) and deletes the slot of its delete through `DeleteLeftoverSlot` without the age (decided by the user), so the next write does not wait; a failure in that delete is swallowed, as the slot is taken over after 2 minutes anyway. `CreateDocument` refuses an id whose history folder exists (decided by the user): a deleted id comes back from the trash, never as a new version 1. An old version comes back as `ReadVersion` and then `ReplaceDocument` by the caller, who sets who changed it. `Versions` reads the current version first, then lists the history folder once; only `v<N>.json` (`SlotVersion`) counts. A move to the trash or back is held for its times (`OpenTimes`) and puts the creation time back after it (`KeepCreationTime`): NTFS tunnels a move from another folder too (measured). Every move goes through `TryMove`, which checks the held folders it is given before each try and after the move: an empty trash or document folder can be made a mount point during the waits (security review). A move to the trash or back holds a marker in both of its folders, made before the slot of a delete (`HoldMarker`, `CreateMarker`: an empty temporary file with delete-on-close that no one can delete or rename, so the folder is never empty, and NTFS refuses a mount point on a folder that is not empty, measured), and `MoveDocument` checks after the move that the file at the new name has the id of the file held for its times (`FileTimes.Id`), as MoveFileExW moves whatever is at the name (decided by the user after the second security review). The id is the 64-bit index that NTFS keeps across a move; FAT changes it, ReFS has 128-bit ids, and 0 tells nothing (M2.11 checks the share). A delete that fails before its move keeps no slot: `TryMove` says whether the file may have moved (`mayHaveMoved`), and only a move that may have been done, its answer lost, leaves the slot as history; the rest delete their own slot through its handle, as `Busy` does (fourth security review).
- **The lock** is the history slot: written whole under a temporary name and renamed to `vN.json` without replacing (`MoveFile` with `replace: false`), which is atomic also over SMB, so the second writer of the same version gets a conflict and a crash never leaves a half-written slot (decided in M2.3, after create-new straight under the name). Do not replace it with a check followed by a rename. The write keeps its slot open to write (the `NewFile` of the slot) until the document is replaced, and so must every write that makes a slot (M2.5): a takeover cannot hold an open slot (M2.4).
- **Takeover of a slot** (M2.4, `MakeSlot`, `DeleteLeftoverSlot`): a slot that a crash left between the slot and the rename is taken over only when it is `SlotAge` (2 minutes) older than the write's own new temporary file, both write times from the file server (decided by the user: no difference between the clocks of machines counts); has the bytes the write read; and the document, read again while the slot is held, still has them (else it is the history of a write that replaced the document since). It is held as itself (`HoldFile`: read and delete, shared only to read, so a second takeover or a write under way stops it with a sharing violation), the held folders are checked, it is deleted through its handle (`DeleteHeldFile`), and the rename of the write's own slot is tried once more, which decides. A link, a folder, a read-only slot, one held without delete sharing, one that goes in between and any other bytes give `Conflict`. A test of the age makes the file server's clock differ from the machine's (`WriteTakes`), as the test machine is both.
- **Holding** (M2.3): a read or a write holds the folders of its path from the root down (`Hold`, `PinnedFolder`), each opened as itself through the folders held above it, and a document is opened to read as itself (`NativeFiles.OpenFileToRead`), so a link is refused through the handle. The hold stops renames and deletes; it shares writes, which a rename into the folder needs, so an empty held folder can still be made a mount point in place, and the layer checks its held folders through their handles (`ThrowIfLink`) after a read, before the renames, and before it deletes by path what it did not hold in between. A rename without replace onto a symbolic link or a junction, also one whose target is missing, gives "exists" and does not follow it. `FileMode.CreateNew` of .NET followed a symbolic link whose target was missing and made the target on the CI runner, though not on the developer machine, so files are made with `FILE_FLAG_OPEN_REPARSE_POINT`. A missing folder is made and held in one call that opens a link at the name as itself (`HoldOrCreateFolder`, NtCreateFile, M2.5); a folder that is there is held with `HoldFolder`, as a file server may ask for the right to make a folder even when it is there.
- **Links behave differently by machine** (M2.3): Windows 11 with developer mode and no administrator (the developer machine) and Windows Server with an administrator (the CI runner) followed links differently. A measurement on one machine does not settle a question about links: use the call that cannot follow (`FILE_FLAG_OPEN_REPARSE_POINT`, a rename without replace), and let CI run the test as the second machine.
- **Windows code in Kiler.Storage** (M2.3): only `NativeFiles` (`CreateFileW` with `FILE_FLAG_OPEN_REPARSE_POINT` and `SECURITY_SQOS_PRESENT`: hold a folder, open a file to read, make a new file with delete access, open a file to delete it, open a file only for its times, make a marker with `FILE_FLAG_DELETE_ON_CLOSE`; `GetFileInformationByHandle` for the id of a file; since M2.4 `SetFileInformationByHandle` to delete through a handle, `DeleteOnClose`; since M2.5 `NtCreateFile` with `FILE_OPEN_IF`, `FILE_DIRECTORY_FILE` and `FILE_OPEN_REPARSE_POINT` to make and hold a folder, with an NT path `\??\…` or `\??\UNC\…` built by `NtPath`, and `MoveFileExW` without `MOVEFILE_COPY_ALLOWED`), because .NET cannot open a path as itself, delete through a handle, make a folder as itself or move without a copy. Never `Directory.CreateDirectory` (it may follow a link at the name and makes a chain) or `File.Move` (it copies to another volume, so a crash can leave the file in both places). The guard `if (!OperatingSystem.IsWindows())` stands in each method that calls Windows: `CA1416` does not see one in a helper method. From 248 characters the path gets the `\\?\` prefix (`\\?\UNC\` for a network path) after `Path.GetFullPath`, as .NET does in its own calls; without it a path over 260 characters gives error 3. Kiler.Storage has `AllowUnsafeBlocks` and `DefaultDllImportSearchPaths(System32)`, checked by `DependencyTests`.
- **Edits in place** (M2.3): `FileStamp.LooksEditedInPlace` is a write time later than the creation time. A document is reported only when `InPlaceEdits` has seen the same stamp for 30 s on `TimeProvider` (`ShouldReport`), because a write of another Kiler looks edited for a moment, and for about 10 s through the SMB cache.
- **Owners** (M2.6, design 7.8): `IFileOwner` (public, in Kiler.Storage) gives the owner of an open file or folder through its handle as a SID string, or `null` when it cannot be read, never an exception; Kiler.App implements it in `FileOwner.Instance` (GetSecurityInfo on the handle). The layer reads the owner through the handle it reads the content with (`IFileSystem.Owner(Stream)`), never by path: `DocumentRead.Owner`, also for a damaged file, and `DocumentVersion.Owner`. Only `Versions` opens the history slots for their owners alone, the newest `SlotsWithOwners` (100) of them up to the version after the current one, as anyone can put any number of slot names there. A folder is held with `READ_CONTROL` only where its owner is read (`HoldFolder(path, readOwner: true)`, `Owner(PinnedFolder)`): since M2.7d, every folder of a private folder, its root among them; a share may refuse it where it lets a folder be listed. The owner is not in `FileStamp`, which the listings give and compare. The public `DataFolder.Create` and `Open` take the owners and have no overload without them. `null` means unknown, never another owner: in C#, `null == null` is true.
- **Temporary files** (M2.3): a listing gives them apart (`FolderListing.Temporary`, only the names `TemporaryName` makes), never as documents; `DeleteOldTemporaryFiles` deletes those older than 10 minutes by their write time, the server's clock against this machine's.
- **The local copy** follows only the changes that Kiler makes: new versions, history slots, moves to `trash\`. A file that disappears outside the trash, is damaged or was edited in place keeps its last good copy apart, and is reported for restore.
- **Following the changes** (M2.7a, `DataCopy`): the copy's `data\` also repeats `trash\` and `history\`, and `kept\` repeats its places with the last good bytes of a document whose file on the share is not a version that Kiler made. An entry is per document and place (`Spot`: the key and `InTrash`). A load lists every folder, the trash ones too, before it chooses what to read for all of them at once, so a document that leaves one place and is listed new or changed in the other is a move, read as a change of the document from there. The state of every read comes from one function (`Next`): the last good bytes again are good; damaged; a stamp that looks edited; no last good version or a newer one is good; else `OutOfOrder` (decided by the user). A change outside Kiler keeps its last good bytes in `kept\` at once and is reported once in `LoadResult.Outside`, an edit in place only once `InPlaceEdits` has seen it settle. The history of a document is listed only when `HistoryFrom` says it changed, and only the new slots are taken, at most 100 a listing, in a budget of its own whose oldest slots make room (decided by the user). The upper layers write through `DataCopy` (`Create`, `Replace`, `Delete`, `RestoreFromTrash`), which takes the bytes it wrote as its own (`Own`, never evicted as a brief leftover) with a stamp that no listing gives (`CopyEntry.Unseen`) and the owner unknown, so the next load reads the share's file back and compares its hash (M2.3 and M2.6 notes). The budget plans a read at the larger of the file and the last good bytes (`Planned`); what a read needs beyond that comes from what the plan left (`Room.Spare` of `Plan.Room`, M2.7c), or the read is `OverBudget` and given all the same. A write through the copy is taken only within the budget (`HasRoom`): an index with more entries than the budget is no index at the next start, which then deletes the whole copy. Files of the copy are put apart or deleted only by comparing the files that the entries name before and after a change (`FilesOf`, `Stale`), and are deleted only after an index that no longer names them is on the disk (`_stale`, flushed by `TryWriteIndex`); the bytes of a version that Kiler made are overwritten only after an index names where they went (`Guarded`), so a stop at any step leaves the last good bytes named (review of M2.7a). A new version keeps the version the copy had as its own slot (`PlanApart`), never left to the history of the share; no slot of the share is taken for a version whose bytes the copy has, current or kept, the deleted version in the trash too (`held`); a history listing reads first and makes room only for the slots that were read good, at most 100 and 8 MiB a listing, and one load lists at most `CopyLimits.HistoryListings` folders and reads `HistoryReads`; the slots of this Kiler (`SlotEntry.Own`) are pushed out only by each other, and push out the slots of the share first (decided by the user). A move can show in two loads, as the SMB client caches each listing for about 10 s: a document listed in both places, or gone from one less than 30 s before the other lists it (`JustGone`), is still followed, but only onto nothing or a late listing (`IsLateListing`: an entry that the copy took less than 30 s ago and has not reported) that is not of this Kiler and has no last good bytes or the same ones (`CanTakeThePlaceOf`), once a document a load: any other entry keeps its last good bytes, its stay and `Own`, else a file put in the other place and taken away changes what the copy keeps of a real document (third and fourth security reviews). A document that goes while a late listing of the other place has its last good bytes goes without them, unreported, and that entry keeps the earlier stay and `Own`; any other is gone, and reported only once it has been gone for `InPlaceEdits.SettleTime`. A move counts what it replaces until it is done, as an index over the budget would be no index. A document that is in both places shares one history folder on the share, so no slot of it is taken from the share; the copy keeps its history per place (`SlotKey.InTrash`: `data\history\` and `data\trash\history\`), so two documents of one id never take each other's slots, and a move never onto an entry whose last good bytes, current or kept, are of this Kiler (`LastGood.Own`). A load that ends over the budget, as a folder whose evictions were planned could not be read, evicts brief leftovers until it fits (`TrimToBudget`); the top of a history range is the last good version; a slot read from the share (`SlotEntry.FromShare`) gives way to the copy's own bytes of its version. A load reports at most 1000 changes outside Kiler, and `InPlaceEdits.KeepOnly` forgets the edits of documents that are no longer edited.
- **The private folder in the copy** (M2.7b): `DocumentKey.Account` names the private folder of a document (`InPrivate(account)`), `null` for the data folder, so a private record and a shared one of one id are two keys, and every entry, slot and path of the copy carries it: `data\private\<account>\`, `kept\private\<account>\` and the history under them (`RootPath`), in one budget with the data folder (decided by the user). A private `DataFolder` has its `Account`, makes the keys of its listings with it, and takes keys with it or without one; the data folder refuses a key with an account (`IsDocumentOf`). Every hold of a private folder starts at the data folder and goes through `private\` (`HoldRoot`), each opened as itself, as `CreatePrivate` holds them: opened by its full path alone, its root would be reached through a `private\` that anyone can swap for a link between the check of `OpenPrivate` and the hold (security review of M2.7b). `DataCopy.Open(…, account)` takes the private folder of the current user as the user's own (`IsOwn`); since M2.7c the entries of another account stay in the index as a private folder of another user, and `DeleteFilesNotNamed` walks every private folder of the copy (`CopyRoots`). A load lists the private folder after the data folder (`ListPrivate`): one that is not there gives its folders as listed whole and empty, so its documents are gone; one that cannot be opened is reported and its documents stay; only the root of the data folder makes a load throw. A write through the copy goes to the root of its key (`RootOf`); a key of another private folder is an `ArgumentException`.
- **The private folders of other users** (M2.7c, decided by the user): an admin's copy takes those of the accounts given to `DataCopy.CopyOthers` (M4 gives them after the sign-in), never every folder in `private\`, at most `MaxOthers` (200, security review); each call takes the place of the last, the current user's account stays the user's own, and an account that is no longer given, and every one before the first call, stays in the index as it is, neither loaded nor let go, so a forged sign-in never costs the last good bytes. A load lists them after the user's own, one pass each (`LoadFolders` with an `OtherCap`), with the data folder and `private\` held across the passes (`HoldPrivateFolders`, as the own pass holds the root) and the folders of each pass held only for it; their files are read for their heads alone (`ReadFolder(…, headsOnly: true)`, `DocumentFormat.ReadHead`, `LoadedFile.Head`, no `Read`), they take no history (`PlanApart`, `TakeHistory`), and they are never given (`Give`, `Given`, `Went`); `LoadResult.Outside` reports their changes outside Kiler while they are given (`IsLoaded`), and those of a frozen one wait. Every budget is a `Cap` (the entries it counts, its limits, the cap it is within) with a `Room` for the pass: the user's own (`OwnCap`); each other private folder (`BytesPerOther`, `DocumentsPerOther`) within all of them (`OtherBytes`, `OtherDocuments`), whose brief leftovers make room only in it (`Room.Take`, `TrimToBudget`); `ReadIndex` counts the two apart: the user's own over twice their budget is no index, while the others alone over theirs leave only themselves out, as frozen entries are never trimmed; `HasRoom` of a write counts only the user's own. Writes to them are refused (`RootOf`).
- **The owner of a private folder** (M2.7d, decided by the user): a private `DataFolder` carries what its root is (`Identity`, a `FolderIdentity`: the owner and the id, never of index 0, read through the handle of the root). `CreatePrivate` gives those of the folder it made; `OpenPrivate(account)` holds the folder at the name and takes those, as first seen, and `OpenPrivate(account, expected)` takes what the copy knows without a hold. Every hold of the root (`HoldRoot`, `HoldPrivateRoot`) holds it with `READ_CONTROL` and compares its owner and id with `Identity`, and every hold of a folder below it (`Hold`, `HoldIfThere`, through `HoldBelow`) compares its owner with that of the root (`ThrowIfForeign`); `List` of a private folder lists it held (security review). Another is a `ForeignFolderException`, an `IOException`, before anything is read or written there. An owner that cannot be read, or an id of index 0, is a plain `IOException`: the folder cannot be checked, which is not proof of another. The copy keeps them per account in its index (`_roots`, `CopyIndex.Roots`, `RootEntry`). `DataCopy.CreatePrivate` keeps those of the folder it made once it is renamed to the name (`CreatePrivate(account, renamed)`), also when the check after the rename refuses the folder there (reviews). The first load or write that opens a private folder the copy knows nothing of keeps those of the folder at the name (`DataCopy.OpenPrivate`, with `_indexBehind`, as nothing else may change the index then), and later ones compare. A load reports a foreign root or folder as `SkipReason.ForeignFolder` (`SkipReasonOf`), and its documents stay as the copy has them; a write through the copy throws. `AcceptPrivateFolder` forgets it, so the next load or write takes the folder at the name as first seen. It covers only the root: a folder in it of another owner than the root stays refused, whatever root is accepted, and is put right on the share (decided by the user after the review): a folder of the history or the trash is deleted, and the next write that needs it makes it again; `records\`, which only `CreatePrivate` makes (a write holds it with `create: false`), is put back as a folder of the user. `ReadIndex` takes the root of the current user's account and of each account with entries in the index, so the entries bound them; that of another user the copy has nothing of is seen first again after a restart. A hold of a private root costs two requests more (owner and id), a hold of a folder in it one (owner). The limit: a copy that has never seen the private folder (a new copy, one whose user has none yet, one whose user's create was refused because a folder was there) takes the first folder at the name as it is, and an accept takes whatever folder is at the name at the next load.
- **The local copy and the load** (M2.7, `DataCopy`): `<copy>\data\` mirrors the share with the bytes of each document as the share has them (M2.7a: the last good bytes of a change outside Kiler are in `kept\`), and `<copy>\index.json` (`CopyIndex`, `CopyEntry` through `StorageJsonContext`) keeps per document the stamp of its listing, the owner, the damage, `Taken` and `GoneAt` on the clock given to `Open`, and the version, SHA-256 and length (`Copied`) of the bytes in the copy. Only the index is in memory; `Documents()` and `Load()` give new `Document`s, read anew and checked against the hash first. A load (`DataFolder.ListFolder`, `ReadFolder`) holds each folder once from its listing to its reads, lists with a limit (`IFileSystem.List(folder, limit)`), lets the copy choose what to read on the calling thread (`Choose`, for all folders at once since M2.7a), reads at most `LoadReads` (16) at a time on threads of its own (`Workers`, not the thread pool, which adds threads slowly for blocking work), checks the held folders after the reads, and never reads a file past the size of its listing (`TryReadBytes(stream, max, …)`). The copy writes its files through a temporary file and `NativeFiles.MoveFile`, also on `Workers`, and its index once per load, last; since M2.7a a file that the index on the disk names is deleted only after an index that no longer names it is written (`_stale`), and the bytes of a version that Kiler made are overwritten only after an index names where they went (`Guarded`). The budget (`MaxBytes` 64 MiB, `MaxDocuments` 20 000, `CopyLimits`) counts the last good bytes of gone and damaged documents too, and is decided before the reads; the leftovers of documents that were in the copy for less than `BriefStay` (a day, counting only the time the share listed them, `TakenAt`) make room for the documents of the share. A failed local write is `NotCopied`, never an exception of the load; links, bad names, unreadable files and what is over the budget are `SkippedEntry`s with an escaped name (`StorageName.Escape`), at most 1000 a load. `Open` touches no share, throws when the index is there but cannot be read, and deletes unnamed files of the copy only when they are 10 minutes old. Every guard and decision is in the notes of M2.7.
- **Times after the year 9999** (M2.7): anyone who can write a file of the share can give it a FILETIME after 9999, which Windows takes, and .NET throws `ArgumentOutOfRangeException` for it from `FileSystemEntry.CreationTimeUtc`/`LastWriteTimeUtc` and from `File.Get…TimeUtc` on a handle. `FileSystem.List` gives such an entry with `FileEntry.TimesUnread`, and `FileSystem.TimeOf` turns the read through a handle into an `IOException`. A new read of a time goes through them.
- **Names from the share** become paths, also in the local copy in the profile. Anyone can write the shared folder, so a name is checked before a path is built from it, and links are not followed.
- **The name check** (`StorageName`, M2.1): lowercase ASCII letters, digits, `.`, `-` and `_`, 1 to 64 characters; no leading or trailing dot, no `..`, no device name of Windows (also with an extension), no `.tmp` at the end, which is kept for temporary files and folders. Lowercase only, because a NAS may tell case apart and the local copy in the profile cannot. So M4 and M5 make every id and the folder name of an account in lowercase. The exception message never repeats a refused name.
- **Paths** come only from `DataFolder` (`DocumentPath`, `HistoryPath`, `TrashPath`) with a `DocumentKey` (`InFolder`, `AtRoot`, and `InPrivate` since M2.7b), which checks every name and has no `init` accessors. Never join a raw name into a path.
- **Roots** (M2.1): `DataFolder.Create` needs the folder above and takes an existing folder only when it holds nothing but empty folders of the layout; `Open` creates nothing; a root that is a link is refused. `CreatePrivate` makes `private\<account>.<random>.tmp\` and renames it without replacing, and refuses a private folder that exists, even an empty one: whoever makes it first is its owner (design 7.8). Since M2.6 the temporary folder and its folders are made new (`HoldNewFolder`, `FILE_CREATE`), the new private folder must have the id (not 0) and the owner of the temporary folder, read through the handle that made it, else it is refused after the rename; the data folder and `private\` are held for the whole create, and the temporary folder until just before the rename. A new root gets only the top folders; `history\<folder>\` and `trash\<folder>\` come with the first write or delete.
- **File operations** go through the internal `IFileSystem` (`FileSystem` on System.IO and `NativeFiles`, with the owners given to it, M2.6), so tests can put `TestFileSystem` with its hooks and its fake owners (`Owners`) in its place: `Before` (a step and its path; it can throw to fail the step), `CrashAt` (that step fails, a new file there keeps half its bytes, and every later step fails, as after a crash), `WriteTakes` (moves the write time of a new file on) and `Waits` (counted, not waited). `CreateFolder` makes one folder in a folder that exists, never a chain, and refuses a link or a file that is already in its place, through the same NtCreateFile call as `HoldOrCreateFolder` (M2.5). A link is any reparse point, from the attributes of the listing; the folder that is listed is checked with one request.
- **Document format** (M2.2): `DocumentFormat.New` and `Next` make the bytes and `Read` checks them; nothing else writes or parses a document file. Since M2.7c `Read` takes whether a file is damaged, and why, from `ReadHead`, which checks the whole file through a pooled `JsonDocument` and gives only the version, so the two never judge a file apart; only the content of a good file is then parsed into nodes. A written file: UTF-8 without a BOM, indented by 2 spaces, LF, a line end after the object, `id` then `version` then the content in its order, non-ASCII as it is. The limits are `DocumentFormat.MaxSize` (1 MiB) and `MaxDepth` (32). A read is strict, and a damaged file gives a `DocumentDamage`, not an exception: invalid UTF-8, comments, trailing commas, a name twice at any level, an escaped lone surrogate, too deep, too large, a wrong `id` or `version`, and `ID` or `Version` beside the layer's own. A stream is read up to `MaxSize` + 1 bytes and no further. `JsonNode.Parse` alone checks none of the UTF-8 inside strings, the lone surrogates or the BOM; the details are in the notes of M2.2.
- **Documents in the upper layers** (M4, M5): `Document.Content` is the object without `id` and `version`; they come only from `Document.Key` and `Document.Version`, and a write drops them from the content. The models read the content with case-sensitive JSON contexts, not the web defaults of `KilerJsonContext`, so a name in another case means nothing to them.
- **A read and a rename** (measured in M2.2, M2.3 and M2.5): a rename over a file that another handle holds open fails with access denied, with or without delete sharing, and so does one with only attribute access (`OpenTimes`), so such a handle is held only for a move. A handle with only attribute access stops no rename of the file itself or of a folder (M1.11). `IFileSystem.OpenRead` shares read, write and delete, and the writes retry the rename. A file that someone holds without delete sharing cannot be moved (a sharing violation).
- **Deletes and renames through a handle** (measured on NTFS in M2.4): `File.Delete` (DeleteFileW) uses POSIX semantics since Windows 10, so the name goes at once also while a reader holds the file. The classic `FileDispositionInfo` through a handle keeps the name taken until the last handle closes, and a rename without replace onto it gives "exists"; `FileDispositionInfoEx` with `POSIX_SEMANTICS` frees it when the deleting handle closes, as `NativeFiles.DeleteOnClose` does. A test that holds a file and expects its name to stay taken shows which one the code uses. `FileRenameInfo` through `SetFileInformationByHandle` fails with error 123 on a `\\?\` path and moves a bare name into the current folder of the process: do not use it.
- `share.json` is not checked again when it is read.

## Tests of the layer

- The tests give a data folder the fake owners, `DataFolder.Create(path, new TestOwners())` (M2.6): the owner of a file is the one the test gave it, found by the file id, so it follows a move; `TestOwners.Me` by default, and `null` for a handle without `READ_CONTROL`, as the owners of Windows give, so a handle of the layer that could not read the real owner fails a test. `TestFileSystem.ZeroIds` gives every folder the index 0.
- File tests work in a temporary folder that is deleted after the test. In Kiler.Storage.Tests it comes from `TestFolder` and nowhere else, so `KILER_TEST_FOLDER` can point all of them to a temporary subfolder of the real shared folder (M2.11); the test folders are then made right in it. `TestFolder.CreateJunction` makes a junction and skips the test off a local disk, where Windows cannot make one. `Directory.Delete` with `recursive` fails on a junction for a user who is not an administrator, because it calls `DeleteVolumeMountPoint`, so `TestFolder` deletes the links first (M2.1).
- `TestFolder.CreateFileLink` makes a symbolic link and skips the test where Windows makes none (an ordinary user needs developer mode); `TestFolder.MakeMountPoint` makes an empty folder a mount point in place, through `FSCTL_SET_REPARSE_POINT`, only on a local disk (M2.3). Since M2.5: `CreateFolderLink` makes a symbolic link to a folder; `DenyWriteAttributes` puts a deny ACE for the attributes and times on a file, as a file server may for a file of another account; `ThroughLoopbackShare` gives the path of a test folder through `\\localhost\<drive>$`, so a test goes over SMB and a UNC path, and skips where the share cannot be reached (it was reachable on the developer machine); `TryMakeMountPoint` gives the error of Windows instead of asserting, for a test that expects the mount point to be refused. `TestFileSystem.MarkersKeepNothing` makes no markers, so a test can still reach the checks that the marker makes unreachable on NTFS.
- A guard of the layer is proven by a test that fails without it, and a race is shown by a hook at the step in between (`TestFileSystem.Before`) rather than by threads, which meet there too seldom (M2.4, M2.5).
- The write time of a file has the resolution of the system clock, about 15 ms, so two writes in a row can have the same one: a test sees that a file was not written again by holding it without delete sharing, so a replace would fail and be reported, not by its write time (M2.7).
- `DataCopy` takes a `TimeProvider`: the tests that time how long a document was in the copy, or the age of its files, give it a `FakeTimeProvider` that starts at the real time (`DataCopyTests._clock`).
- A test writes a document file of the share as Kiler leaves it, through `DataFolder` or `TestFolder.WriteAsKiler`, never with a bare `File.WriteAllBytes`: a new file written so gets a write time a moment after its creation time in about half of the cases (measured in M2.7a), so it looks edited in place, which the copy follows as a change outside Kiler. `TestFolder.EditInPlace` makes a real edit in place.
