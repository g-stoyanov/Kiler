# Kiler: UI

Decisions come from `docs/PLAN.md` (section 2, M1, M4, M6, M7), `docs/tasks/M1.md`, `docs/tasks/M4.md`, `docs/tasks/M6.md` and sections 7.5–7.7 and 8–10 of the design (`KILER_DESIGN.md`, local, not in git). Anything not decided yet is listed under "Deferred". Do not invent it; if a task needs such a decision, ask.

## Basics

- React 19, TypeScript, Vite. ESLint and Prettier. TypeScript in strict mode, as a good practice.
- The browser is only the view. Filters, search, permissions and encryption live in C#.
- The build is embedded in `Kiler.exe`. **The app works without internet:** every library is in the build. No CDN and no requests to external addresses.
- The app is entirely in English: UI texts, messages and errors (PLAN section 8, rule 9). The Bulgarian texts in the design are only examples of meaning; do not copy or translate them word for word.
- Package versions are the current stable ones when `src/ui` is created (PLAN section 2), checked with `docs-researcher`, not from memory. `package-lock.json` goes into git, because `npm ci` needs it (M1.8, CI in M1.9). `node_modules` and `dist` do not.
- Fixed in M1.7 (`src/ui/package.json`): Vite 8, React 19.3, ESLint 10 with typescript-eslint `strict`, Prettier 3, Vitest 5, jsdom 30.
  - TypeScript stays on `~6.0`: typescript-eslint 8 does not support TypeScript 7, which has no programmatic API. Move to 7 only when typescript-eslint does.
  - create-vite makes React projects with Oxlint by default; Kiler uses ESLint (`--eslint`).
  - jsdom 30 needs Node 24.15 or newer (`engines` in `package.json`).
- On the developer machine Node.js is a portable install on the user PATH, without admin rights; a shell started before it was put there does not see it. A corporate proxy inspects HTTPS with its own root certificate, which Node 24 trusts from the Windows store, so npm works as it is. Do not turn off TLS checks (`strict-ssl`).
- Node 24 runs the TypeScript of `dev/` as it is, by stripping the types: relative imports name the `.ts` file, and only erasable syntax (`erasableSyntaxOnly`), so no parameter properties or enums.
- Prettier writes LF and 2 spaces (`.prettierrc.json`, `.editorconfig`), and `.gitattributes` keeps LF in `src/ui` also where `core.autocrlf` is on (CI on Windows).
- The keys of the `globals` package are camelCase (`globals.sharedWorker`). A wrong key gives `undefined`, which ESLint accepts without a word (M1.7).
- `build.cssTarget` names browsers with `light-dark()` (Chrome and Edge 123, Firefox 120). With an older target, lightningcss rewrites `light-dark()` into variables that resolve once on the root.

## Layout (M1.7)

- `src/texts.ts`: all the UI texts, in one place (decided in M1.7). Components take their texts from it. From M6 (decided by the user at its start), `texts.ts` takes each area of M6 from a file of its own in `src/texts/` (`browse.ts`, `record.ts`, `form.ts`, `code.ts`, `history.ts`), so two parallel sessions never write one file; the components still read `texts.<area>`, and a new text of an area goes into its file.
- A screen of M6 keeps its CSS in a file of its own beside its component, which imports it (`Browse.css`), on the variables of `index.css`; `index.css` keeps the shared classes. The build puts the imported CSS into its stylesheet file, which the policy allows. `main.tsx` imports `index.css` before `App.tsx`, so a rule of a screen comes later and wins its ties with a shared one; until the merge of M6.3 it came first and lost them, so `Browse.css` names the parent in such rules.
- That stylesheet is one for all the screens, so a class of a screen's CSS is global: a new class takes a name that no other CSS file defines, except a shared class of `index.css` in a compound selector (`.tree-row.chosen`). Two parallel sessions both defined `.record-fields` and `.record-path`, the list's and the record view's, and the list's flex won over the view's grid, so a code block overflowed its card; no test saw it, only the screenshots of M6.13, which renamed the list's to `.record-row-*`. A class in two files shows with: `for f in src/ui/src/*.css; do grep -oE '\.[a-zA-Z][a-zA-Z0-9_-]*' "$f" | sort -u | sed "s|$| $f|"; done | awk '{n[$1]++; c[$1]=c[$1]" "$2} END {for (k in n) if (n[k]>1) print k, c[k]}'` (in Git Bash; the `.ts`, `.tsx` and `.css` it also prints come from the comments).
- The shared files of `src/ui` (`api.ts`, `App.tsx`, `texts.ts`, `index.css`, the shared parts of M6.2, `package.json`, `package-lock.json`, `vite.config.ts` and the other configs) change only in the task that owns them (its "Owns" in `docs/tasks/M6.md`, and `docs/tasks/README.md`, "Parallel sessions"). A task in a parallel session that needs a change of one asks the main session instead.
- Screens (decided at the start of M4, whose screens come first): no component library, own CSS on the variables of `index.css`; React Router for the addresses, which have no dot in their last segment (M1.8); the data through `api.ts` and React state, with no data library.
- React Router 8 (M4.7, from `docs-researcher`): the package `react-router` only (v8 dropped `react-router-dom`, whose npm `latest` is still v7), in declarative mode: `BrowserRouter`, `Routes`, `Route`, `Link`, `Navigate`, `useNavigate`, all from `react-router`. No data mode and no `ScrollRestoration`, which writes an inline script that the CSP blocks. A test that needs a route renders it in `MemoryRouter` with `initialEntries`.
- `src/api.ts`: the API client, with a function and a reader for each endpoint. `src/theme.ts`: the theme.
- The page (M4.7): `App.tsx` makes the `SessionStore` (`session.ts`) and the frame; the content shows only while the stream is connected. Under it, `DataGate.tsx` shows the state of the data, or the wizard (`Wizard.tsx`, its logic in `wizard.ts`), and only then the routes, behind the session (`SessionGate` in `App.tsx`). A screen takes the session as a prop, and the answer of an action that gives the session goes to `store.set`. The foot line of the frame (M6.2) shows the data folder, which `DataGate` gives through `onFolder` at each read of the data, and the version, read from `/api/health` once the stream has connected; it keeps what it last read after a stop.
- The routes by the session (M4.8, `AppRoutes` in `App.tsx`): without a session and without guest mode only `/sign-in`, which every other address leads to with `{ from }` in the state of the address (`signInFrom`), and the sign-in goes back there (`returnPath`, which takes only a path of this origin); with `mustChangePassword` only `/password`; else the screens. A new screen is a route of the last set, and needs no check of its own for these; one that needs a session renders `ToSignIn` for a guest, as `/password` does.
- After `store.set` of a session without a sign-in (a lock), the routes alone send the page to the sign-in: a screen that also calls `navigate` races them, as the store renders the new session at once and React Router 8 changes the address in a transition, so a `*` route of the guest's set can win (M4.8 code review). The same holds for any `navigate` right after `store.set` that a route of the new set redirects.
- Each screen keeps its logic in a `.ts` module apart from its component, as a pure function or reducer (`wizard.ts`, `signIn.ts`, `changePassword.ts`, and `admin.ts` for both admin screens), so Vitest tests it in `node` without rendering. A form field is `Field.tsx`: the label, the input and the problem of the page's checks.
- The admin screens (M4.9): `/users` (`Users.tsx`) and `/levels` (`Levels.tsx`) in the last set of routes, behind `AdminOnly` in `App.tsx` (a guest to the sign-in, a user who is not an admin to `/`), with links in the header of an admin without a temporary password. A refusal of an admin request shows through `AdminRefusal.tsx`: Kiler's sentence, and "Sign in again" (a lock) on `levelsChanged`.
- A field that is disabled while its request runs loses the focus, so the screen gives it back after a refusal (`SignIn.tsx`).
- The screens of the records (M6, decided at its start): `/` is the main view (`Browse.tsx`), and its query is in the address as the query of `GET /api/records` (`q`, `stash`, `template`, `tag` once per tag, `field.<key>`), so a link to a node is `/?stash=<ids>`, and Back and a reload keep the view; `/records/<id>` is a record (`RecordPage.tsx`), `/records/<id>/edit` its edit and `/new` a new record (`RecordForm.tsx`), with `?stash=<ids>` from a "+"; `/trash` and `/records/<id>/history` are M6.14. `AppRoutes` is keyed by `signedIn` and `levels`, so a change of the levels mounts every screen again. In `App.tsx` (M6.2): the screens sit under the layout route `Screens`, which shows the banner of a guest after a lock (`/sign-in` and `/password` are outside it); `ByRecord` mounts a screen of one record again for each id, so nothing of one record stays on another; `EditorOnly` sends a guest from `/new` and the edit to the sign-in, and a user without `canEdit` back. The header has "Trash" for a signed-in user, and the brand links to `/`. The props of the screens are fixed there: `Browse` and `Trash` take `{ session }`, `RecordPage` and `History` `{ id, session }`, and `RecordForm` `{ id?, session }` (no `id` at `/new`). Until its task, a screen is a typed constant without parameters, `(props: …) => ReactNode`, which shows its title, as an unused prop fails the lint and the type check; the task that fills it makes it `export function …` with the same props.
- The shared parts of the records (M6.2), which a parallel task uses and does not change:
  - `fields.ts`: `recordPath(id)`, the address of a record; `isCodeValue` and `isRefValue`, a value told by its shape; `valueText`, the text of a value (null for a `ref` that has gone); `urlView`, a `url` as `link`, `local` or `text`; `localDateTime(iso)`, a time of Kiler as `2026-10-21 14:32` in the browser's zone;
  - `FieldValue.tsx` (`field`, `type` of the field in the template, `shorten`): a field by its `kind`; without `type` a `url` is text; the padlock is its text alone, and a screen puts its button beside it; a `local` url has its own "Copy" and the sentence why;
  - `CopyButton.tsx` (`value`, `label`, `copyFailed`): `value` is a text, or `(signal) => Promise<string>` that gives it on the click, such as a `secret`, aborted when the button unmounts; a refused request shows its sentence; "Copied" goes after 2 s. `Secret.tsx` uses it;
  - `CodeBlock.tsx` (`code`, `language`, `dialect`) and `CodeEditor.tsx` (`id`, `value`, `onChange`, `language`, `dialect`, `disabled`): CodeMirror since M6.9, with the props of M6.2, its logic in `code.ts`. `CodeBlock` has its own "Copy" of the code that shows, so a screen puts none beside it, and for a SQL "Format" / "Show as saved", which only shows. `CodeEditor` has "Format" for a SQL, one step of its history (Ctrl+Z); a new `value` from the props replaces the code without a step and is not echoed to `onChange`. Its `id` is on a host `<div>` (`tabIndex={-1}`) whose `focus` goes on to the editor, so `getElementById(id).focus()` works; the `<label for={id}>` of `Field.tsx` stays, and the editor takes the label's text as its `aria-label`;
  - `changes.ts`, whose `useChanges()` grows at each `changed` event (M6.11): a screen that reads records puts it among the dependencies of its read. Its reads at the event carry the mark of no activity (`changes.follows`, "API" below) with no change of the screen. A write of this Kiler gives two events, at the write and at the next load of the shared folder, so each screen reads twice.
- The history and the trash (M6.14): `history.ts` gives the buttons by the levels of the record, the trash item or the versions and those of the session (`holdsEvery`); the record view has "History" and "Delete", `/trash` (`Trash.tsx`) "Restore", `/records/<id>/history` (`History.tsx`) "Restore" of an old version; each refusal shows its sentence and reads again.
- The stash picker (M6.6): `StashPicker.tsx` takes `{ id, state, dispatch, disabled }`, with the state of `stashPickerReducer` (`stashPicker.ts`) in the form, which starts it with `startOfNode(pathOfAddress(<?stash=>))` or `startOfRecord(record.stash)`; `id` is on the control that takes the focus (the open position, else the last control).
- The record form (M6.7, M6.8): `RecordForm.tsx` reads, `Editor` holds the draft (`recordFormReducer`) and the picker; the logic is in `recordForm.ts` (`fieldViews` for the levels and the padlocks, `checkDraft`, `recordRequest`, `overwriteRequest`); `FieldInput.tsx` is a field by its type, with `TagsInput.tsx` and `RefPicker.tsx`.
- The texts of the frame, of `FieldValue` and of `CopyButton` are in `texts.ts` (`frame`, `field`, `copy`).
- `src/events.ts`: the event stream and the hub that shares it; it runs in the page and in the worker, so it uses only what both have. `src/events-worker.ts`: the SharedWorker. `src/connection.ts`: the page side.
- Three TypeScript projects (`tsc -b`): `tsconfig.app.json` (DOM), `tsconfig.worker.json` (WebWorker, only the worker file) and `tsconfig.node.json` (`vite.config.ts` and `dev/`). DOM and WebWorker cannot be in one project. A module imported by the worker is checked in both, so it must not use `SharedWorker` or other names that only one of them has.
- `dev/`: the dev mode (Node), with its tests.
- Commands in `src/ui`: `npm run dev`, `npm run build`, `npm run lint`, `npm run typecheck`, `npm test`, `npm run format:check` (`npm run format` writes).
- `check-ui.ps1` in the repository root runs `format:check`, `lint`, `typecheck` and `test`, and CI runs it before the build (M1.9). It runs `npm ci --ignore-scripts` first only when `package-lock.json` is newer than `node_modules`, the rule of the Release build, so it leaves alone the `node_modules` of a running dev server.

## API

- Requests go only to the same origin, `/api/...`.
- The API of the templates, stashes and records (M5, M6) is the contract in `docs/api.md` (M5.1): the endpoints, the shapes, the rights and the refusals. `api.ts` follows it, and a change of the API goes there first.
- Sign-in uses an HttpOnly cookie set by the server. JavaScript never sees or stores the token, not in `localStorage` or anywhere else. The cookie is named per instance (M1.7): `kiler`, and `kiler-<key>` with `--data`.
- The API client (`api.ts`) handles errors in one place: every failure becomes an `ApiError` with a message for the user (401, 503, another status, no answer, an answer it cannot read), and the page shows it instead of breaking. An abort by the caller passes through, but one while the body of a refusal is read becomes the status, so a screen where only the last read counts checks its own `signal.aborted`, not the kind of the error (M6.1 code review). It refuses a path outside `/api/`, and one with a `.` or `..` segment, before any request: `encodeURIComponent` leaves the dots of an id, and the id of a `ref` is any text of the share (M6.1).
- The readers of the records (M6.1) are strict: a member that does not fit makes the whole answer `invalid`, and a field of any `kind` but `value` that carries a value does not fit, so no answer but the request of a secret puts a secret value into the page.
- `EventSource` on `/api/events` is the heartbeat. Since M4 it also carries `session` (no data): the session was locked or changed, so every page drops the data it shows and reads the session again; it goes through the SharedWorker as another `HubMessage` type. Since M6.11 it carries `changed` (no data) the same way (`onChanged` of `KilerEvents`, the third listener of `connectEvents`): the data changed, by a load of the shared folder or a write of this Kiler, and `App.tsx` passes it to `changes.note()`, so `useChanges()` grows and the screens read again (`docs/api.md`, "The changes of other users").
- A read that the page makes of its own, not at an action of the user, must not be activity for the automatic lock, or the page never locks (decided by the user in M6.11): `/api/events`, `/api/health` and `/api/data` are no activity in Kiler, and a read at `changed` carries the mark. `changes.ts` holds it: `changes.follows` is true from a `changed` event until the user's next input in the page (`inputEvents`: `keydown`, `pointerdown`, `click`, `input` and `popstate`, watched on the window in the capture phase by `changes.watchInput`, which `App.tsx` starts), and `api.ts` then sends each `GET` with `Kiler-Activity: none` (`activityHeader`, `noActivity`), which Kiler takes only on a `GET`. Another read of its own, such as one on a timer, needs a decision first.
- The session is one per Kiler process, shared by all its pages (M4). A guest, a locked session and a session that must change its password see only the screens they may; the server checks every request anyway.
- `SessionStore` (`session.ts`, M4.7) reads `GET /api/session` once the stream has connected (behind the worker, once the page's port is in its set, so no `session` event after it is missed), again on each connect and each `session` event, and on an action of the user (`reload`), never on a timer: the read is activity for the automatic lock. On the event and on a stop it drops the session first, so everything under `SessionGate` unmounts and drops its state. Only the last read counts; the answer of an action (`set`) cancels a read under way. A session without a sign-in after one with it is `locked` (M4.8), until the next sign-in or a stop: the sign-in is then the lock screen, and a guest's screens show a banner that says that Kiler has locked (`Screens` in `App.tsx`).
- A refusal of Kiler, `{ "error" }` with 400, 403, 404 or 409, is an `ApiError` of kind `refused` whose message is Kiler's sentence, with its status. A refusal of a write also keeps what the page acts on (M6.1): `field`, the key of the member of a 400 that does not fit, and `current`, the record of the 409 of a conflict (`docs/api.md`, "Conflict"); both are null otherwise, and a refusal whose `field` or `current` does not fit is `invalid`. After a 403 of an endpoint other than the sign-in, the screen reads the session again (`store.reload()`); after a 409 of the wizard, the state of the data.
- A refused read of an admin list (M4.9) only shows its sentence with "Try again", and reads no session: a session whose file says `isAdmin` without the key of every level gets 403 on every read, and a new read of the session would mount the screen and read again, in a loop. A refused admin action follows the rule above, and its 409 reads the list again (`afterAdminRefusal` in `admin.ts`).
- `store.reload()` shows "Reading the session…" while it reads, so the screen unmounts and its message goes. A refusal that is about the form itself, such as the 403 of a wrong current password, therefore reads nothing again, and the screen tells it by Kiler's sentence. The sentences that the page acts on are constants in `api.ts` (`missingFile`, `passwordRefusals`, `levelsChanged`), and the C# constant or `Message` names `api.ts`, so a change of one changes the other. The change of password (`afterPasswordRefusal`) also offers a new sign-in (a lock, then `/sign-in`) on the 409 of a user file that has changed, and reads the session after a 400 of the forced change: a change of password gives no `session` event, so another page may still show the forced change.
- `GET /api/data` is no activity, so `DataGate` asks it on a timer: every second while the copy opens, every 10 s once it is open or offline, and never while the wizard shows, so a new state does not take the recovery key away. A new read keeps the last state on the screen, so the wizard keeps its form. The rules are in `data.ts`: the wizard is offered in `missing`, and in `open` while `levels` and `settings` are both `missingFile`, the sentence of `DataApi.MissingFile`. The session read at the connect may be of a copy that was still opening, without its guest mode, so once the routes show after a state that did not show them, `DataGate` reads the session again (code review); that covers the end of the wizard too.
- **One stream for all the pages** (decided in M1.7). Without TLS the browser talks HTTP/1.1 with at most 6 connections per host, so a stream per page would stall every request from the sixth page on. A SharedWorker (`events-worker.ts`) holds the one `EventSource` and sends its state to each page. The browser ends the worker when the last page of the origin closes, and that closes the stream. A page says `bye` to the worker when it unmounts; a page that closes says nothing, and its port stays in the worker's set.
- Without SharedWorker, or when the worker does not start (its `error` event, or the constructor throws), the page holds a stream of its own. It falls back once: a second `error` must not open a new stream after a stop.
- On its first `error` the stream is closed, in the handler itself, and the state becomes "stopped". It does not let the browser reconnect: after a stop, each try sends the cookie to the old port, and cookies are not separated by port, so by then the cookie can hold the token of a newer Kiler, and the old port can belong to another program (M1.6 security review). The one exception: a page that loads after the stop and joins the worker opens a new stream; that load has just sent the cookie to the same port anyway. The dev mode needs it: the next `npm run dev` serves the page on the same Vite port, and an old tab keeps the old worker alive.
- The SharedWorker is found by its URL and name (`kiler-events`), always with the same options. The constructor must keep the exact form `new SharedWorker(new URL('./events-worker.ts', import.meta.url), {...})`, or Vite does not bundle the worker. The build emits it as `dist/assets/events-worker-<hash>.js` (`worker.format: 'es'`).

## Dev mode (M1.7)

- `npm run dev` (`dev/start.ts`):
  - starts Kiler with `dotnet run --project src/Kiler.App -- --no-browser --data <repo>/dev-data`. `dev-data/` is out of git, and a data folder of its own makes the dev Kiler an instance of its own, apart from the user's Kiler (M1.5);
  - reads Kiler's `Open:` line (`dev/kiler.ts`) and prints Kiler's output with the token hidden;
  - starts the Vite dev server with the proxy to that port (`dev/vite-server.ts`);
  - opens the default browser on `http://127.0.0.1:<vite port>/?t=<token>` through `rundll32 url.dll,FileProtocolHandler`. Not through Vite's `openBrowser`, which first requests the page itself from Node, token and all;
  - stops the dev server when Kiler stops (the last page closed, or Ctrl+C, which reaches Kiler through the shared console).
- `npm run dev -- --no-browser` prints `Open: <dev address with the token>` instead, as Kiler does with `--no-browser`.
- `npm run dev -- --account <name>` (M4.8) passes `--account` to Kiler, for a second user of `dev-data` (decisions of M4). The single instance is per data folder, so it starts once the first dev Kiler has stopped.
- `dev-data` with the demo data (M4.10, its stashes and records from M5.5): from the repository root, `dotnet run --project tools\Kiler.DemoData -- dev-data`, with `--replace` over one that is there, while no dev Kiler runs, and `--volume` for 2000 records. Then `npm run dev -- --account demo.admin`, or another demo user; the accounts and passwords are in the kiler-dotnet skill, `demodata.md`.
- A second `npm run dev` while one runs stops with a message: the dev Kiler is running already, or, after a change of the C# code, `dotnet run` cannot rebuild the exe that the first one runs.
- The proxy (`kilerProxy`) keeps the protection on:
  - only `/api/` (with the slash, so `/apiary` stays with Vite) and the exchange `^/\?t=`, a RegExp on the path with the query. Vite serves `/` without `t`;
  - `changeOrigin: true`, so `Host` names the Kiler port; otherwise the guard returns 400 (M1.4). The browser's cookies, `Sec-Fetch-Site`, `Set-Cookie` and `Location: /` pass as they are;
  - the Vite dev server listens on `127.0.0.1` only, as Kiler does (M1.3), and the page is opened there, not on `localhost` (M1.5);
  - the proxy closes its request to `/api/events` when the browser closes its own, so a closed tab stops Kiler in dev mode too. Vite 8 proxies with http-proxy-3, which does it on the response's `close`; the old `http-proxy` did not. Do not set the proxy's `fetch` options: that path does not close the request. `dev/vite-server.test.ts` checks all of this against a made-up Kiler.
- **No HMR** (decided in M1.7, after the security review): `server.ws: false`, and the plugin `kiler-refuse-websockets` in `vite.config.ts` refuses every WebSocket handshake at once. With HMR, Vite's client tries the port of a dev server that went away every second while the tab is visible, with every cookie of 127.0.0.1 (the user's real Kiler too), and reloads into whatever answers: the reconnect that the event stream avoids. Without the plugin, Vite's proxy leaves the handshake open until the server stops, and the client then tries once more. After a code change, reload the page by hand; a reload keeps Kiler running.
- The dev server sends `Content-Security-Policy: frame-ancestors 'none'` and `X-Frame-Options: DENY`: in dev mode Vite serves the page, without Kiler's guard, so a page on another port of 127.0.0.1 could frame it with the cookie.
- Vite logs the address of a failed proxy request (`http proxy error: /?t=<token>`), so the dev server gets a logger that hides the token (`tokenMaskingLogger`).
- A change of `vite.config.ts` restarts the dev server, which drops the streams; the page then shows "stopped", and Kiler stops after the idle wait. Run `npm run dev` again.

## The embedded build (M1.8)

- A Release build and a publish of Kiler run `npm ci` and `npm run build` and embed `dist/` in `Kiler.exe` (kiler-dotnet, "UI files and publish"). A Debug Kiler has no UI; in dev mode Vite serves it.
- Kiler serves every UI file with a Content Security Policy: `default-src 'self'; img-src 'self' data:; object-src 'none'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'`. So the UI code:
  - has no inline scripts and no event handler attributes;
  - has no `<style>` elements or `style` attributes in HTML. React's `style` prop is fine, because it goes through the CSSOM;
  - loads nothing from other hosts, and loads fonts and other files as files. Vite puts assets under 4 KB inline as `data:` (`build.assetsInlineLimit`), which the policy allows only for images.

  A library that injects styles or needs more, such as CodeMirror or Mermaid (M6, M7), changes the policy in its own task, with a security review. CodeMirror did not (M6.9): style-mod writes a `<style>` element into a document, which the policy refuses, but adopts a constructed style sheet into a shadow root, which the policy does not govern, so `useCodeView` (`code.ts`) mounts the editor in a shadow root of a host `<div>`. The page's CSS does not reach in: its look is an `EditorView.theme` and a `HighlightStyle` on CSS variables, which inherit into the shadow root. This helps only a library that adds its CSS as a constructed sheet, as style-mod does: a `<style>` element or a `style` attribute in markup is refused inside a shadow root too, and Mermaid (M7) puts both into the SVG it returns (security review of M6.9).
- The dev server does not send this policy, because in dev mode Vite and the React plugin use inline scripts. A violation therefore shows only in the embedded build: check the console of the published exe, and the E2E tests (M6) fail on a `securitypolicyviolation` event.
- Addresses of the UI's own routing (M4.7) have no dot in their last segment. Kiler gives `index.html` only to such addresses; a name with a dot is a file, and a missing one is 404 (also on a reload).
- `/assets/` is cached for a year without a check, because Vite puts there only names with a hash of the content. Files in `public/` keep their names, are served from the root and are checked each time; nothing goes into `public/assets/`.

## Secret values

- Passwords (`secret` fields) do not come with lists. The value is requested from the server only on "show" or "copy".
- A shown value does not stay in state longer than needed. It is never logged and never put in a URL.
- Fields above the user's level are shown with a lock: "🔒 requires level X", with the `levelName` of the field. Until the locking per level (PLAN section 10) the unlock button is the sign-in, for a guest; a signed-in user below the level has nothing to unlock, so the padlock has no button (decided at the start of M6).
- A value of a `secret` comes only from its own request, on "Show" or "Copy" (`use`). A shown value hides again after 30 s (`shownSeconds` in `recordView.ts`), on "Hide", on leaving the screen, at each read of the record again and at each change of the session store; `ShownSecrets` holds it and aborts its request at each of these (M6.5).
- A password is kept in state only until its request is sent. Its fields have `autocomplete="current-password"` or `"new-password"`.
- The recovery key (the wizard) and a temporary password (the admin actions) come once, in the answer of their request: shown with a copy button (`Secret.tsx`, for both), kept in state only while their screen is open, and gone when it closes. The temporary password is `temporary` of `usersReducer` (`admin.ts`), shown in place of the list until "Close"; leaving the screen drops it too. A pasted recovery key is trimmed first (`kiler-crypto`, "Rules"). The recovery key sits above `SessionGate` (in `DataGate`), so a `session` event does not take it away before the user has saved it; a stop of the stream does, as Kiler has stopped.
- The copy button (`CopyButton.tsx`) uses `navigator.clipboard.writeText`; 127.0.0.1 is a secure context. When the browser refuses, the screen says to copy by hand (the Claude Code in-app browser refuses).
- At the `session` event of a lock, the page drops every decrypted value it holds, not only the shown ones.

## HTML, Markdown, Mermaid

- No `dangerouslySetInnerHTML` with unsanitized HTML. All HTML from Markdown goes through DOMPurify.
- A `url` of a record is a link only with `http` or `https` (`docs/api.md`, "Values by type"), opened in a new tab with `rel="noopener noreferrer"`. One whose host is `localhost`, a name under `.localhost`, an address of `127.0.0.0/8` or `[::1]` is text with "Copy", and a short sentence says why: the browser sends the cookie of Kiler to every port of 127.0.0.1 (the M1.4 risk; decided by the user at the start of M6). `fields.ts` decides it (M6.2).
- Mermaid in strict mode (M7).

## Theme

Light, dark and system (M1.7). The choice is kept in `localStorage` (`kiler.theme`) until the personal configuration after the exam (PLAN section 10, item 11), which keeps it through the API. The origin has the port, which changes with every start, so until then a choice in `localStorage` lasts one run of Kiler; the open nodes of the tree (M6.3) too.

- Every colour is a CSS variable with `light-dark(<light>, <dark>)` (`index.css`). The root has `color-scheme: light dark`, so "system" follows Windows by CSS alone, also before the script runs and when Windows changes its theme. A light or dark choice sets `data-theme` on the root, which sets `color-scheme` to one side.
- `main.tsx` applies the saved choice before the first render. A storage that throws counts as no choice.
- Components with themes of their own (CodeMirror, Mermaid in M6/M7) need the resolved theme: `data-theme`, or `matchMedia('(prefers-color-scheme: dark)')` without it. CodeMirror's colours are CSS variables (`index.css`, `Code.css`, `--code-*` with `light-dark()`) that inherit into its shadow root, and `useResolvedTheme` (`code.ts`, watching `data-theme` and the media query) picks its dark base theme (M6.9).

## Manual checks

- The Claude Code in-app browser blocks the network requests of a SharedWorker: its module imports and its `EventSource` fail, while a dedicated Worker and the page fetch normally (checked in M1.7). There the dev mode falls back to a stream per page, because the worker script does not load, and the build shows "Stopped", because the worker's stream fails. Check the shared stream in Chrome or Edge.
- Run `npm run dev -- --no-browser` from Claude, so it opens no window on the user's desktop; the address with the token is then in its output.
- In the in-app browser, `preview_stop` leaves the tab open, and its stream keeps the dev Kiler running: close the tab with `tabs_close`, and Kiler stops after its idle wait (M6.2).
- In the user's PowerShell it is `npm.cmd run dev`: the AllSigned policy stops the unsigned `npm.ps1`. In cmd it is `npm`.
- In Chrome or Edge, `chrome://inspect/#workers` or `edge://inspect/#workers` lists the shared worker `kiler-events`, and `Get-NetTCPConnection -RemotePort <kiler port> -State Established` counts the streams (one for all the tabs).
- The embedded build: `publish.ps1`, then `artifacts\publish\Kiler.exe --no-browser --data <temporary folder>` and the `Open:` address in Chrome or Edge. Its console shows CSP violations, which the dev mode does not have.
- Without a window (M4.7): headless Chrome (`chrome.exe --headless=new --remote-debugging-port=<port> --user-data-dir=<new folder>`) and a Node script over CDP (Node 24 has `fetch` and `WebSocket`): `PUT /json/new`, then `Page.addScriptToEvaluateOnNewDocument` with a `securitypolicyviolation` listener that keeps the violations in a global, `Page.navigate` to the `Open:` address, and `Runtime.evaluate` to fill the fields (the native `value` setter and an `input` event, as React reads them) and click. `Log.entryAdded` gives the console. Kiler stops 60 s after its start without a stream, so start the browser at once. Headless Edge ended the stream of the SharedWorker a moment after it opened, without an error to the page, so its state stayed "Connected" and Kiler stopped 10 s later; headless Chrome keeps it, and so does a page without SharedWorker in Edge. The frame reads `/api/health` for its version once the stream has connected, which puts the stop off by 60 s and hides a dead stream that long. Headless Chrome fires no focus event while its page has no focus (`document.hasFocus()` false): `Emulation.setFocusEmulationEnabled({ enabled: true })` before a check of the focus (M6.9).
